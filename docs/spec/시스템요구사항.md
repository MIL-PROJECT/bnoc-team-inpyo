# 시스템 요구사항

## 2026-10-25 · SR-BE-004·017·031·032 신청 재사용 계약

요청 상세 DTO의 `canReuse`는 현재 역할이 requester이고 요청 소유자와 등록자가 모두 현재 계정일 때만 true다. 상태의 종결 여부로 재사용을 막지 않으며 기존 조회권한은 유지한다. UI는 이 값으로 버튼을 표시하되 클릭 시 원본을 다시 조회해 재검사한다. 별도 복제 저장 명령은 없고 새 신청 초안에서 기존 createRequest만 사용한다. 복사값은 명시적 허용 목록으로 제한하고 희망 일정·첨부·정비대상자·신원·상태·작업/이력·번호·버전/영수증을 제외한다. 제출 전 쓰기 없음, 원본 불변, 새 제출키/번호·대기 상태, 회의 재첨부 필수, 계정/경로 변경 중 늦은 응답 폐기·이동 취소·초안 정리를 검사한다.

## 2026-10-25 · SR-BE-041·043 원본 보기 정정

최신 사용자 요청은 권한 있는 원본 미리보기 복구다. 회의 첨부도 HWP/DOCX `render-source` 및 PDF/이미지 `inline` 경로로 원본을 제공한다. 기존 회의 미리보기·원본 경로 금지 조건은 이 결정으로 대체하며, 연결되지 않은 임시 파일·타 요청자의 원본 접근은 계속 거절한다. `excluded`는 서버 분석·메타데이터·검색·재분석 제외만 의미한다. DOCX는 서버 분석 범위를 확대하지 않고 브라우저 격리 프레임에서 본문/표/내장 이미지를 표시한다. 프레임에서 외부 네트워크·상위 페이지 접근·스크립트 문서 내용을 허용하지 않으며 렌더 오류·한도 초과 시 원본 다운로드를 유지한다. PC1280/1440의 실제 원본 표시, 권한 거절, 회의 분석 제외, 실패/닫기 동작을 검사한다.

> 2026-10-23 통합 기준: GitHub main8a561f8의 DEC033~035 일정·배정·후보고 집계·v9 자료 이관을 보존한다. 설문 시안도 선택 희망1/2지망과 실제 시작/완료/사유 후보고, 개별 작업의 작업 준비 표시를 같은 의미로 사용한다. 요청 종합 작업 중 상태는 유지한다. HWP 시안의 쓰기는 여전히 메모리이며 실제 API 목록에서 연 요청 상세는 실제 조회와 연결한다. 로그인 변경·자원 기능 재추가는 없다. 아래 과거 단일 희망시각·축약 후보고 설명과 충돌하면 이 기준을 우선한다.

> 2026-10-22 로그인 롤백 결정: 부서별 작업반 계정은 유지하며 같은 부서 내부의 행정병·작업병을 로그인에서 구분하지 않는다. 이번 추가 기능 작업의 로그인·계정 선택·인증 흐름 변경은 모두 기준051444d로 복원한다. 데모 전용 로그인/계정/세션·권한 관리 화면 대체를 제거하며 기존 SSO/부서 계정을 그대로 사용한다.

> 2026-10-24 문서 범위 정정: HWP/PDF 원본 보기·다운로드와 디지털 문서의 본문·메타데이터 추출 및 검색을 유지한다. OCR은 제외한다. 스캔 PDF는 텍스트가 없으면 `no_text`로 처리하고 원본 보기·다운로드만 제공한다. 과거 OCR 결과는 새 파서 버전으로 갱신하며 원본 첨부는 유지한다. 기존 첨부는 순차 재분석되므로 완료 전까지 내용 검색이 대기 상태일 수 있다.

> 최신 범위: FR-039 요청 입력 확장과 FR-040 가용 자원 기능은 철회했다. 설문 추가 기능은 FR-038 상태 안내, FR-041 요청·첨부 내용 검색, FR-042 HWP/PDF 원본 보기·본문·메타데이터 추출이다. OCR은 제외한다. 2026-10-24 팀원 피드백 FR-045~049도 유지한다. FR-043은 설문 기능이 아닌 기존 자기 반 권한 정리다.

### 상태 안내와 전체 흐름 · SR-BE-037

- **근거:** FR-038, UC-014, E-027.
- **동작:** 목록의 요청/우리 반 상태 배지에 동일한 마우스·키보드 안내를 제공한다. 상세에서 기본 흐름·예외 경로·현재 상태·부서 진행을 표시한다. 기존 상태 계산 결과를 설명하며 상태를 다시 계산하거나 변경하지 않는다.
- **입력:** 현재 역할에 허용된 상태·EffectiveWorkSummary·일반화된 진행 맥락과 공식 부서 대표번호 자료(자료 없음은 허용).
- **출력:** 2026-10-24 사용자 후속 결정에 따라 hover/focus는 상태 배지에 이미 표시된 상태/현재 단계 대신 요청의 유효 담당 부서 전체와 공식 대표번호를 표시한다. 개별 작업 배지는 해당 작업의 부서 하나를 표시한다. 번호 자료가 없으면 `대표번호 미등록`으로 표시하고 임의 번호를 만들지 않는다. 선조치 후보고는 수행 부서로 표현한다. 공식 번호는 요청자 군내전화·개인전화·정비대상자 번호로 대체하지 않는다. 상세는 기존 단계 도식을 계속 제공하고 예외·후보고 안내는 기존 기준을 유지한다. 상태만으로 이전 완료 이력·다음 담당자를 추정하지 않는다.
- **예외:** 후보고·취소·문서 대기·미해결 반환·유효 부서0개를 별도로 설명한다. 요청자에게 원문 반환 사유·내부 메모를 노출하지 않는다.
- **합격:** hover와 focus에 같은 담당 부서/번호 또는 `대표번호 미등록`이 나오고 Escape/초점 복귀가 동작한다. 여러 유효 부서는 모두 구분해 표시하며 작업 배지는 해당 부서만 표시한다. 담당 부서 없는 요청에는 전화번호를 만들지 않는다. 상태 계산·권한·미해결 반환 집계와 상세 도식은 유지한다. 1280/1440에서 안내 잘림·가로 넘침 없음.
- **팀원 기능 연계:** 요청 상태와 개별 작업 상태를 서로 다른 출처에서 읽는다. 우리 반 작업 `작업 중`은 `작업 준비`로만 표시하고 요청 전체 `작업 중`은 유지한다. 목록과 상세에서 실제 개별 작업 3단계 안내를 호출하며, 요청 상태만으로 우리 반 상태를 만들어내지 않는다.
- **배정:** [StatusGuide와 기존 상태/상세 모듈](아키텍처설계.md#survey-module-allocation-20261022).

### 요청·첨부 본문 및 메타데이터 키워드 검색 · SR-BE-040

- **근거:** FR-041, UC-017, E-029.
- **입력:** 선택 q(앞뒤 공백 제거 후 최대200자), 기존 검색 조건·페이지·현재 인증 주체.
- **동작:** q는 문자열의 연속 부분 일치다. 요청 본문·기존 분류 정보 또는 현재 연결된 첨부의 추출 본문·허용 메타데이터 중 하나에 일치하고, 나머지 기존 조건을 모두 만족하는 요청만 찾는다. 여러 첨부가 일치해도 한 요청으로 센다. 파일명은 검색하지 않는다.
- **출력:** 같은 권한/조회 기준의 total·목록, 요청 내용 요약·일치 출처·최대160자 문맥, 문서 블록 또는 메타데이터 항목 위치를 제공한다. 문서 결과를 선택하면 현재 권한을 다시 확인하고 해당 원문 위치를 표시한다. 현재 정렬·페이지와 검색/Enter 시점을 유지한다.
- **예외:** q 미입력은 기존 조회다. %·_ 같은 문자는 사용자 와일드카드가 아닌 문자로 찾는다. SQL 매개변수·LIKE escaping을 적용하고 정규식/외부 검색 서비스는 쓰지 않는다.
- **권한:** 기존 요청 가시성과 현재 담당/과거 참여 권한 의미를 유지한다. 다른 사람 요청·비공개 작업 메모는 검색하지 않는다.
- **연계 범위:** q는 권한별 신청 목록에만 적용한다. 팀원 일정·전체 공유 작업 현황 DTO에 요청 문맥을 추가하지 않으며 계획 정비를 요청 검색 결과로 섞지 않는다.
- **분석 상태:** 분석 중·실패·텍스트 없음은 일치 없음으로 확정하지 않는다. 사용자 권한 범위 안에서 분석 미완료 상태를 기존 검색 맥락과 함께 알린다. OCR을 실행하지 않으므로 텍스트 없는 스캔 PDF는 내용 검색에 포함되지 않지만 원본 보기·다운로드는 유지한다.
- **합격:** 요청 본문·분류·추출 가능한 첨부 본문/메타데이터 일치, 기존 조건 AND, 문자 리터럴, 권한 밖 요청·내부 메모 차단, 여러 문서 일치 시 요청 중복 제거.
- **배정:** [QueryService와 검색 화면](아키텍처설계.md#survey-module-allocation-20261022).

### HWP/PDF 보기·본문·메타데이터 추출 · SR-BE-041

- **근거:** FR-042, UC-018, E-037~038 및 2026-10-24 사용자 결정.
- **동작:** HWP/PDF 원본을 보존하고 기존 요청 조회 권한을 확인해 HWP 페이지·PDF 인라인 원본 보기, 다운로드, 디지털 본문·구조 블록·문서 정보 후보의 추출과 저장을 제공한다. HWP 페이지 렌더러는 브라우저에서 원본 바이트로 페이지 SVG를 렌더링한다. 분석은 첨부 연결 저장 후 비동기로 진행한다.
- **추출:** Apache Tika의 HWP/PDF 텍스트 파서를 사용한다. PDF 텍스트 추출은 `pages.text=EXTRACT`, 이미지 인식 엔진은 `text-recognizers=[]`로 설정한다. Tesseract 및 다른 OCR 엔진은 설치·실행하지 않는다. 텍스트가 없는 스캔 PDF는 `no_text`로 기록하고 원본 보기·다운로드를 제공한다.
- **메타데이터:** 문서 제목·회의명·일시·장소 후보와 원문 근거를 저장한다. 문서에 없는 값이나 모호한 날짜를 추측해 확정하지 않고 요청 입력·작업 일정·후보고 시각을 덮어쓰지 않는다.
- **권한:** download·inline·HWP render-source·document 결과는 매 요청마다 첨부 연결과 현재 요청 조회 권한을 검사한다. 화상회의·일반회의 지원 첨부는 원본 다운로드만 허용하고 분석·검색·inline/HWP render-source를 금지한다. 연결되지 않은 임시 파일은 뷰어·분석에 공개하지 않는다.
- **기존 데이터:** OCR 설정 변경으로 분석기 버전을 올려 기존 첨부를 새 no-OCR 파서로 다시 처리한다. 분석/job 행과 첨부 원본 파일 자체는 유지한다. 갱신 전까지 구버전 OCR 결과를 새 분석 결과로 표시하거나 검색하지 않는다.
- **한도·오류:** pending/processing/ready/partial/failed/unreadable/no_text와 회의 첨부 excluded를 구분한다. 파일당 기존10MiB·건당10개/50MiB, 프로세스1개·512MiB·120초·PDF 최대50쪽·출력100만자·ZIP 해제100MiB 한도를 유지한다. 일부 처리 범위를 표시하고, 분석 실패가 요청 저장·원본 다운로드를 막지 않는다.
- **합격:** 디지털 HWP 본문/메타데이터 추출, 검색 가능한 PDF 추출, 이미지 전용 PDF의 `no_text`, OCR 도구 부재 상태에서도 동일한 분석 동작, HWP/PDF 보기·다운로드, 분석 실패 후 요청·원본 보존, 권한·회의 첨부 경로 차단.
- **배정:** [AttachmentService·DocumentAnalysisService·QueryService·HwpPageRenderer·AttachmentDocumentDialog](아키텍처설계.md#survey-module-allocation-20261022).

## 팀원 사용 피드백 기능 명세 · 2026-10-24

근거는 사용자가 전달한 팀원 사용 피드백과 2026-10-24 사용자 결정이다. 기존 로그인·부서 계정·팀원 일정 계약은 유지한다. 개인전화 공개 범위는 답변 전 안전한 최소 공개 기본값으로 정했다. 대리 요청은 BNOC가 기존 활성 요청자 계정을 등록 때 연결한다.

### 회의 지원 첨부·화상회의 방식 · SR-BE-043

- **근거:** FR-045, UC-020, 사용자 전달 피드백·2026-10-24.
- **입력:** 요청 유형, 회의 유형, 화상회의 방식, 첨부 참조 목록.
- **동작:** 요청자의 새 회의 지원 신청에서 화상회의·일반회의는 지원 의뢰서 첨부 1개 이상을 요구하고, 화상회의는 KJCCS·AFCCS·웹미팅 중 하나를 필수 선택한다. 일반회의·기타에 화상회의 방식은 받지 않는다. 회의 유형이 기타이면 필수 양식 첨부 규칙을 적용하지 않는다. 선조치 후보고는 기존 계약을 유지하며 신규 신청용 첨부·화상방식 필수 규칙을 적용하지 않는다.
- **수정 경계:** 기존 회의 요청에 소급 첨부를 강제하지 않는다. 새로 신청하거나 회의 유형을 변경하는 경우만 현재 정책으로 검증한다. 등록된 요청의 첨부를 수정할 때 마지막 필수 첨부를 제거할 수 없다.
- **실패·금지:** 신규 회의 신청이 화상회의/일반회의인데 첨부가 없거나 화상회의 방식이 없으면 서버가 거절한다. 선조치 후보고에 신규 신청 필수값을 강제하지 않는다. 보안 양식의 본문을 수집·재현하거나 첨부 내용이 올바른 양식인지 자동 판독하지 않는다.
- **배정:** RequestRegistrationForm, AttachmentPicker, requestPayload, WorkflowService, AttachmentService.

### 선택 개인전화 · SR-BE-044

- **근거:** FR-046, UC-021, 사용자 전달 피드백·2026-10-24.
- **입력:** 선택 개인전화번호. 7~15자리 숫자를 허용하며 `+`, 공백, 괄호, 하이픈만 서식 문자로 허용한다. 전체 길이는 50자 이하다.
- **동작:** 요청·수정에서 선택 입력으로 저장·표시한다. 요청자 본인·BNOC·해당 요청의 현재 유효 배정 작업반만 요청 상세에서 본다. 반납되거나 재배정/해제된 과거 작업반에는 제공하지 않는다.
- **실패·금지:** 숫자가 7~15자리가 아니거나 서식 문자 이외 문자가 있으면 입력을 거절한다. 개인전화는 `GET /api/work-overview`, 일정 응답·카드, 알림, 다른 작업반 DTO, 변경 이력에 포함하지 않는다. 요청자 군내전화번호의 기존 공유 범위는 유지한다. 로그·검색 결과에 전화번호를 남기지 않는다.
- **배정:** RequestRegistrationForm, RequestDetailWorkspace, RequestRecord/Database migration, QueryService, API DTO.

### BNOC 대리 등록 요청자의 수정 · SR-BE-045

- **근거:** FR-047, UC-022, 사용자 전달 팀원 피드백·2026-10-24.
- **입력:** BNOC 대리 등록 시 활성 `requester` 계정의 공개 참조값.
- **동작:** BNOC 전용 요청자 선택 조회는 최소 표시값(이름·소속·공개 참조값)만 반환한다. 생성 시 서버가 활성 계정을 확인하고 `requesterSubject`에 연결하며 `registeredBy`는 BNOC로 유지한다. 실제 요청자는 기존 canEdit 상태 규칙과 허용 필드만 수정한다.
- **실패·금지:** client가 보낸 이름·역할·소속으로 계정을 추정하거나 직접 연결하지 않는다. 비활성·비요청자·없는 참조, BNOC 아닌 계정 조회, 요청자 신원/등록자 수정은 거절한다. 기존 소유 계정 없는 대리 요청은 자동 연결하지 않는다.
- **배정:** RequestRegistrationForm, ApiClient, ApiController, WorkflowService, Actor/Request DTO, QueryService, Database.

### 요청 단위 기각 · SR-BE-046

- **근거:** FR-048, UC-023, 사용자 전달 팀원 피드백·2026-10-24.
- **입력:** BNOC, 요청 번호·현재 요청 버전, 필수 기각 사유.
- **동작:** 작업이 아직 하나도 배정되지 않은 `대기` 또는 `문서 대기` 요청만 기각한다. 상태·사유·행위자·시각·변경 이력을 한 트랜잭션으로 저장하고 연결 요청자에게 내부 알림을 보낸다. 요청자는 상세에서 사유를 본다.
- **실패·금지:** 기각 사유가 없거나 요청에 작업이 있거나 요청 상태가 허용되지 않으면 거절한다. 완료·취소·기각은 다시 기각하지 않는다. 기각 뒤 편집·취소·배정·작업 생성·재개는 거절한다. 기각은 작업반 반환과 별도 상태다.
- **배정:** RequestDetailWorkspace, WorkflowService, RequestStatusCalculator, Database migration, QueryService, History/NotificationQueryService.

### 선조치 후보고의 24시간 입력 · SR-BE-047

- **근거:** FR-049, UC-024, 사용자 전달 팀원 피드백·2026-10-24.
- **입력:** 시작 날짜·HH:mm, 완료 날짜·HH:mm.
- **동작:** 입력 UI는 각 시각을 `00:00`~`23:59`의 24시간 표기로 받는다. 프런트는 기존 Asia/Seoul 해석 후 UTC ISO 8601로 전송하고 서버는 기존 instant와 완료≥시작 검증을 유지한다.
- **실패·금지:** 12시간 AM/PM 표시를 사용하지 않는다. 다른 시간 필드·희망 일정의 오전/오후 선택·기존 UTC 저장/기록은 변경하지 않는다. 잘못된 날짜·시각·역순 제출은 거절한다.
- **배정:** WorkExecutionPanel/RequestRegistrationForm의 후보고 입력, afterActionReportCommand, dateTime parser/formatter, WorkflowService.

### SSO 로그인과 서버 세션 · SR-BE-001

- **근거:** [FR-001·NFR-002, SSO 사용자 결정·대회 모의 연동 사용자 결정](요구사항.md#current-requirements) · [로그인과 역할 §1](유스케이스.md#current-usecases).
- **동작:** 서비스 진입 시 선택된 인증 제공자의 결과를 BNOC 서버에서 검증하고 서비스 권한을 결합한다. 대회 모드에서는 모의 인증 서버를 사용하며 같은 서버 세션·권한 검사를 거친다. 자체 회원가입과 운영 화면의 자유 역할 전환은 제공하지 않는다. 공개 시연에서는 브라우저 로그인 위치를 BNOC 공개 Origin의 /identity로 안내하고, 서버의 확인표 검증은 loopback 모의 제공자 주소를 사용한다. 각 부서 지정 담당자는 소속이 연결된 개인 신원으로 인증하며 현황 관리 권한 departmentManager는 BNOC/작업 수행 역할과 독립해 서버에서 결합한다.
- **입력:** 서버 실행 설정으로 고정된 제공자, 시작 브라우저의 서버 사전 인증 상태·로그인 요청과 연결된 인증 결과 또는 모의 단회 확인표, 서버에 등록된 시험 식별자·서비스 권한, 공개 HTTPS Origin·loopback 제공자 주소
- **출력:** 현재 사용자에게 허용된 화면·행동과 서버 세션, 로그인 상태, 같은 Origin의 /identity 로그인 위치; 개인의 소속·독립 현황 관리 범위
- **실패·금지:** 미인증·위조·만료·재사용·요청 불일치·시작 브라우저 불일치는 거절한다. 로그인 요청은 시작 브라우저의 서버 사전 인증 상태에 묶고 인증 완료 시 함께 소비한다. 운영 모드에서는 모의 인증을 거절하며 실제 연동 실패 시 모의 인증으로 자동 전환하지 않는다. 브라우저의 역할 값으로 권한을 만들지 않는다. 공개 프록시는 정확한 GET/POST /identity만 허용하며 /identity/verify·/identity/issue·/control·/feeds/*를 외부에 노출하지 않는다.
- **설계값·후속 조건:** 기술 설계값: 세션 유휴 30분·절대 8시간, 로그인 요청 5분·단회 확인표 60초. 서버 시험 식별자에 역할·부서·작업반 권한을 매핑한다. 실제 공군 SSO 프로토콜·로그아웃·검증은 후속 실연동 조건. 공개 시연의 HTTPS Origin은 서버 시작 설정으로 고정하며 공개 쿠키의 Secure·HttpOnly·SameSite=Lax와 기존 CSRF·Origin 검사를 유지한다. 초기 department-manager의 BNOC 배치나 작업반 전원 관리 권한을 정상 조직으로 승계하지 않는다. 각 부서의 지정 담당 신원과 비담당 신원을 구분하며 실제 SSO의 부서 제공 규격은 후속 조건이다.
- **확인 방법:** 설계 검토: 근거·주체·입력·결과·금지 사례와 담당 모듈을 대조. 해당 API 정상/거절·저장 결과는 제품 검증 기록으로 확인. [담당 모듈 보기](아키텍처설계.md#allocation).
- **과거 데모 연결:** SR-DEMO 001·003·004. 업무 의미만 대조하며 합성 인물·역할 전환·메모리 초기화·모사 첨부를 서버 요구로 승계하지 않는다.

### 역할·작업반 권한 관리 · SR-BE-002

- **근거:** [ACT-04·NFR-003](요구사항.md#current-requirements) · [UC-012 역할·작업반 권한 관리](유스케이스.md#current-usecases).
- **동작:** 권한 관리자가 개인 계정의 역할·작업반·소속 부서와 연결된 독립 departmentManager 권한을 부여·회수하고 이력을 남긴다. 각 부서 지정 담당자만 자기 명부·병력·야간 현황을 관리한다. 같은 부서 구성원에게 자동 관리 권한을 주지 않고 현황 관리만으로 BNOC 배정/작업 수행 권한을 부여하지 않는다. 권한은 다음 요청부터 적용한다.
- **입력:** 관리 대상 개인 계정 참조·서버에 확인된 소속 부서·부여/회수할 역할/작업반/departmentManager 권한·현재 버전
- **출력:** 변경된 권한·감사 이력. 후속 요청과 재시도에도 새 권한 적용
- **실패·금지:** 관리 권한 없음·자기 권한 상승·타 부서 관리 범위 부여·오래된 버전은 거절한다. 회원가입·범용 부서 담당 계정·행정병만의 자격 제한으로 확대하지 않는다.
- **설계값·후속 조건:** 기술안: 최초 관리자는 서버 시작 설정의 외부 식별자로 지정하고 서버에서 서비스 권한에 연결한다. 브라우저 가입·첫 로그인 자동 관리자는 없다. 실운영 관리자 복구·인수는 후속 고도화 조건.
- **확인 방법:** 설계 검토: 근거·주체·입력·결과·금지 사례와 담당 모듈을 대조. 해당 API 정상/거절·저장 결과는 제품 검증 기록으로 확인. [담당 모듈 보기](아키텍처설계.md#allocation).

### 지원 유형과 선택 입력 보존 · SR-BE-005

- **근거:** [FR-005·006, 사용자 지원 대상 설명](요구사항.md#current-requirements) · [UC-001·요청 등록 §2](유스케이스.md#current-usecases).
- **동작:** 장비/체계와 회의 지원의 기존 조건부 입력을 유지한다. 회의 지원은 화상회의 방식(KJCCS·AFCCS·웹미팅)을 조건부로 받으며 화상회의·일반회의 신규 신청은 해당 지원 의뢰서를 첨부한다. 개인전화번호는 선택 입력이며 개인전화 노출은 별도 권한 조건을 따른다. 희망 일정은 선택 입력인 1·2지망이며 각각 날짜와 오전/오후만 선택하고 실제 작업 일정과 구분한다. 2지망을 쓰면 1지망도 필요하다. 정비대상자 정보를 사용하면 기존 네 항목을 함께 받는다. 필수/선택 정보를 표시하고 선택 영역을 접어도 값을 보존한다. 그룹 유형 오류는 해당 선택칸의 오류·첫 초점에 연결한다. 요청 내용·증상 placeholder 예문은 선택한 체계 종류·자원 유형·작업 유형 조합별로 다르게 제공하고 실제 통계상 빈도·실제 운영자료를 암시하지 않는다. 작업 위치 placeholder는 `예: 건물 층 부서명 등 작업 위치를 적어주세요.`다. 사용자가 입력하면 placeholder는 가려지고 기존 값·분류 변경으로 작성값을 덮어쓰지 않는다. 신규·수정·후보고 화면에 같은 규칙을 적용한다. 장비·체계 식별정보와 문서 참조정보에는 입력 후에도 남는 의미·기입 예·생략 가능 안내를 제공한다. 실제 번호·문서명을 예시로 만들지 않는다.
- **입력:** 체계·자원·작업 유형 또는 회의 유형, 필요 시 화상회의 방식·필수 회의 의뢰서, 내용·위치·군내전화·선택 개인전화, 선택 희망 일정 1·2지망(날짜·오전/오후)·문서·장비 정보
- **출력:** 정규화한 요청 입력과 해당 항목의 오류; 내용·위치 입력의 비저장 예문 안내; 식별정보·문서 참조의 지속 안내
- **실패·금지:** 희망 일정 필수화·새 자원 분류의 임의 필수화 금지. 컴퓨터·프린터·회선·전화·회의 범위를 누락하지 않음.

### BNOC의 최초 배정·부서 추가·배정 시각 기록 · SR-BE-010

- **근거:** [FR-012~014, 최신 답변: 접수 시간=배정 시각·반장 지정 제거](요구사항.md#current-requirements) · [UC-002·004·BNOC 접수 배정 §3](유스케이스.md#current-usecases).
- **동작:** BNOC는 일반·긴급을 정하고 주·부 구분 없이 하나 이상의 작업 부서를 최초 배정한다. 요청 내용 자체가 작업지시이며 반장 지정·별도 지시문은 없다. 미완료·비취소·완료 후보고가 아닌 요청에는 현재 미담당 부서를 추가할 수 있다. 모든 배정 해제 뒤 유효 작업0개여도 배정 이력이 있으면 추가 경로를 쓴다. 접수 시간은 배정 성공 시 서버가 기록하는 배정 시각이다. 새 작업 일정은 미정이다. 작업 일정은 작업반이 정하며 희망 일정을 복사하지 않는다. 부서 추가는 과거 BNOC 배정 이력과 저장된 general/urgent가 있는 요청에만 허용한다. 최초 배정이 성공적으로 저장되면 화면은 BNOC 요청 현황을 최신 조건으로 다시 조회해 보여주고, 저장 실패·불명확 응답이면 성공으로 간주해 목록으로 이동하지 않는다. 부서 추가·재배정·배정 해제 조작은 각각 별도 카드로 표시하며 기존 명령별 조건과 효과는 분리해 유지한다.
- **입력:** 최초 assignTeams는 요청 번호·요청 버전·중복 없는 부서·general/urgent. addTeams는 요청 번호·요청 버전·현재 미담당 부서 목록이며 분류/작업 일정/반장은 받지 않는다.
- **출력:** 기존 작업·분류·일정을 유지한 신규 부서별 작업·과거 최대 순번 다음 작업 번호·서버 배정 시각·전체 상태·이력·해당 반 알림을 원자적으로 저장. 최초 배정 성공 시 갱신된 BNOC 요청 현황으로 돌아가 남은 미배정 요청을 확인
- **실패·금지:** 미분류·유효하지 않은 부서·기존 작업 존재 시 최초 배정 거절. 일부 부서만 저장 금지. 현재 유효 담당 반 중복·취소/완료 요청/후보고에 부서 추가 거절. 최초 배정은 과거 작업이 있으면 거절하되 추가는 과거 참여 이력만으로 막지 않는다. BNOC 일정 지정·희망 일정 자동 복사 금지. 과거 BNOC 배정 이력이 없는 신규 미배정 요청 또는 분류null의 addTeams는 거절한다.
- **설계값·후속 조건:** 0.8 승인 부서 추가 계약. addTeams는 기존 분류를 유지하고 요청 잠금 후 최신 미완료 상태·유효 부서·요청 버전을 재검사한다. 새 번호는 해당 요청의 과거 최대 작업 순번+1을 같은 잠금 안에서 발급한다. 완료가 먼저면 추가 거절, 추가가 먼저면 새 작업까지 끝나야 전체 완료다. 과거 BNOC 배정 이력과 저장된 general/urgent가 있어야 addTeams를 허용한다. 신규 미배정/분류null은 거절하고 과거 배정 이력·저장 분류가 있으며 현재 유효0개인 요청은 허용한다.
- **확인 방법:** 설계 검토: 근거·주체·입력·결과·금지 사례와 담당 모듈을 대조. 해당 API 정상/거절·저장 결과는 제품 검증 기록으로 확인. [담당 모듈 보기](아키텍처설계.md#allocation).
- **과거 데모 연결:** SR-DEMO 016·040·041. 업무 의미만 대조하며 합성 인물·역할 전환·메모리 초기화·모사 첨부를 서버 요구로 승계하지 않는다.

### BNOC의 일반·긴급 결정과 사후 정정 · SR-BE-011

- **설계값·후속 조건:** 0.8 화면 기본 선택 제안은 기존 일반 자동 기본값 금지와 구분한다. 서버는 BNOC·명시값 검사 유지. 저장값과 편집 초안을 비교해 미저장 여부를 판단하고 저장 결과에 분류·부서를 명시한다.
- **확인 방법:** 설계 검토: 근거·주체·입력·결과·금지 사례와 담당 모듈을 대조. 해당 API 정상/거절·저장 결과는 제품 검증 기록으로 확인. [담당 모듈 보기](아키텍처설계.md#allocation).

### 작업반의 담당 인원·상태·일정·메모 저장 · SR-BE-012

- **근거:** [FR-016~019, 일정 결정 사용자 답변](요구사항.md#current-requirements) · [UC-003·004·작업반 처리 §4](유스케이스.md#current-usecases).
- **동작:** 작업반은 자기 작업의 담당 인원을 자기 반 명부에서 선택하고 네 상태·선택 일정의 여러 시간 구간·메모를 명시적으로 저장한다. 새 구간은 하루 24시간 중 정시 시작의 1시간 단위로 선택하며 연속 슬롯은 한 구간으로 저장할 수 있다. 기존 정확한 일정 시각은 반올림하지 않고 원래 시작값으로 보존해 1시간 구간으로 해석한다. 여러 인원을 선택할 수 있으나 선택은 새 필수 시작/완료 조건이 아니다. 선택 담당 인원과 SSO 저장 행동자·완료 처리자는 별개다. 반환 시 현재 일정 구간 전부를 previousSchedule에 보존하고 현재 구간을 비운다. 반환 정정 시 이전 구간 전체 재사용 또는 미정을 선택한다.
- **입력:** 요청/작업 번호·작업 버전, 선택 상태·여러 일정 구간·메모·상태별 정보, 선택 담당 인원 참조 목록
- **출력:** 자기 작업의 담당 인원·내부 상태·여러 일정 구간 변경과 이력, 재계산된 요청 상태. 화면은 내부 상태 `작업 중`을 `작업 준비`로 표시하지만 같은 상태값으로 갱신한다.
- **실패·금지:** 다른 반·취소 요청·재배정/해제로 해결된 반환·후보고 완료 작업 수정 거절. 다른 부서/반 인원 참조·중복 참조 거절. 담당 인원 미선택을 이유로 완료 금지하지 않으며 상태 선택만으로 저장하지 않는다. 반환 전 구간을 현재 예정 일정으로 사용하거나 새 재배정 작업에 복사하지 않는다.
- **확인 방법:** 설계 검토: 근거·주체·입력·결과·금지 사례와 담당 모듈을 대조. 해당 API 정상/거절·저장 결과는 제품 검증 기록으로 확인. [담당 모듈 보기](아키텍처설계.html#sr=SR-BE-012).
- **과거 데모 연결:** SR-DEMO 018·020·033·034·042. 업무 의미만 대조하며 합성 인물·역할 전환·메모리 초기화·모사 첨부를 서버 요구로 승계하지 않는다.

### 완료된 선조치 후보고 · SR-BE-016

- **근거:** [FR-022·023](요구사항.md#current-requirements) · [UC-011·선조치 후보고 §5](유스케이스.md#current-usecases).
- **동작:** 작업반이 직접 받은 일을 끝낸 후 요청·자기 반 완료 작업·이력·BNOC 알림을 함께 생성한다. 미분류로 저장하고 BNOC가 나중에 분류한다. 새 완료 작업은 전체 공유 현황의 할당·완료 및 부서별 작업 수에 한 번씩 포함하고 실제 배정 출처와 구분한다. 우리 반 일정에는 실제 시작 시각이 속한 정시 1시간 칸의 완료 기록으로 포함하며, 정확한 실제 시작 시각을 보존한다. 승인·미완료 별도 등록·BNOC 전달·자동 역할 전환은 없다.

### 일·주·월 정비 일정 · SR-BE-021

- **근거:** [FR-028·공고 R07](요구사항.md#current-requirements) · [UC-010·일 주 월 일정 §7](유스케이스.md#current-usecases).
- **동작:** 일·주·월로 현재 예정·완료 처리 기록·반환 전 계획·미정 목록을 구분해 조회한다. 현재 예정은 유효 일반 작업 중 배정/내부 `작업 중`이며 여러 일정 구간이 있는 작업만 센다. 새 구간은 24시간의 정시 시작 1시간 단위고 연속 시간은 연결한다. 선택 기간 안에서 같은 작업은 카드 하나로만 배치하고, 조회 기간과 겹치는 가장 이른 일정 구간의 시작 시각 순으로 정렬한다. 카드 하나에 기간과 겹치는 모든 해당 작업 구간을 함께 표시한다. 조회 범위 전에 시작해 이어지는 구간은 기간 내 처음 보이는 겹침 시각에 배치하면서 원래 시작 시각을 보존한다. 완료 후보고는 현재 예정과 분리한 완료 기록으로 실제 시작 시각에 한 번 표시한다. 완료 일반 작업은 계획 구간이 기간과 겹치면 계획 시간만 표시하고 완료 날짜·시각을 카드에 덧붙이지 않는다. 계획 구간 없이 완료 시각으로 배치되는 카드는 해당 시간 칸에 두되 카드 시간 문자열은 생략한다. 예정·완료 카드는 파랑·초록 계열 색으로 구분하고 작업 상태 텍스트를 유지한다. 카드에는 시간, 같은 줄의 `작업번호: 102-1`과 상태, 위치·작업 메모를 표시하고 전체 카드를 상세 링크로 만든다. 키보드 활성화와 상세 권한 재검사를 지원한다. 카드·응답에는 전화번호·요청 상세 내용을 넣지 않는다. 시간 외 글자는 같은 크기·두께이며 시간만 색·굵기로 강조한다. 내부 `작업 중`은 `작업 준비`로 표시한다.
- **입력:** 일/주/월·조회 기간·허용 작업반 범위
- **출력:** 작업 번호·반·표시 상태·작업당 카드 1개와 기간 안의 여러 현재 일정 구간/반환 전 구간/후보고 실제 시작 기록·분리된 건수·위치·작업 메모. 일정 항목은 상세 화면 이동용 요청 번호만 연결하며 요청 상세 내용·전화번호·그 외 요청 요약 필드는 제외한다.
- **실패·금지:** 희망일을 작업일로 대체하거나 BNOC 달력 조작으로 작업 일정을 정하지 않음. 일반 요청자 전체 달력 권한 추가 없음. 취소·해결된 반환·미해결 반환을 현재 예정 건수에 포함하지 않는다. 후보고 완료는 완료 기록에만 두고 현재 예정에 포함하지 않는다. 반환 전 구간을 지우거나 현재 일정으로 자동 복귀하지 않는다.

- **실패·금지:** 요청자 군내전화번호만 허용된 연락처 예외다. 요청 본문·위치·정비대상자 연락처·첨부·인원·내부 메모·이력 원문 등 나머지 상세는 제외하고 상세 권한은 기존대로 검사한다. 재고·장비 가용 추론 없음. 취소·재배정/해제로 해결된 반환을 주 집계에서 제외한다. 후보고 완료는 할당·완료 수에 한 번 포함하고 출처별 하위 수는 다시 더하지 않는다.

RequestStatusCalculator 공통 요약을 호출한다.

### BNOC 공지게시판과 첨부문서 · SR-BE-027

- **근거:** [공고 R03, 최신 답변: 공지게시판·BNOC 게시·첨부문서](요구사항.md#current-requirements) · [지시사항 §9.4](유스케이스.md#current-usecases).
- **동작:** 공지게시판은 모든 로그인 사용자가 조회한다. BNOC가 제목·본문·첨부를 게시하며 BNOC 계정이면 작성자와 무관하게 수정할 수 있다. 게시 종료·숨김·읽음 확인·미확인자 집계는 없다. 공지 편집은 글자 크기·제한된 색상·굵게·밑줄·목록을 제공하며 저장/재조회 후 보존한다. 서식 없는 기존 공지도 읽고 수정한다.
- **입력:** BNOC의 제목·본문 payload(body plain 문자열, 선택 bodyDocument 허용 문서 JSON)·첨부 참조·제출 키; 수정은 공지 참조·버전. 조회는 로그인 세션.
- **출력:** 공지 목록·본문·첨부 표시정보·권한 검사 후 문서 다운로드, 게시/수정 전후 이력. 기존 공지에 연결된 타 BNOC 업로드 첨부도 유지 가능. 신규 임시 첨부만 현재 업로더 소유 검사. 첨부 제거는 현재 연결 해제 후 이전 자료 보존 rich 문서는 서버가 bodyDocument에서 body를 계산해 검색/목록의 평문과 일치시킨다.
- **실패·금지:** BNOC 외 게시·임시 첨부 가로채기·권한 없는 글/첨부 조회 거절. 첨부 연결 실패를 게시 성공으로 표시하지 않음. 임의 HTML·스크립트·원격 자원·허용 밖 구조/스타일·본문 없는 빈 서식 거절. 클라이언트 body와 rich 본문 이중 원본을 허용하지 않는다.
- **설계값·후속 조건:** 0.8 승인 서식 계약. bodyDocument는 허용 노드/속성만, 글자 크기16/20/24px·색 기본/#1d4ed8/#b91c1c/#166534·bold/underline/list. plain body 1만자와 bodyDocument 직렬화 UTF-8 64KiB 제한을 각각 검사한다. 기존 plain/첨부/공동 수정/전후 이력/충돌 정책 유지. bodyDocument={version:1,blocks:[...]}에서 paragraph/listItem·bullet/ordered 목록·text runs의 bold/underline/size/color만 허용하고 blocks/runs 각각1000개 이하·고정 깊이를 검사한다. rich 수정에서 문서 누락은 거절하고 plain 전환은 명시적 bodyDocument=null과 body가 있어야 한다. rich payload의 body를 함께 보내면 서버 계산값과 같아야 한다.
- **확인 방법:** 설계 검토: 근거·주체·입력·결과·금지 사례와 담당 모듈을 대조. 해당 API 정상/거절·저장 결과는 제품 검증 기록으로 확인. [담당 모듈 보기](아키텍처설계.md#allocation).

### 업무·이력·알림의 함께 저장 · SR-BE-028

### 동시 수정과 오래된 화면 거절 · SR-BE-030

- **근거:** [NFR-008·009](요구사항.md#current-requirements) · [공통 화면 동작·UC-003~007](유스케이스.md#current-usecases).
- **동작:** 요청 변경은 요청 버전, 작업 변경·재배정은 해당 작업 버전을 비교한다. 같은 요청의 저장을 짧게 직렬화하고 최신 작업들로 전체 상태를 계산한다. 반환 정정/재배정/해제는 원 작업 버전으로 경합하고 부서 추가는 요청 버전과 최신 유효 부서 집합을 재검사한다. 추가와 마지막 완료도 같은 요청 잠금으로 순서를 결정한다.
- **입력:** 주 대상 expectedRevision·현재 버전·같은 요청의 최신 작업
- **출력:** 유효한 독립 작업은 모두 저장. 같은 대상 충돌은 최신 재조회 안내
- **실패·금지:** 조용한 덮어쓰기·취소 되살림·반환 정정과 재배정 이중 성공 금지. 다른 반 버전을 화면에 추가 요구하지 않음. 반환의 이중 해결·현재 담당 반 중복 추가·이미 완료된 요청의 추가 재개 금지.
- **설계값·후속 조건:** 기술안: MySQL InnoDB 트랜잭션에서 요청→주 대상 작업 순으로 행 잠금, 잠금 후 버전/현재 권한 재검사. 잠금 대기 5초, 교착 상태는 내부 최대 2회 재시도 후 결과 불명/일시 실패를 구별한다. 요청→작업 잠금 순서는 신규 addTeams/withdrawReturnedWork에도 동일 적용한다. 양쪽 실행 순서에서 최신 상태를 재검사한다. assignTeams/addTeams/reassignAssignedWork/reassignReturnedWork/withdrawReturnedWork의 배정 구조 변경 성공은 전체 상태가 같아도 요청 버전을 증가시킨다. 다른 반의 독립 작업 저장은 유효한 주 대상 작업 버전으로 검사하고 화면에 별도 요청 버전을 추가 요구하지 않는다.
- **확인 방법:** 설계 검토: 근거·주체·입력·결과·금지 사례와 담당 모듈을 대조. 해당 API 정상/거절·저장 결과는 제품 검증 기록으로 확인. [담당 모듈 보기](아키텍처설계.md#allocation).

### 조회·저장·충돌·만료 화면 상태 · SR-BE-032

- **근거:** [FR-008·NFR-005·006](요구사항.md#current-requirements) · [공통 화면 동작](유스케이스.md#current-usecases).
- **동작:** 조회 중·빈 결과·실패를 구분하고 명시적 저장 성공 뒤 목록을 갱신한다. 오류 시 입력을 유지하며 충돌은 최신 값을 보고 다시 선택하게 한다. PC에서 그룹/개별 오류를 해당 항목과 첫 초점에 연결한다. 성공은 대상·처리를 명시하고 재편집을 미저장으로 구별한다. 지난 조회 결과의 실제 조건을 새 실패와 구별하되 조회시각은 화면에 표시하지 않는다. 저장 분류·배정 부서와 편집 초안을 구분하고 같은 저장값을 변경으로 오판하지 않는다. 부서/날짜 요약은 저장값과 편집 중 값을 분리한다. 전역 상황/새 알림은 계정 전환·로그아웃 때 캐시를 지우고 권한 변화 뒤 최신 세션 표시를 확인한다.
- **입력:** 조회/저장 응답·필드 오류·인증 만료·충돌·결과 불명
- **출력:** 입력 오류 위치·첫 오류 초점·재확인·재인증·재조회 안내·대상/처리별 성공·미저장 상태·성공 조회 조건. API 시각은 유지하되 화면에 표시하지 않음
- **실패·금지:** 성공 전 완료 표시·조회 실패의 0건 표시·자동 입력 덮어쓰기 금지. 과거 서버 요약을 현재 초안의 요약처럼 보이거나 반환 미해결 수를 알림 확인으로 지우지 않는다.
- **설계값·후속 조건:** 화면안: 미저장 이동 안내. 만료 시 현재 화면 메모리 입력만 유지하고 저장하지 않음. 같은 브라우저 재인증 후 제출 결과·권한 확인, 명시적 재제출. 파일은 유효 임시 참조만 복원, 브라우저 영구 저장 없음.
- **확인 방법:** 설계 검토: 근거·주체·입력·결과·금지 사례와 담당 모듈을 대조. 해당 API 정상/거절·저장 결과는 제품 검증 기록으로 확인. [담당 모듈 보기](아키텍처설계.md#allocation).
- **과거 데모 연결:** SR-DEMO 012·033·034·039. 업무 의미만 대조하며 합성 인물·역할 전환·메모리 초기화·모사 첨부를 서버 요구로 승계하지 않는다.

<a id="sr-be-033"></a>
### 검토·시연의 인물 표시 원칙 · SR-BE-033

- **근거:** [사용자 표시 원칙·NFR-004·공고 자료 조건·대회 모의 연동 사용자 결정](요구사항.md#current-requirements) · [로그인 §1·병력 §9.2](유스케이스.md#current-usecases).
- **동작:** 설계와 시연에 가짜 이름·합성 계급·실제 개인정보·실제 부대 운영 수치를 채우지 않는다. 역할명과 빈 입력/등록 없음으로 구조를 검토한다. 외부 연동 시험용 상황 값은 문서·서버 설정·검증 기록에 모의 출처를 명시해 수집 시연에 사용한다. 실제 부대 상황이나 실제 SSO 연동으로 주장하지 않는다. 사용자 화면에 모의/대회용 표시·실제 연동 여부 설명을 넣지 않는다.
- **입력:** 역할명·빈 상태·사전 정의한 모의 상황 응답, 운영 시 승인된 표시 속성
- **출력:** 역할명으로 표시한 화면, GPS 정보원·CPCON 정보원 표시와 수집 상태. API 원본 시각·내부 sourceMode·문서·설정·검증 기록에 실제 구현 구분 보존; 시각은 화면에 표시하지 않음
- **실패·금지:** 옛 합성 계정·자료를 새 기본값으로 복사하지 않음. 가짜 이름·합성 계급·시험 단계 A/B 같은 임시 용어 금지. 인물처럼 꾸민 기술 시험 식별자·실무 자료를 코드·로그·증거로 복제하지 않음.

### CPCON 상황 수집·저장·조회 · SR-BE-035

- **근거:** [공고 R02·CPCON 누락 정정·전체 로그인 조회 결정](요구사항.md#current-requirements) · [상황 §9.4](유스케이스.md#current-usecases).
- **동작:** CPCON은 GPS와 별도 수집·저장하며 모든 로그인 사용자가 조회한다. 공개 근거 기반 1~5 코드와 CPCONⅠ급~CPCONⅤ급 정보원 표시명은 별도 사전에서 검증해 저장·API에 유지한다. 공통 상단·CPCON 전용 팝업의 단계 결과는 코드에 대응하는 영문 대문자 I~V만 표시하고 CPCON 항목명과 분리한다. 팝업은 BNOC SPA와 분리된 정적 시연 사이트 `/external-systems/cpcon/index.html`이며 같은 로그인 세션으로 `GET /api/situation/cpcon`만 조회한다. 한국 공군의 전체 태세명·의미를 확인한 것으로 주장하지 않는다. 모든 로그인 업무 화면 공통 상단의 문자·그래픽·수집 이상은 종류별 응답을 사용하며 시각은 화면에 표시하지 않는다.
- **입력:** 종류 cpcon, 정보원의 scopeKey, 별도 1~5 단계 코드·원본 기준시각·모의 출처. 실제 부대명·시험 단계 A/B를 만들지 않는다.
- **출력:** API의 CPCONⅠ급~CPCONⅤ급 표시명과 원본/성공/시도 시각은 유지한다. 화면은 I~V 단계 결과·정보원 적용 범위·CPCON 정보원·미수집/성공/실패/오래됨 상태를 표시하고 시각은 숨긴다. 단계 사전 미설정은 명시적 미설정 상태; expiresAt·serverNow로 실패/시간 경과에도 유효성을 판단한다.
- **실패·금지:** GPS 5=양호·부대 공통 범위를 CPCON에 복사하지 않는다. 별도 사전 밖 코드·오류를 정상화하지 않고 GPS 성공으로 CPCON 실패를 덮지 않는다. 임시 단계명·임의 한국어 태세명·실제 부대 범위 추정 금지. 그래픽 색/방향만으로 의미를 만들거나 GPS 양호 판단을 차용하지 않는다. 헤더/상세 불일치·실패 후 오래된 정상 고정 금지.
- **설계값·후속 조건:** 공개 근거 기반 기술안과 사용자 조회 권한 확정. 범위는 정보원 scopeKey별 독립 저장·조회. 수집 30초/시간 초과 5초/유효 120초는 GPS와 별도 설정. 국내 실제 단계 의미·연동 규격·인증은 후속 실연동 조건. 공통 상단/상세는 같은 종류별 응답과 캐시를 사용하며 진입·30초·복귀 조회 실패 중에도 응답 기준 만료를 연장하지 않는다.
- **확인 방법:** 설계 검토에서 GPS와 별도 기능·모듈·입출력을 확인한다. 독립 성공/실패·미설정·잘못된 코드·저장값 조회는 제품 검증 기록으로 확인한다. 실제 연동 성공 증거로 사용하지 않는다. [담당 모듈 보기](아키텍처설계.md#allocation).

### 계획 정비 작업 등록·관리·집계 · SR-BE-036

- **상태:** 구현·독립 검증 완료 · 2026-10-21. 디자인 기반과 승인 시안은 `d1f32a7`에 먼저 커밋했다.
- **근거:** [FR-037 계획 정비 작업](요구사항.md#current-requirements) · [UC-013 계획 정비 작업](유스케이스.md#uc-013-계획-정비-작업) · 2026-10-21 사용자 결정.
- **동작:** 현재 세션의 작업반이 외부 계획 체계를 참고해 제목과 날짜로 작업을 등록한다. 외부 체계의 작업 정보를 자동 조회하지 않고 비계획 정비 요청 데이터도 재사용하지 않는다. 신규 항목은 `진행 중`으로 시작한다. 입력 날짜는 일일 업무 목록에 처음 나타나는 기준일이다. 진행 중 항목은 기준일부터 선택한 날짜까지 업무 목록에 자동 표시되며 다음 날 반복 등록하지 않는다. 과거 날짜를 선택해도 과거 상태는 복원하지 않고 현재 완료된 항목은 진행 목록에서 제외해 완료 목록에 표시한다. 기준일은 과거·오늘·미래를 허용한다. 상태는 `진행 중`과 `완료`만 둔다. 수정·완료·삭제는 서로 별도 동작이다.
- **입력:** 현재 세션의 작업반, 제목, 최초 업무 기준일(date-only), 완료 시 오늘 이하의 완료일, 대상 항목 버전과 명시적 명령. 기준일은 오늘이 기본이며 달력과 이전 날짜·오늘·다음 날짜 조작으로 과거·미래를 선택한다. 시각·별도 위치·일일/주간/월간 유형·부서 입력은 받지 않는다. 날짜·제목 오류는 해당 필드에 연결한다.
- **출력:** 해당 작업반의 선택 날짜 기준 진행 중 목록과 완료 작업을 반환한다. 같은 진행 중 작업은 여러 날짜 목록에 나타나도 하나의 식별자·상태를 유지한다. 공유 현황의 할당·완료에는 완료 선조치 후보고를 한 번 포함하고, 출처별 후보고 수는 부분집합으로 표시한다. 전체 작업은 할당 작업과 별도 계획 정비의 합계다. 계획 작업을 BNOC가 배정한 `할당 작업`으로 부르지 않는다.
- **실패·금지:** 화면에서 받은 부서/역할 값으로 소유권을 정하지 않는다. 계획 항목을 요청 연결 작업 테이블에 `request_number IS NULL`로 저장하지 않는다. 기존 비계획 정비 명령·요청 상태·`RequestStatusCalculator` 산식을 바꾸지 않는다. 같은 진행 중 작업을 다음 날 다시 등록하게 하거나 일일 목록에 매일 수동 추가하게 만들지 않는다.
- **저장·집계 설계:** 계획 작업은 비계획 요청/작업과 분리해 저장하며 날짜별 복제 행이나 날짜 기록 배열은 만들지 않는다. 작업은 최초 업무 기준일과 선택적인 완료일을 가진다. 기준일부터 선택 날짜까지 진행 중 작업을 일일 목록에 자동 노출하며, 여러 날짜에 노출돼도 작업 하나당 진행 중 한 건 또는 완료 한 건만 집계한다. 완료 작업은 상태와 완료일을 보존하고 이후 날짜의 진행 중 목록에서 제외한다. `GET /api/work-overview`의 기존 비계획 필터·버킷·목록·상세 접근을 유지한다. 비취소 완료 선조치 후보고는 `assigned`·`completed`에 한 번 포함하고 `after-action`·`afterActionCompleted`는 부분집합으로 표시한다. 남은 작업에는 후보고를 넣지 않는다. 계획 전용 및 전체 버킷을 제공하며 `all = assigned + planned`, `allCompleted = completed + plannedCompleted`, `allRemaining = remaining + plannedInProgress`로 센다. 각 버킷은 동일 조건으로 카드 건수·부서 건수·목록·목록 총건수를 계산한다. 계획 공유 행에는 출처·계획 식별자·부서·제목·상태 및 완료일(해당 시)만 사용하며 요청번호·요청 분류·일반/긴급·예정 일정을 지어내지 않는다. 계획 제목은 로그인 사용자 모두에게 표시한다. 선택 날짜의 업무 목록과 전체 현재 상태 집계는 다른 기준이다. 외부 체계 대조·일일 실적 판정은 제공하지 않는다.
- **삭제:** 삭제는 명시적 영구 삭제다. 같은 트랜잭션에서 계획 작업·완료일과 작업을 복원할 수 있는 이전 결과 영수증을 지운다. 삭제 사건·삭제 영수증·잠금 행은 남기지 않는다. 작업 정보나 삭제 사건과 연결할 수 없는 이전 제출 키의 비가역 해시만 남겨 늦은 생성 재전달을 거절한다. 삭제를 완료로 세지 않는다. 이 동작은 기존 요청·작업의 이력 보존 규칙에 대한 계획 작업의 명시적 예외다.
- **설계값·미결:** 완료 재개는 이번 안에 넣지 않고 날짜 정정·개별 삭제는 작업반 수정에 포함한다. 이는 사용자의 직접 결정이 아닌 설계 보완안이다. 공유 제목은 사용자 결정에 따라 로그인 사용자 모두에게 보인다. 외부 계획 체계는 작업반이 오늘 업무를 수동 확인하는 출처다. 별도 자동 대조나 일일 실적 일치 판정은 이번 범위가 아니다.
- **오류·동시성:** 제목·기준일 필수값, 완료일이 기준일 이상이며 오늘 이하인지, 현재 작업반 권한, 대상 버전을 검사한다. 생성·제목/기준일 수정·완료의 중복 제출은 명령 식별자로 한 번만 반영하고 오래된 편집은 충돌로 거절한다. 성공 결과 재전달은 현재 작업반과 저장된 작업 소유 작업반이 일치할 때만 허용한다. 같은 제출 번호를 다른 계정에서 재사용하면 작업 결과를 공개하지 않고 `OPERATION_NOT_AVAILABLE`로 거절한다. 삭제는 최종 확인 뒤 작업과 삭제 이력을 남기지 않고 수행한다. 영구 삭제는 재시도 영수증을 남기지 않는다. 응답 유실 뒤 최신 목록에서 항목 부재를 확인하고, 항목이 남아 있으면 현재 버전으로 다시 시도한다. 응답을 잃은 화면은 같은 제출 번호로 재시도한다. 미확정 생성 중에는 화면 이동을 막는다. 제출 번호·날짜·시각만 현재 탭의 sessionStorage에 보관하고 제목·로그인 식별자는 저장하지 않는다. 새로고침 뒤 제목을 다시 입력하며, 다른 계정의 이전 제출 번호가 거절되면 해당 임시 항목을 지우고 새 작업을 제목부터 입력한다. 삭제 뒤 재시도가 제출 번호 충돌이면 최신 목록을 조회하고 원래 작업이 없음을 사용자가 확인한 뒤 새 제출 번호로 전환한다. 로그아웃과 계정 전환 때 임시 정보를 지운다.
- **확인 방법:** API·DB 검사에서 생성·수정·완료·영구 삭제·작업반 격리·오래된 버전·중복 재전달을 확인하고, 조회/UI 검사에서 다음 날짜 자동 노출·완료 제외·전체 한 건 집계·제목 공유·새로고침 및 서버 재시작 보존을 확인한다. 비계획 API·상태·기존 현황 응답과 화면 회귀도 확인한다. 기존 `SAVE_FAILED` HTTP 500은 별도 원인 진단 후 전체 회귀 결과와 구별한다. 결과는 [계획 정비 구현 기록](../records/작업기록.md#planned-maintenance-implementation-20261021)에 남긴다. ## 현재 웹 데모의 기준선

아래는 복원된 정적 데모의 승인 당시 계약이다. 변경되지 않은 정비 업무 규칙을 추적할 때 사용한다. **일반·긴급 제외, 합성 인물, 운영 기능 제외 등 최신 결정과 충돌하는 과거 내용은 후속 구현에 적용하지 않는다. 위의 최신 결정과 [요구사항](요구사항.md)을 우선한다.** 현재 구현·검증 상태는 문서 첫 부분과 [개발 진행](../records/개발진행.md)을 따른다.

## 1. 작성 순서

1. 요구사항과 유스케이스로 제품이 해야 할 일을 정한다.
2. 시스템 요구사항으로 시연용 시스템에서 관찰할 수 있는 동작과 제약으로 구체화한다.
3. 승인된 시스템 요구사항을 각 모듈과 컨트롤러에 배정하며 아키텍처를 설계한다.
4. 아키텍처 검토 중 누락이 발견되면 시스템 요구사항으로 돌아와 수정한다.
5. 시스템 요구사항과 아키텍처가 승인된 뒤 개발명세서를 작성한다.

즉, 기본 순서는 `시스템 요구사항 → 아키텍처`다. 단, 설계가 요구사항의 누락이나 모호함을 발견하면 앞 단계로 돌아가는 반복을 허용한다.

## 2. 목표와 범위

### 2.1 목표

- 요청자, BNOC, 작업반 사용자가 하나의 요청을 등록·배정·처리·조회하는 흐름을 실제 제품처럼 시연한다.
- 유스케이스 `UC-001~011`의 정상, 주요 대안, 주요 예외 흐름을 화면에서 시연한다.
- 백엔드 완성도보다 화면 완성도, 업무 흐름의 이해도, 시연 안정성을 우선한다.
- 브라우저에서 접근할 수 있는 공개 URL로 배포한다.

### 2.2 포함

- 합성 계정을 이용한 `ACT-01` 요청자, `ACT-02` BNOC, `ACT-03` 작업반 사용자 흐름
- 하나의 시연 세션에서 등록·수정·배정·상태 변경·알림·이력을 연결하는 시연
- 합성 초기 데이터와 시연 중 생성된 휘발성 데이터
- 반응형 화면, 마우스 조작, 입력 검증, 빈값·오류 표시
- 공개 웹 배포

### 2.3 비범위

- 실제 공군 인트라넷 로그인, SSO, 실제 계정 연동
- `ACT-04` 권한 관리자와 `UC-012` 권한 관리
- 운영 수준의 서버 API, 서버 권한 검사, CSRF 방어, 서버 세션
- DB, 기기 간 공유, 재접속 영속성, 기한 없는 보존
- 실제 파일 전송·저장·재접속 다운로드
- 실제 동시 수정, 분산 트랜잭션, Idempotency-Key
- 실제 알림 전달, 푸시, 전자우편, SMS
- 실제 부대명·인물·군번·연락처·운영 자료

## 3. 데모 해석 규칙

- 이 문서의 `저장`은 별도 표시가 없으면 현재 시연 세션의 데모 상태 변경을 뜻한다.
- 요청자로 등록한 결과는 같은 시연 세션에서 BNOC로 역할을 바꿨을 때 보여야 한다.
- 새로고침이나 별도 기준 상태 복구 수단은 사전 정의된 합성 초기 상태를 복구할 수 있다. 복구 수단은 일반 사용자 화면에 데모 기능으로 노출하지 않는다.
- 화면에서 역할별 정보를 숨기는 것은 시연용 표현이며 실제 서버 보안 경계를 의미하지 않는다.
- 알림은 화면 내 이벤트로, 첨부는 파일 선택과 메타데이터 표시로 모사한다.
- 사용자 화면은 실제 배포되어 운영 중인 업무 서비스처럼 표현한다. 데모·모사·휘발성·더미 등 구현 한계는 사용자 화면에 표시하지 않는다.
- 실제 인증·권한·저장·알림·첨부·동시성의 구현 경계는 내부 문서와 검증 결과에서만 정확히 기록한다.

### 4.3 BNOC 검토·배정

| ID | 시스템 요구사항 | 연결 | 검증 기준 |

| SR-DEMO-014 | BNOC는 모든 데모 요청을 조회하고 요청 내용·위치·연락처·일정·문서 참조정보를 수정할 수 있어야 한다. 요청 식별값·등록자·등록시각은 편집할 수 없어야 한다. | FR-010, UC-002 | 허용된 필드만 수정되고 자동 생성 필드에는 편집 제어가 없다. |

BNOC는 외부 체계의 문서 등록·확인을 기다릴 때 `대기`인 요청을 `문서 대기`로 전이할 수 있어야 한다. `문서 대기`에서 작업반을 배정하면 `배정`으로, 요청자가 취소하면 `취소`로 전이해야 한다. `문서 대기`에서 이 외의 상태로 직접 전이하지 않아야 한다. `대기`에서 바로 배정하는 흐름과 모든 비취소 상태의 취소는 기존 규칙을 따른다. 문서 대기 외의 지연·외부 대기 상태는 제공하지 않는다. | FR-011(상태 전이로 정정), FR-032, UC-002, UC-007, 사용자 검토 반영 | `문서 대기`가 요청 상태로 표시되고 별도 해제 행동·버튼·토글은 없다. 문서 대기와 관련된 직접 전이는 `대기 → 문서 대기`, `문서 대기 → 배정`, `문서 대기 → 취소`만 허용되고, 문서 대기에서 `작업 중`·`완료`로 직접 전이할 수 없다. `대기 → 배정`과 기타 비취소 상태의 `취소` 전이는 유지된다. |

### 4.4 작업반 처리·상태 계산

## 8. 검토 기준

사용자 승인 완료. 이 문서를 개발 계약으로 사용하며 검증은 다음을 확인한다.

1. `UC-001~011`의 정상 흐름과 핵심 예외 흐름이 빠지지 않았는가.
2. 내부 문서·검증에서는 구현 경계를 숨기지 않으며, 사용자 화면은 실제 배포된 운영 서비스처럼 표현하는가.
3. 시연 중 역할 전환으로 요청 생성부터 완료까지 하나의 흐름을 이어갈 수 있는가.
4. 실제 운영 자료 없이, 가림·자리표시자가 아닌 자연스러운 합성 데이터만으로 전체 시연이 가능한가.
5. 아키텍처나 특정 기술을 미리 확정한 항목이 없는가.
6. 각 요구사항이 화면 조작이나 검사로 확인 가능한가.
