## 2026-10-28 · 팀원 검토에 따른 신청·조회 흐름 개선

[요구·흐름·기능 명세](시스템요구사항.md#team-feedback-20261028)의 기존 모듈 배정을 확장한다. 과거 HTML은 대상이 아니다.

- GuidedRequestFields/intakeModel: 입력·활성 분기·현재 대상과 순차 탐색을 받아 이전 단계/바로 다음 질문을 계산하고 값·수량·파일 참조를 보존한다. RequestRegistrationForm은 새 신청/재사용 진입과 제출·초안 잠금을 연결한다.
- AttachmentPicker/AttachmentDocumentDialog/HwpPageRenderer: 업로드된 첨부 메타와 권한 있는 원본 bytes로 신청 전/후 동일 원본 미리보기·닫기·실패 복구를 제공한다. AttachmentService/DocumentAnalysisService는 본인 request 임시 파일 예외와 연결 파일의 현재 권한을 검사하고 임시 파일 분석/검색은 만들지 않는다.
- QueryService/RequestQueryService: 목록은 숫자 요청번호 기준으로 정렬하고 요청자 상세의 현재 부서/대표전화만 투영한다. 원 작업·반환 레코드는 변경하지 않는다. RequestListAndSearch/RequestDetailWorkspace/App는 재사용 후보와 원본 재조회 경로를 연결한다.
- 기존 OperationsService/Database/WorkflowService: 부서 대표전화의 비파괴 저장·초기 임시값·관리자 전용 명령/버전/동일 제출 처리를 담당한다. SharedWorkOverview는 관리자 편집을 제공하고 일반 역할은 현재 담당 요청 상세에서 번호를 읽는다.
- 공통 전화 입력/검증은 신청·수정·후보고·명부·대표전화에서 재사용한다. SharedWorkOverview의 비교표는 마지막 성공 부서 조건으로만 행을 제한하고 기존 집계는 유지한다.

## 2026-10-27 · 적응형 신청 모듈 배정

[SR-BE-054](시스템요구사항.md#adaptive-intake-20261027)을 기존 단일 업무 서버 구조에 배정한다. 아키텍처 HTML은 변경하지 않는다.

| 모듈 | 행동·입출력·연결 |
| --- | --- |
| RequestRegistrationForm / GuidedRequestFields / intake model | 입력은 현재 세션·RequestInput, 출력은 미완성 초안과 최종 대상 목록. 목적 4선택과 지원 하위 경로를 먼저 정하고 활성 경로의 질문만 표시한다. 새 대상은 선택 작업을 이어받고 기존/대상별 다른 작업은 보존한다. 필수 진행 목록과 활성 필드 목록을 분리하고 기본 경로의 대상별 확인을 최종 확인에 통합한다. 추가정보/첨부 편집은 별도로 열고 단일 필드 수정 뒤 출발 요약으로 복귀하며 알려진 연락처/요청자는 재질문하지 않는다. 이전 위치는 명시적 빠른 선택으로만 현재 대상에 적용한다. 추가정보 선택은 현재 대상의 사용자 선택과 탐색 복귀를 구별해 Back/초안에 보존하며 다음 대상과 분할 자식에 전파하지 않는다. 목적/경로별 입력과 첨부·질문 복원, 선택·분할·뒤로는 정식 저장과 분리하고 공통 Button/ActionGroup/DateInput을 사용한다. |
| requestPayload / requestReuse / RequestDetailWorkspace | 활성 분기만 직렬화하고 상세·수정·재사용에서 구조화 대상을 보존한다. 기존 신청/후보고 계약으로 전달하며 재사용의 신원·첨부·일정 허용목록은 유지한다. |
| IntakePolicy / WorkflowService | 대상 스키마·수량 합계·활성 필드·첨부 참조를 검증/정규화하고 대표 분류/내용/위치를 계산한다. 기존 권한·버전·영수증·알림 트랜잭션 안에서 호출한다. |
| RequestRecord / Database | 기존 요청에 nullable intake_json을 추가한다. 구형 자료는 null로 두고 새 대상 구조만 함께 저장/조회한다. |
| RequestDraftService / useRequestDraft | 현재 계정/역할의 미완성 진행과 보호 첨부를 기존 CAS/64KiB/원자 소비 계약으로 보존한다. |
| QueryService | 현재 요청 권한 안에서 모든 대상·위치·분류를 검색하고 상세/요약에 제공한다. 공유 현황/달력에 비공개 대상 내용·연락처를 추가하지 않는다. |

대상 배열은 WorkRecord의 처리 단위로 전달하지 않는다. 실제 부서 배정·일정·상태 계산은 기존 모듈에 남긴다.

## 2026-10-25 · 신청서 영속 초안 모듈 배정

RequestRegistrationForm은 현재 입력·마지막 임시저장 스냅샷·시작 draftId/revision을 분리하고 명시적 저장/복원/삭제와 현재 필수 검사를 담당한다. App은 기존 로그인/신청/재사용 경로를 연결하며 계정·역할 변경 시 폼 메모리를 교체한다. ApiClient는 기존 같은 Origin/CSRF로 초안 조회·쓰기 API를 호출한다.

ApiController는 활성 세션을 RequestDraftService에 전달한다. RequestDraftService는 WorkflowService가 같은 DB/쓰기 트랜잭션과 파일 경로로 구성하는 모듈이며 작성 계정/역할·허용 입력·CAS·첨부 보호·동일 저장 재시도와 정확한 초안 소비를 담당한다. Database는 v15 초안 행과 attachment.draft_ref를 저장한다. AttachmentService는 보호된 파일을 임시 정리에서 제외한다. RequestCommands/WorkflowService는 성공 영수증 처리 뒤 제출 초안을 잠그고 현재 필수/소유권/파일 검사를 수행하며 정식 생성 성공과 함께 소비한다. Query/검색/분석 모듈은 초안을 정식 요청으로 조회하지 않는다. HTML 설계 이력은 갱신하지 않는다.

## 2026-10-25 · 이전 신청 초안 모듈 연결

QueryService.detail은 원래 조회권한을 확인한 후 본인 직접 등록 여부인 canReuse만 추가한다. RequestDetailWorkspace는 재사용 버튼·진행/실패 안내를 제공하고 App은 현재 상세 재조회→계정/경로/canReuse 확인→미저장 이동 확인→허용 필드의 메모리 초안 전달을 맡는다. requestReuseFields는 입력으로 받은 DTO의 허용 필드만 새 등록폼 입력으로 변환한다. RequestRegistrationForm의 기존 initialDraft와 새 초안별 key를 사용하며 저장은 기존 RequestCommands/createRequest를 사용한다. DB·복제 API·새 업무 상태는 만들지 않는다.

## 2026-10-25 · 원본 미리보기 책임 정정

AttachmentService는 기존 연결·조회권한 검사를 유지하면서 회의 첨부의 PDF/이미지 inline과 HWP/DOCX render-source를 허용한다. AttachmentDocumentDialog는 분석 상태와 원본 보기 가능 여부를 분리해 원본을 기본 표시하며 분석 제외 파일의 빈 분석 패널은 숨긴다. HwpPageRenderer는 기존 HWP 원본, 신규 DocxPageRenderer는 sandbox 프레임의 DOCX 페이지 렌더를 맡는다. DOCX 렌더는 자체 제공 JS만 실행하고 외부 네트워크/상위 DOM 접근을 차단한다. ### StatusGuide · 프런트엔드 공통 안내

- **입력:** 상태, 허용된 부서 진행, 공개 진행 맥락, 요청/작업 구분, 연결된 공식 부서 대표번호(없을 수 있음).
- **출력:** 요청 배지는 모든 유효 담당 부서, 개별 작업 배지는 해당 작업 부서 하나와 번호를 표시한다. 번호 자료가 없으면 `대표번호 미등록`으로 표시하며 요청자·개인·정비대상자 번호로 대체하지 않는다. 선조치 후보고는 수행 부서로 표현한다. 실제 처리 이력·다음 담당자를 추정하지 않는다. 상세 단계 도식에서 개별 작업의 내부 `작업 중`은 `작업 준비`로 표시하고 요청 전체 `작업 중`은 유지한다.
- **호출:** 목록/상세/작업 화면이 같은 컴포넌트를 사용한다. 서버 데이터는 ApiClient만 호출한다. 반환 원문/다른 부서 메모를 안내 생성에 전달하지 않는다.

### QueryService 개정 · 검색·권한·표시

- **입력:** 기존 필터 + q, 현재 Actor. 요청 본문·분류와 현재 연결된 HWP/PDF 디지털 본문·메타데이터를 권한 범위에서 검색한다.
- **출력:** 기존 권한별 목록과 요청 요약·일치 출처/안전한 문맥·문서 블록/메타데이터 위치. 총건수·목록·분석 미완료 안내는 같은 repeatable-read 스냅샷을 사용한다.
- **연결:** Database의 요청 구조 정보와 현재 연결된 DocumentAnalysisService 결과만 읽는다. OCR 결과를 만들지 않으며 문서 본문을 기존 전체 공유 현황 DTO로 전달하지 않는다.
- **일정 연계:** 검색 q는 신청 목록 조회에만 추가한다. 팀원 일정 카드에는 본문·문서 문맥·전화번호를 넣지 않으며 기존 상세 링크에서 요청 권한을 다시 검사한다. 계획 정비는 요청 검색 대상이 아니다.
- **주의:** 요청 대상 구조를 새로 추가하지 않는다. 일정·공유 DTO와 기존 요청 상세 권한을 유지한다.

### DocumentAnalysisService / AttachmentViewer

E-037·E-038에 따라 HWP 원본 페이지 레이아웃 보기와 PDF 원본 보기를 제공한다. HwpPageRenderer는 같은 Origin의 권한 검사 endpoint에서 HWP 원본을 받아 브라우저 내 WASM으로 페이지 SVG를 만든다. AttachmentViewer는 첫 페이지를 기본 표시하고 페이지 이동과 추출 본문 보기를 제공한다. SVG 문자열을 HTML로 삽입하지 않으며 닫힘/권한 상실 시 임시 URL·문서 바이트를 정리한다. 한컴 앱과의 완전한 시각 일치는 주장하지 않고 비민감 다중 쪽·표 fixture로 배치·쪽나눔을 확인한다.

- **서버 행동:** 현재 요청 연결을 확인해 분석 작업을 영구 예약하고 로컬 격리 작업자로 원본을 읽는다. 디지털 HWP/PDF 본문·문단/표 블록·명시적인 메타데이터 후보·출처·처리 상태를 저장한다. PDF는 Tika native text extraction만 사용한다.
- **입력:** 저장된 첨부 참조·원본 해시·분석기 버전·작업 세대. 재분석 요청에는 현재 권한·현재 분석 버전·같은 제출 키를 받는다.
- **출력:** 허용된 사용자에게 문서 상태·메타데이터·페이지/블록 단위 읽기자료, 검색에는 현재 연결된 성공/일부 본문과 완전성만 제공한다.
- **일정 경계:** 회의 일시·장소 후보를 희망 지망, 실제 작업 구간, 후보고 실제 시작·완료 시각에 자동 반영하지 않는다.
- **호출:** AttachmentService가 연결 저장 성공 후 작업을 예약한다. 시작/스케줄러가 영구 대기 작업을 처리하며 로컬 Tika parser만 사용한다. Tesseract와 OCR parser를 구성하지 않는다. DB 작업 예약 실패는 복구 탐색으로 보완한다. 업무 트랜잭션에서 문서 파싱을 실행하지 않는다.
- **원본 보기:** AttachmentService의 별도 inline 경로는 PDF/이미지를 제공한다. `/render-source`는 요청 권한·HWP 형식·FR-045 제외를 재검사해 HWP 바이트를 반환한다. 다운로드 경로는 유지한다.
- **HWP 렌더링:** HwpPageRenderer는 원본 byte array를 `@rhwp/core` WASM에 전달한다. 브라우저 Canvas로 글자 폭을 재고 SVG 페이지를 만든다. DOM에 SVG markup을 주입하지 않고 Blob URL을 `<img>`에서 열며 페이지 변경·언마운트 때 URL과 문서 buffer를 해제한다. WASM 로드/파싱 오류는 추출 본문·원본 다운로드 경로로 우회한다.
- **화면:** AttachmentViewer는 HWP 페이지 레이아웃·추출 읽기보기·추출 정보·분석 상태를 렌더링하며 PDF/이미지 원본과 기존 기타 형식 읽기보기도 유지한다. 닫기/권한 상실 시 자료와 임시 URL을 정리한다.

**설계 0.8 · 2026-10-17 사용성 개선 구현 완료.** 현업 의견8개·각 부서 지정 개인 담당자 정정을 기능·모듈·함수·호출에 연결해 구현했다. 기존 업무 계약을 유지하며 추가한 동작과 검증 결과는 [개정·합격 기준·실행 기록](../records/작업기록.md#usability-design-20261017)에 연결했다. 이 설계도 자체는 실행 증거가 아니며 실제 SSO/GPS/CPCON 연동은 남아 있다.

**2026-10-20 후속 사용성 설계·표현 조정:** 기존 모듈 안에서 조합별 placeholder·최초 배정 후 현황 복귀·배정 조작별 별도 카드 배치·일정 카드에서 요청 상세 제외와 표시 규칙·공유 목록의 요청자 군내전화번호 예외·상태 표시명 매핑을 연결한다. 조회 범위·저장 상태·업무 명령은 유지한다. 최신 구현과 검증은 [작업 기록](../records/작업기록.md#followup-usability-implementation-20261020)·[개발 진행](../records/개발진행.md)을 따른다. 일정 카드의 연락처·표시 상세는 2026-10-21 DEC-034로 대체한다.

**2026-10-21 · 일정·선조치 후보고 설계 결정:** 요청 희망 일정은 선택 1·2지망(날짜+오전/오후), 작업반 일정은 24시간 범위의 정시 시작 1시간 구간 여러 개로 모델링한다. 기존 정확한 작업 시각은 시작값 그대로 보존해 1시간으로 이관한다. 선조치 후보고 완료는 공유 할당·완료 집계와 우리 반 일정에 포함하지만 출처를 구분하며 BNOC 배정으로 표현하지 않는다. 실제 시작을 포함하는 정시 1시간 칸에 완료 기록으로 두고 정확한 시각을 보존한다. 일정 카드의 작업 번호·상태·위치·메모·전체 카드 링크와 전화번호/요청 상세 제외를 각 조회·화면 모듈에 배정한다. 기존 DB 구조로 복수 선호/일정 구간을 표현할 수 없어 마이그레이션이 필요하다. 상세 계약은 [DEC-034](요구사항.md#dec-034)·[개발 명세](개발명세서.md#일정선조치-후보고-저장전송-계약-2026-10-21)를 따른다. 제품 코드는 이 문서 작업에서 바꾸지 않는다.

**2026-10-22 · 작업반 일정 카드 중복 제거 결정:** OpsQueryService가 반환한 작업별 복수 시간 구간은 유지한다. TeamScheduleView는 조회 기간과 겹치는 같은 작업을 카드 하나로 모아 가장 이른 겹침 시작 시각으로 배치·정렬하고, 그 카드에 기간 안의 모든 구간을 표시한다. 계획 구간이 조회 범위에 없는 완료 작업은 완료 시각, 후보고는 실제 시작 시각으로 한 번 배치한다. 조회 시작 전부터 이어진 구간은 범위 내 처음 겹치는 시각에 두고 원래 시각을 표시한다. 완료 카드는 예정 카드와 색을 구분하고 상태 문구를 유지한다. 완료 일반 작업에 계획 구간이 보이면 계획 시간만 표시하고 완료 날짜·시각은 덧붙이지 않는다. 계획 구간이 없어 완료 시각의 시간 칸에 배치되는 카드도 별도 시간 문자열은 생략한다. 선조치 후보고의 실제 시작 시각 표시는 유지한다. [DEC-035](요구사항.md#dec-035)와 [SR-BE-021](시스템요구사항.md#sr-be-021)를 따른다. 저장·API·DB 계약은 변경하지 않는다.

**0.7 제품 당시 · 2026-10-14 PC 전용 완성도 개선:** 기존 모듈·API/저장 경계와 업무를 유지한다. PC 1280·1440 화면으로 검수하고 모바일 반응형·표 카드·좁은 화면 검수는 폐기한다. 관련 화면 모듈의 오류/초점·구체 저장 결과·조회 조건/시각·단위·배치 책임을 아래에 반영한다. 새 업무 서버나 별도 설계 웹은 만들지 않는다.

## 백엔드·운영 모듈 설계 · 설계 0.8 구현 계약

[요구사항](요구사항.md#current-requirements)·[유스케이스](유스케이스.md#current-usecases)를 36개 시스템 요구사항으로 구체화하고 아래 40개 책임 단위에 배정했다. 책임 단위는 클래스·화면·외부 연결을 포함하며 독립 서버 40개를 뜻하지 않는다. **단일 백엔드 서버 안의 모듈 분리안**이다. 2026-10-21 계획 정비 모듈 배정에 따라 실제 구현과 독립 검토·검증을 완료했다. 과거 [인터랙션 웹](아키텍처설계.html)은 2026-10-21 이후 갱신·검토하지 않는다. 현재 계획 정비 계약은 이 Markdown을 따른다. 원본 복구본은 Git `fed2b10:docs/spec/아키텍처설계.html`에 보존한다.

기존 업무 계약을 유지하면서 0.8의 일반 기본 선택·배정 추가/해제·개인 소속 관리 권한·서식·공통 상단을 구현했다. 2026-10-21 계획 정비 모듈을 기존 서버·화면에 구현했다. 새 업무 서버나 새 설계 웹을 만들지 않았다. 공통 상단은 OperationsView가 표시하고 ApiClient가 공유 조회 상태를 맡는다. 실행 결과는 [개발 진행](../records/개발진행.md)에 연결하며 이 지도 자체를 실행 증거로 사용하지 않는다. 실제 공군 SSO/GPS/CPCON 연동 완료 증거는 없다.

## 모듈별 구현 계약

함수는 사용자 승인된0.8 구현 계약이다. 기존0.7 제품과 새 동작을 구분하며 실제 외부 연결·제품 검증 완료를 뜻하지 않는다. 변경된 행동·입출력은 최신 기능 명세를 우선한다.

<a id="airforcesso"></a>
### 공군 SSO · 실제 연동 경계 · `AirForceSSO`

- **실행 영역:** 외부 연동
- **책임:** 외부 인증 시스템. 검증 가능한 신원을 제공하며 서비스 내 업무 권한과 전체 부대 명부까지 제공한다고 가정하지 않는다. 대회에는 연결하지 않으며 모의 인증 제공자를 사용한다. 실제 규격 확보 후 연결 부분을 구현·검증한다.
- **받는 값:** 인증 연동 요청(규격 미정)
- **내보내는 값:** 서버가 검증할 인증 결과
- **실패·금지:** 연동 실패·위조·만료는 서버가 거절한다.
- **설계값·후속 조건:** 실제 프로토콜·검증 키·로그아웃; 대회용 계약과 별도
- **배정 기능:** SR-BE-001, SR-BE-034

| 함수 | 행동 | 조건 |
| --- | --- | --- |
| `authenticate(connection): IdentityProof` | 외부 신원 확인 | 연결 규격 미정. 실제 로그인 화면을 여기서 구현하지 않음 |

<a id="externalsituationfeed"></a>
### GPS 정보원 · 실제 연동 경계 · `ExternalSituationFeed`

- **실행 영역:** 외부 연동
- **책임:** 부대 공통 GPS 단계를 제공하는 외부 시스템 경계. 새로 답한 자동 수집 요구를 연결한다. 대회에는 실제 연결 없이 모의 정보원을 사용한다.
- **받는 값:** 정해질 인증·조회 요청
- **내보내는 값:** 외부 단계·원본 기준시각
- **실패·금지:** 연결/값 오류는 정상 단계가 아니다.
- **설계값·후속 조건:** 정보 제공 시스템·연동 규격
- **배정 기능:** SR-BE-026, SR-BE-034

| 함수 | 행동 | 조건 |
| --- | --- | --- |
| `fetch(connection): ExternalGpsSnapshot` | 외부 GPS 정보 조회 | 실제 URL·인증·원본 값 규격 미확정 |

<a id="externalcpconfeed"></a>
### CPCON 정보원 · 실제 연동 경계 · `ExternalCpconFeed`

- **실행 영역:** 외부 연동
- **책임:** 향후 CPCON 실제 정보원을 연결할 경계. 대회에는 연결하지 않으며 공군에서 실제 제공하는 API가 확인됐다는 뜻이 아니다.
- **받는 값:** 후속 확정할 인증·조회·적용 범위
- **내보내는 값:** CPCON 원본 코드·표시명·기준시각·적용 범위
- **실패·금지:** GPS 응답으로 대체하거나 같은 단계 사전을 사용하지 않는다.
- **설계값·후속 조건:** 실제 정보원·규격·단계 사전·범위
- **배정 기능:** SR-BE-035, SR-BE-034

| 함수 | 행동 | 조건 |
| --- | --- | --- |
| `fetch(connection): ExternalCpconSnapshot` | 실제 CPCON 정보 조회 | 실연동 규격 확보 후 구현·호환 검증 |

<a id="demoidentityprovider"></a>
### 대회용 모의 인증 제공자 · `DemoIdentityProvider`

- **실행 영역:** 외부 연동

- **설계값·후속 조건:** 대회 기술값: 확인표 60초·로그인 요청 5분. 역할명으로 표시하고 서비스 권한은 BNOC 서버 매핑에서 결정. 초기 BNOC 범용 담당자나 작업반 전원 관리 권한 구성은 개정 대상이며 정상 구조로 승계하지 않는다.
- **배정 기능:** SR-BE-001, SR-BE-003, SR-BE-033, SR-BE-034

<a id="transactionstore"></a>
### 트랜잭션·영구 저장 · `TransactionStore`

- **실행 영역:** 백엔드 서버
- **책임:** 메모리 전체 상태 교체를 DB의 원자적 저장으로 옮긴다. 같은 요청의 경합·중복 제출·번호 고유성을 처리하며 전체 AppState는 화면으로 보내지 않는다.
- **받는 값:** 검증된 명령 컨텍스트·제출 키·주 대상 버전·변경 집합; 종류·범위별 상황 스냅샷·수집 시도
- **내보내는 값:** 함께 저장된 업무·이력·알림·영수증 또는 충돌/실패
- **실패·금지:** 권한 재검사 뒤 재전달. 커밋 여부 불명은 성공/롤백으로 단정하지 않는다. 상황의 마지막 성공 값과 실패한 시도 결과를 구별하며 종류 간 덮어쓰기를 금지한다.
- **설계값·후속 조건:** 성공 영수증은 업무 기록과 함께 보존한다. 요청→주 대상 작업 순서로 잠그며 잠금 대기는 5초, 교착 시 내부 최대 2회 재시도한다. 처리 중 응답은 202/PROCESSING·Retry-After 2초다. 상세는 개발명세서 기술 설계값을 따른다. addTeams와 마지막 완료, 반환 정정/재배정/withdrawReturnedWork 모두 요청→작업 잠금과 최신 조건 재검사를 사용한다. 작업 순번은 과거 최대+1로 발급하고 해제 번호 재사용 금지. 알림 확인은 실제 표시된 본인 수신 notificationIds 집합만 is_read=false→true로 단조 갱신한다. 하나라도 타 수신자/비허용/없는 ID면 전체 거절하며 다른 과거/늦게 도착한 항목은 건드리지 않는다. assignTeams/addTeams/reassignAssignedWork/reassignReturnedWork/withdrawReturnedWork의 배정 구조 변경 성공은 전체 상태가 같아도 요청 버전을 증가시킨다. 다른 반의 독립 작업 저장은 유효한 주 대상 작업 버전으로 검사하고 화면에 별도 요청 버전을 추가 요구하지 않는다. 계획 작업은 별도 저장하고 계획 작업 자체 버전으로 동시성을 검사한다. 삭제는 작업·최초 기준일·완료일을 같은 트랜잭션에서 영구 제거하고 삭제 이력은 남기지 않는다.

<a id="sessionmanager"></a>
### SSO 검증·서버 세션 · `SessionManager`

- **실행 영역:** 백엔드 서버
- **책임:** 실행 설정의 제공자로부터 인증 결과를 검증하고 시험/운영 신원을 서버의 서비스 권한에 매핑한다. 대회에도 같은 서버 세션을 생성하고 매 요청 권한을 확인한다. 시작 브라우저의 서버 사전 인증 상태·로그인 요청과 인증 결과를 연결하며 브라우저의 역할 선택값은 권한 근거가 아니다. 공개 시연에서는 브라우저 로그인 위치를 BNOC 공개 Origin의 /identity로 안내하고, 서버의 확인표 검증은 loopback 모의 제공자 주소를 사용한다. 각 부서 담당자는 개인 소속과 독립 관리 권한으로 식별하며 재인증·권한 오류·복귀 때 표시 맥락을 새 세션 응답으로 갱신한다.
- **받는 값:** 시작 브라우저의 서버 사전 인증 상태·로그인 요청·인증 확인표 또는 세션 참조, 서버의 대회/운영 제공자 설정, 공개 HTTPS Origin·loopback 제공자 주소·공개 인증 조회 조건/폼
- **내보내는 값:** 서버가 확인한 사용자·역할·부서·작업반 권한, 공개 로그인 위치·모의 인증 HTML; 개인 소속과 역할 독립 departmentManager 범위
- **실패·금지:** 미인증·위조·만료·재사용·요청 불일치·시작 브라우저 불일치는 거절한다. 로그인 요청은 시작 브라우저의 서버 사전 인증 상태에 묶고 인증 완료 시 함께 소비한다. 운영 모드에서는 모의 인증을 거절하며 실제 연동 실패 시 모의 인증으로 자동 전환하지 않는다. 브라우저의 역할 값으로 권한을 만들지 않는다.
- **설계값·후속 조건:** 기술값: 세션 유휴 30분·절대 8시간, 로그인 요청 5분·단회 확인표 60초. 시험 신원/권한 매핑은 서버 저장. 실제 공군 SSO 규격·로그아웃·검증은 후속 조건.
- **배정 기능:** SR-BE-001, SR-BE-002, SR-BE-003, SR-BE-034

| 함수 | 행동 | 조건 |
| --- | --- | --- |
| `beginLogin(preAuthSession): LoginChallenge` | 서버 로그인 요청 생성·제공자 로그인 이동 안내 | 현재 브라우저의 서버 사전 인증 상태에 요청 식별값·만료·허용된 복귀 경로 결합; 업무 권한은 아직 없음 |

<a id="accesspolicy"></a>
### 서버 권한 판정 · `AccessPolicy`

- **실행 영역:** 백엔드 서버
- **책임:** 상세·공유 조회와 수정 권한을 분리한다. 입력된 역할 대신 서버의 현재 컨텍스트와 대상 소유·소속을 검사한다. 자기 부서 명부/현황 쓰기는 지정 개인의 departmentManager와 소속을 함께 검사한다. 메뉴 표시와 직접 경로도 현재 권한에 맞춘다.
- **받는 값:** 현재 ActorContext·행동·대상 소유/부서/반

<a id="sharedworkqueryservice"></a>
### 전체 공유 작업 집계 · `SharedWorkQueryService`

- **실행 영역:** 백엔드 서버
- **책임:** 모든 로그인 사용자가 전체 작업 집계·목록을 보되 상세 권한은 유지한다. 비계획 요청 작업은 RequestStatusCalculator의 공통 요약을 사용한다. 비계획 공유 행은 승인된 요청자 군내전화번호를 예외로 투영하고 다른 비공개 필드는 제외한다. 계획 정비는 별도 저장 데이터에서 논리 작업 단위로 집계한다.
- **받는 값:** 부서·유형·상태·분류 필터와 `assigned/completed/remaining/returned/after-action/unassigned/planned/all` 버킷
- **내보내는 값:** 기존 작업 집계·같은 조건의 공유 목록·총건수·기준시각, 계획 진행 중/완료 수와 전체 합계. 비계획 행의 requesterContact, 계획 행의 식별자·부서·제목·상태·기준일·완료일을 출처별로 반환한다.
- **실패·금지:** 요청자 군내전화번호 외 요청 본문·위치·정비대상자 연락처·첨부·인원·작업 메모·이력 원문을 비계획 공유 행에 노출하지 않는다. 계획 행에는 연락처나 요청 상세 링크를 만들지 않는다. 재고/장비 가용 추론 없음.
- **설계값·후속 조건:** 유효 비계획 작업은 취소되지 않은 요청의 resolution.kind=open이며 미해결 반환을 포함한다. 일반/긴급을 모두 보이고 반환을 미배정으로 오인하지 않는다. 최신 사용자 결정 FR-044에 따라 비취소 선조치 후보고 완료를 할당·완료 및 부서별 해당 수에 한 번 포함한다. 후보고 출처별 수는 이 수의 부분집합으로 중복 가산하지 않는다. 기존 미배정 요청은 작업과 분리한다. 계획 `planned`와 출처별 전체 `all` 버킷은 논리 작업을 건당 한 번 센다. `assigned`에는 후보고 완료가 이미 포함되므로 `all = assigned + planned`, `allCompleted = completed + plannedCompleted`, `allRemaining = remaining + plannedInProgress`다. 계획 전용 `planned`는 요청번호·유형·우선순위·예정 일정이 없는 별도 데이터이며 기존 비계획 요청 권한은 바꾸지 않는다. 요청 전용 필터가 지정되면 계획 데이터는 일치 기준이 없어 전체 조회에서도 제외하고 부서 필터는 계획 소유 작업반으로 제한한다. 상태 `완료`는 계획 완료를 포함하고 `진행 중`은 계획 상태에만 적용한다. 날짜별 화면 노출은 전체 현재 상태 합계와 구분하며 외부 체계 자동 대조는 하지 않는다. 동일 필터의 카드·부서별 합계·선택 버킷 목록·총건수를 일치시킨다. 반환 처리 대기는 기존 bucket=returned,size=1의 returned 응답으로 조회한다.
- **배정 기능:** SR-BE-003, SR-BE-023, SR-BE-015, SR-BE-036

<a id="plannedworkservice"></a>
### 계획 정비 작업 처리 · `PlannedWorkService`

- **실행 영역:** 백엔드 서버
- **책임:** 현재 로그인 세션의 작업반이 소유한 계획 작업을 생성·수정·완료·영구 삭제한다. 계획 체계 연결이나 비계획 요청/작업 명령은 호출하지 않는다. 기준일부터 선택한 날짜까지 진행 중 작업을 같은 항목으로 일일 목록에 자동 노출한다.
- **받는 값:** ActorContext·제목·과거/오늘/미래를 허용하는 최초 업무 기준일·오늘 이하의 완료일·계획 작업 식별자/버전·명시적 operationId(삭제는 버전만)
- **내보내는 값:** 허용된 작업반의 제목·최초 업무 기준일·선택적 완료일·`진행 중`/`완료` 상태 또는 명시적 거절
- **실패·금지:** 작업반은 세션에서 결정하며 입력 부서값으로 바꿀 수 없다. `request_number IS NULL`인 비계획 작업 행을 만들지 않는다. 매일 날짜 기록을 따로 추가하거나 날짜별 복제 행을 만들지 않는다. 기준일 정정은 작업반의 명시적 수정으로만 허용한다. 완료 재개는 이번 범위에 포함하지 않는다.
- **설계값·후속 조건:** 신규 항목은 진행 중으로 시작한다. 최초 업무 기준일 이후 선택 날짜의 목록에서 계속 보이며 완료일 이후에는 진행 목록에서 빠진다. 완료는 기준일 이상·오늘 이하의 명시한 날짜와 함께 저장한다. 기존 `WorkflowService` 공통 명령은 작업번호·요청번호와 지속 `bnoc_receipts`/`bnoc_operation_locks`를 전제하므로 계획 저장은 별도 계획 API·계획 전용 영수증에 둔다. 영수증은 해당 계획 작업을 참조하며 영구 삭제 때 항목·완료일·이전 결과 영수증을 같은 트랜잭션에서 제거한다. 업무 내용/계정과 연결되지 않은 제출 키 전역 해시와 행동자별 사용 키 해시만 남겨 다른 계정의 키 재사용 및 삭제 뒤 늦은 재전달을 거절한다. 재전달은 현재 세션 작업반과 영수증이 가리키는 작업의 저장 작업반이 일치할 때만 허용한다. 삭제 자체는 영수증·잠금 행을 만들지 않고 응답 유실 뒤 재조회해 부재를 확인한다. 공유 집계는 별도의 SharedWorkQueryService가 맡는다.
- **배정 기능:** SR-BE-003, SR-BE-036

### BNOC 공지게시판 처리 · `DirectiveService`

- **실행 영역:** 백엔드 서버
- **책임:** 모든 로그인 사용자가 공지 목록·본문·첨부를 조회한다. BNOC가 글을 게시하고 BNOC 계정이면 작성자와 무관하게 제목·본문·첨부를 수정한다. 게시 종료·숨김·읽음 확인은 없다. 기본 서식을 허용 문서 구조로 저장하며 rich일 때 body는 서버가 bodyDocument에서 계산한다.
- **받는 값:** 서버 BNOC 권한·제목·본문 payload(body plain 문자열, optional bodyDocument 문서 JSON)·첨부 참조·제출 키, 수정은 공지 참조·버전.
- **내보내는 값:** 게시/수정된 공지·첨부 연결·전후 이력 또는 로그인 사용자에게 허용된 목록/본문. 제거한 첨부는 현재 연결만 해제하고 과거 자료 보존.
- **실패·금지:** BNOC 외 게시·첨부 소유/연결 오류·권한 밖 조회 거절. 게시물과 첨부 연결의 부분 성공 금지. 해당 공지의 기존 연결 첨부는 타 BNOC 업로드라도 유지 허용, 신규 임시 첨부만 현재 업로더 소유 검사. 임의 HTML·스크립트·원격 자원·허용 밖 구조·빈 서식·rich/평문 불일치 이중 원본 거절.
- **설계값·후속 조건:** 0.8 승인 서식 계약. 글자크기16/20/24px·색기본/#1d4ed8/#b91c1c/#166534·bold/underline/list allowlist. 평문1만자·문서JSON UTF-8 64KiB를 별도 검사. 기존 plain·첨부·타 BNOC 수정·이력·충돌 유지. bodyDocument={version:1,blocks:[...]}에서 paragraph/listItem·bullet/ordered 목록·text runs의 bold/underline/size/color만 허용하고 blocks/runs 각각1000개 이하·고정 깊이를 검사한다. rich 수정에서 문서 누락은 거절하고 plain 전환은 명시적 bodyDocument=null과 body가 있어야 한다. rich payload의 body를 함께 보내면 서버 계산값과 같아야 한다.
- **배정 기능:** SR-BE-003, SR-BE-019, SR-BE-027, SR-BE-028, SR-BE-029, SR-BE-030

### 화면의 API 호출 · `ApiClient`

- **실행 영역:** 프런트엔드

## 검토용 경계 통과 사례

1. **최초 배정/분류:** 상세는 일반 기본 초안 또는 저장된 현재 분류로 시작한다. ApiClient가 명시 general/urgent·요청 버전·제출키를 전달하고 서버가 BNOC·누락·현재 상태를 검사한다. 성공 뒤 저장 분류·부서를 읽기 상태로 표시하며 후보고는 미분류를 유지한다.
2. **부서 추가/반환 해제:** RequestCommands.addTeams와 WorkItemCommands.withdrawReturnedWork는 요청→작업 잠금·현재 권한/버전을 검사한다. 해결 이력을 지우지 않고 유효 작업·전체 상태·이력·알림을 함께 저장한다. 완료1+반환1의 해제는 전체 완료·요청자 알림이며 모두 해제는 미배정 대기·작업0·수정/추가 가능이다. 과거 BNOC 배정 이력·저장된 general/urgent가 없는 신규 요청의 추가는 거절한다. 완료가 먼저면 부서 추가를 거절한다.
3. **상태/집계/일정:** RequestStatusCalculator.summarizeEffectiveWorks를 명령·세 조회가 공유한다. 전체/우리 반 상태·현재/완료 반수·현재/과거 참여와 작업 건수는 구분한다. 미해결 반환은 남은 유효 작업이며 해결 반환은 현재 담당/일정/집계에서 제외한다.
4. **개인별 부서 관리:** 각 부서의 지정 개인은 개인 소속·departmentManager로 자기 명부/병력/야간만 수정한다. 비담당자/타 부서 쓰기는 거절하며 역할/소속 선택으로 권한을 만들지 않는다. 저장 현황과 편집 초안, 조회 부서/날짜 맥락을 구분한다.
5. **공지 서식:** OperationsView가 허용 문서 JSON을 payload로 보내고 DirectiveService가 검증·평문 계산·첨부/이력/버전을 함께 저장한다. 기존 plain 공지·다른 BNOC 수정·첨부 보존은 유지한다.
6. **공통 상단:** OperationsView는 ApiClient의 같은 종류별 캐시로 GPS/CPCON 문자/그래픽·독립 이상을 표시하고 선택한 종류의 별도 팝업을 연다. 시각은 화면에서 숨긴다. 새 알림 건수는 알림함 메뉴 배지에만 표시하고 BNOC 반환 수는 기존 미해결 업무로 유지한다. 알림을 확인해도 반환은 해결되지 않는다. expiresAt/serverNow와 경과시간으로 실패 후 오래된 정상 고정을 막는다.
7. **외부 인증/수집:** 대회 제공자는 고정 서버 설정으로 선택한다. 시작 브라우저 결합·단회 인증·실제 서버 세션/권한·종류별 GPS/CPCON 수집 경로를 유지하며 실제 공군 규격을 확보했다고 표현하지 않는다.

## 1. 설계 결론

### 1.1 채택 구조

인터넷에 정적 파일로 배포하는 브라우저 단일 페이지 애플리케이션(SPA)으로 만든다.

```text
합성 기준 데이터 ──> 초기화 모듈 ──> 세션 상태 저장소
                                      │
화면 ──명령──> 업무 흐름 모듈 ──새 상태──┤
  ▲                                   │
  └──── 화면용 조회값 <── 조회 모듈 <────┘

정적 빌드 결과 ──> HTTPS 웹 호스팅
```

- 브라우저 밖의 API, 백엔드, DB는 없다.
- 같은 탭의 현재 시연 세션에서만 변경 상태를 유지한다.
- 역할을 바꿔도 같은 세션 상태를 공유한다.
- 새로고침하면 검토된 합성 기준 데이터로 돌아간다.
- 화면은 업무 명령만 보내고 업무 상태를 직접 수정하지 않는다.
- 모든 업무 변경은 한 개의 업무 흐름 모듈을 통과한다.
- 조회·검색·집계는 상태를 바꾸지 않는 조회 모듈이 계산한다.
- 사용자 화면에는 데모 구현 한계를 노출하지 않는다.

각 모듈 내부가 실제로 어떤 클래스로 나뉘고 클래스끼리 무엇을 주고받는지는 4장에서 정의한다.

### 1.2 의도적으로 만들지 않는 것

- API 계층, HTTP 클라이언트, 서버, DB
- 저장소 인터페이스와 구현체 분리
- 범용 이벤트 버스, 플러그인 구조, 마이크로서비스
- 실제 파일 업로드와 파일 내용 보존
- 브라우저 재접속 뒤 데이터 복구
- 실제 인증·서버 권한·실시간 동시 수정

이 항목들은 현재 데모 합격 조건을 높이지 않는다. 운영 체계 개발을 시작할 때 별도 아키텍처로 다시 설계한다.

### 3.3 명령과 결과

화면 명령과 내부 업무 명령을 분리한다. 화면은 내부 ID를 알지 못한다.

```text
ViewCommand (M-06 → M-05)
- type: 실행할 행동
- operationId: 같은 제출을 식별하는 세션 내 값
- requestNumber: 기존 대상을 바꾸는 명령의 화면용 요청 번호
- workNumber: 기존 작업을 바꾸는 명령의 요청별 화면용 작업 참조값
- expectedRevision: 기존 주 대상을 바꾸는 명령에서 사용자가 화면으로 본 버전
- payload: 행동별 입력값

Command (M-05 → M-03, 내부 전용)
- type, operationId, expectedRevision, payload
- targetId: M-05가 현재 세션·requestNumber·workNumber로 해석한 내부 요청 또는 작업 식별값

내부 실행 입력
- state: 현재 AppState
- session: M-02가 보관한 현재 SessionContext
- command: M-05가 만든 내부 Command
- env: 현재시각·내부 식별값·화면용 요청 번호·작업 참조값 생성기와 내부 QA 실패 정책

CommandResult (M-03 → M-05, 내부 전용)
- 성공: ok, nextState, changedIds, replayed
- 실패: ok=false, 기존 state, errorCode, fieldErrors, latestValue

ViewCommandResult (M-05 → M-06)
- 성공: ok, replayed, 생성 명령이면 공개 requestNumber
- 실패: ok=false, errorCode, fieldErrors, refreshRequired
- 금지: AppState, changedIds, 원본 latestValue, 내부 요청·작업 ID
```

오류 코드는 다음으로 제한한다.

| 코드 | 뜻 | 상태 변경 |
| --- | --- | --- |
| `VALIDATION` | 필수값·형식·조건 오류 | 없음 |
| `FORBIDDEN` | 역할·소유·작업반 범위 위반 | 없음 |
| `INVALID_STATE` | 현재 상태에서 허용되지 않는 행동 | 없음 |
| `NOT_FOUND` | 대상이 없음 | 없음 |
| `CONFLICT` | `expectedRevision`이 최신값과 다름 | 없음, 최신값 반환 |
| `DUPLICATE_ACTION` | 같은 `operationId`를 다른 명령에 재사용 | 없음 |
| `SAVE_FAILED` | 사전 정의된 저장 실패 시나리오 | 없음 |

M-05는 `SessionContext.activeActorId + ViewCommand`로 명령 지문을 계산한다. 같은 행동자·같은 `operationId`·같은 명령 지문이 다시 들어오면 오류로 처리하지 않는다. 저장된 `OperationReceipt`로 최초 성공 여부와 생성 명령의 공개 `requestNumber`를 `replayed=true`와 함께 반환하고 상태·이력·알림은 바꾸지 않는다. 내부 `changedIds`는 화면에 반환하지 않는다. 역할 전환 뒤 다른 행동자가 같은 ID나 명령을 사용하면 영수증 내용을 반환하지 않고 `DUPLICATE_ACTION`으로 거절한다.

`ViewCommand.requestNumber`와 `expectedRevision`, 내부 `Command.targetId`는 생성 명령인 `createRequest`, `createAfterActionReport`에는 없다. 기존 요청을 바꾸는 명령에는 요청 번호와 revision이, 기존 작업을 바꾸는 명령에는 요청 번호·작업 참조값·revision이 필수다. `updateWork`와 `reassignReturnedWork`는 `requestNumber + workNumber`로 작업 하나를 해석한 뒤 현재 세션 소유권과 상태를 검사한다. 이 명령들이 함께 바꾸는 요청 종합 상태는 현재 최신 상태에서 다시 계산하며 별도 요청 revision을 잠그지 않는다.

### 4.3 M-02 역할 세션·접근 규칙

| 항목 | 계약 |
| --- | --- |
| 입력 | 합성 계정 목록, 선택할 `actorId`, 대상 요청·작업·화면 행동 |
| 행동 | 현재 `SessionContext`를 M-02 내부에 보관하고 `switchActor(actorId)`로 교체, 현재 역할·본인 소유·소속 작업반 검사, 허용 메뉴와 행동 계산. 업무 `AppState`는 변경하지 않음 |
| 출력 | 현재 `SessionContext`, 현재 `RoleContext`, 허용 여부, 허용 메뉴·행동 목록 |
| 실패 | 존재하지 않는 사용자 `NOT_FOUND`, 권한 밖 행동 `FORBIDDEN` |
| 테스트 | 요청자·BNOC·서로 다른 두 작업반의 조회·변경 허용표, 역할 전환 전후 같은 `AppState`, 명령 payload로 행동자를 바꿀 수 없음 |

#### `SessionManager` · 로그인 사용자 전환기

- 책임: 현재 `SessionContext`를 브라우저 메모리에 소유하고, 지금 누가 로그인해서 쓰는지와 역할을 바꾸면 무엇이 바뀌는지 계산한다. 화면은 이 값을 직접 주입·덮어쓸 수 없고 신청·작업 내용은 건드리지 않는다.
- 의존: 없음 (기반 로직)
- 관련 요구사항: SR-DEMO-003, SR-DEMO-004

| 메서드 | 설명 |
| --- | --- |
| `switchActor(actorId, accounts): SessionContext` | 존재하는 합성 계정으로 현재 로그인 사용자 바꾸기 |
| `getCurrentSession(): SessionContext` | M-02가 보관한 현재 세션 문맥 조회 |
| `getCurrentRoleContext(accounts): RoleContext` | 현재 세션으로 역할·권한 정리하기 — 일반·BNOC·작업반 중 무엇인지, 어느 메뉴가 보이는지 |

#### `AccessPolicy` · 권한 확인자

- 책임: 지금 로그인한 사람이 이 행동을 해도 되는지 판단한다. 화면 버튼을 숨기는 것과 별개로 실제 명령이 올 때마다 다시 확인한다.
- 의존: 없음 (기반 로직)
- 관련 요구사항: SR-DEMO-003, SR-DEMO-023, SR-DEMO-025

| 메서드 | 설명 |
| --- | --- |
| `canPerform(context, action, target?): boolean` | 신뢰된 현재 `RoleContext`로 행동 허용 여부 판단 — 화면 입력의 역할·행동자는 받지 않음 |

### 4.5 M-04 조회·화면용 계산

| 항목 | 계약 |
| --- | --- |
| 입력 | 읽기 전용 `AppState`, `SessionManager`가 현재 세션에서 만든 신뢰된 `RoleContext`, 적용된 검색·기간·상태·작업반·유형·위치·화면용 요청 번호 조건 |

| 실패 | 빌드 오류, 직접 경로 404, 정적 자산 누락, 브라우저 실행 실패를 배포 실패로 처리 |
| 테스트 | 로컬 생산 빌드, 공개 URL 직접 접속·새로고침, Chromium·Firefox 핵심 흐름, 실행 중 외부 요청·사용자 입력 로그 부재 |

M-07은 위 계약 형식만 다른 모듈과 같을 뿐, `AppState`도 `Command`도 다루지 않고 4.1~4.8의 런타임 클래스 의존관계 그래프에 전혀 참여하지 않는다. 빌드 시점에 한 번 실행되는 배포 파이프라인이라 M-01~M-06과 같은 급의 "모듈"로 번호를 매긴 것 자체가 재검토 대상이며, 이번 개정에서는 실행 클래스 목록에서 제외하고 하나의 별도 항목으로만 남긴다.

## 5. 업무 흐름 모듈의 행동 계약

각 행은 그대로 단위 테스트의 `입력 상태 → 행동 → 기대 결과`가 된다.

| --- | --- | --- | --- |

| `cancelRequest` | 현재 요청자 세션, 본인 화면용 요청 번호, `expectedRevision` | 요청 `취소`, 취소 이력, 계정 연결 요청자의 상태 알림; 관련 작업 조작 불가 | 타인 요청, 이미 취소, 충돌 |

| `createAfterActionReport` | 현재 작업반 세션, 작업 완료 확인값, 실제 요청자 자유 텍스트, 요청 필수값, 선택 완료 메모 | 완료 확인 시 내부 식별값과 중복 없는 `101` 형식 요청 번호를 가진 요청, `101-1` 작업 참조값과 현재 세션 작업반의 `origin=after-action` 완료 작업, 자동 등록·완료정보, 이력, BNOC 알림 | 필수값 누락, 작업반·행동자 덮어쓰기, 요청 번호·작업 참조값 중복, 일부 생성 실패, 중복 제출. 미완료이면 이 명령을 보내지 않음 |

`문서 대기`에는 별도 해제 행동이 없다. `assignTeams` 성공이 `문서 대기 → 배정` 전이를 만든다.

선조치 후보고 화면에서 사용자가 작업 미완료를 선택하면 M-06은 후보고 객체를 만들지 않고 입력값을 UI 상태에 유지한다. 작업반 역할의 일반 요청 제출은 `FORBIDDEN`이다. 사용자가 BNOC 역할로 전환하면 유지된 입력을 BNOC 대리 등록 폼에 채우며, 제출 뒤에는 `createRequest` 계약을 따른다.

반환 때문에 요청이 `대기`가 됐으면 `moveToDocumentWaiting`과 최초 배정용 `assignTeams`를 표시하거나 실행하지 않는다. 반환 문제는 반드시 `reassignReturnedWork`로 해결한다. 직접 명령 호출도 `INVALID_STATE`로 거절한다.

### 5.1 작업 상태 전이 계약

| 현재 상태 | 저장 가능한 다음 상태 | 상태별 현재정보 처리 |
| --- | --- | --- |
| `배정` | `배정`, `작업 중`, `완료`, 사유 있는 `반환` | 완료 진입 때 새 완료정보 생성. 반환 진입 때 사유 저장 |
| `작업 중` | `배정`, `작업 중`, `완료`, 사유 있는 `반환` | 완료 진입 때 새 완료정보 생성. 반환 진입 때 사유 저장 |
| `완료` | `배정`, `작업 중`, `완료`, 사유 있는 `반환` | 완료를 떠나면 현재 완료정보 제거. 과거 완료 이력은 유지 |
| 미해결 `반환` | `배정`, `작업 중`, `완료`, `반환` | 반환을 떠나면 현재 반환 사유 제거. 과거 반환 이력은 유지 |

같은 상태 저장은 일정·메모·상태별 입력 변경 때만 허용하고 변화가 없으면 중복 결과를 만들지 않는다. 모든 정·역방향 변경은 `revision` 증가, 변경 전후 이력, 요청 상태 재계산을 함께 수행한다. 재배정으로 `resolvedByWorkItemIds`가 생긴 기존 반환 작업, 취소 요청의 작업, `origin=after-action` 완료 작업은 모든 상태 변경을 거절한다. 상태 선택은 UI 임시값이며 `저장` 전에는 명령을 보내지 않는다.

### 5.2 요청 상태 계산 계약

아래에서 처음 일치하는 상태를 결과로 사용한다.

1. 요청이 취소됐으면 `취소`.
2. 현재 요청 상태가 `문서 대기`면 `문서 대기`.
3. 유효 작업 중 하나라도 `작업 중`이면 `작업 중`.
4. `resolvedByWorkItemIds`가 비어 있는 반환 작업이 있고 진행 작업이 없으면 `대기`.
5. 유효 작업이 하나 이상이고, 해결되지 않은 반환이 없으며, 모든 유효 작업이 `완료`면 `완료`.
6. 유효 작업이 하나 이상이면 `배정`.
7. 그 외에는 `대기`.

유효 작업은 상태가 `반환`이 아닌 관련 작업이다. 재배정된 새 작업은 유효하며, 새 작업으로 해결된 기존 반환 작업은 계산에서 제외한다. 정·역방향 작업 상태 저장 뒤마다 최신 작업 집합으로 다시 계산한다. 상태 계산 함수 입력은 `Request + 관련 WorkItem[]`, 출력은 요청 상태 한 값이다. 입력 객체는 수정하지 않는다. 관련 작업이 없는 신규 요청은 반드시 `대기`다.

### 5.3 알림 생성 계약

| 사건 | 수신자 | 생성 조건 |
| --- | --- | --- |
| 요청 등록 | BNOC | 등록 성공 시 1개 |
| `문서 대기` 전이 | 계정 연결 요청자 | 요청 상태가 실제 `문서 대기`로 바뀐 경우 |
| 최초 배정·재배정 | 선택된 각 작업반, 계정 연결 요청자 | 작업반별 1개, 요청 상태가 실제 `배정`으로 바뀌면 요청자 1개 |
| 작업 상태 정·역방향 변경 | 계정 연결 요청자 | 요청 종합 상태가 실제 `배정`·`작업 중`·`완료` 중 다른 값으로 바뀐 경우만 1개 |
| 작업 반환·반환 정정 | BNOC | 반환 진입 또는 반환 해제 성공 시 1개. 반환 때문에 생긴 `대기`는 요청자 알림 없음 |
| 요청 취소 | 계정 연결 요청자 | 요청 상태가 실제 `취소`로 바뀐 경우 1개 |
| 선조치 후보고 | BNOC | 후보고 전체 성공 시 1개 |

`requesterActorId`가 없는 BNOC 대리 등록·선조치 후보고 요청은 체계 내부 알림 수신 계정과 본인 조회·수정·취소 대상을 추정하지 않는다. BNOC와 배정된 작업반만 업무 권한에 따라 조회·처리한다. 이는 자유 텍스트 요청자를 계정과 연결하지 않는 `DEC-026`의 직접 결과다.

## 6. 조회 행동 계약

| `getRequestList` | 신뢰된 현재 세션, 적용 검색조건 | 권한 범위 안의 요청 요약 목록 | 요청자는 본인만, 작업반은 자기 반 배정 건만, BNOC는 전체. 내부 식별값 제외 |

`RequestListAndSearch`는 임시 검색조건을 UI 로컬 상태로 유지한다. 입력·선택 변경은 `searchRequests`를 호출하지 않는다. `검색` 버튼 또는 검색 입력의 Enter는 임시 조건 전체를 적용 조건으로 복사한 뒤 `searchRequests`를 한 번 호출한다. `초기화`는 두 조건을 비우고 기본 목록을 한 번 호출한다. 이 계약은 메인 신청 목록에만 적용하며 `BnocOverviewView`의 현황 집계 필터는 이번 변경 범위가 아니다.

화면용 조회 모델과 사용자 노출 경로는 `requestNumber`와 필요할 때 `workNumber`만 사용한다. 내부 요청·작업 ID는 `AppState` 참조와 명령 처리 안에서만 사용하며 URL, DOM 텍스트·속성, 접근성 이름, 알림·이력 문구, 복사 가능한 텍스트에 넣지 않는다. 화면용 요청 번호·작업 참조값을 내부 ID로 해석하는 책임은 `RequestQueryService`와 `SessionStateStore`가 가진다. 작업 명령은 `requestNumber + workNumber + revision`으로 작업 하나를 찾은 뒤 현재 세션의 역할·소속 작업반 권한을 검사한다. 호출자는 역할·행동자·내부 대상 ID를 전달할 수 없다.

이력 조회는 원본 `HistoryEntry`를 화면에 직접 반환하지 않는다.

| 역할 | 이력에 표시 | 제거 |
| --- | --- | --- |
| 요청자 | 공개 상태, 일정, 요청자가 수정 가능한 요청 항목의 변경 시각과 결과 | 작업반 내부 메모, 반환 내부정보, 다른 사람 연락처·식별값, 원본 before/after 객체 |

### 8.2 유스케이스 연결 테스트

브라우저 테스트는 모듈을 다시 세밀하게 검사하지 않는다. 다음 연결만 확인한다.

1. 요청자 등록과 선조치 후보고에서 `101` 형식 요청 번호 생성, 목록·상세·알림·이력·검색에서 내부 ID 비노출.
2. 요청자 등록 → BNOC 확인·복수 배정 → 두 작업반 독립 처리 → 요청자가 완료 상태 조회.
3. `대기 → 문서 대기 → 배정`과 `문서 대기 → 취소`; 별도 해제 조작 부재.
4. 작업 상태 `배정 → 완료 → 작업 중 → 배정`, `작업 중 → 반환 → 작업 중` 정정과 완료정보·반환사유·이력·알림·요청 종합 상태 일치.
5. 작업 반환 → BNOC 재배정 → 기존 반환 작업 잠금 → 새 작업 완료 → 종합 상태 완료.
6. 요청 수정 가능·불가 경계와 언제든 취소.
7. 작업반 선조치 후보고의 요청·완료 작업·이력·알림 동시 생성과 완료 상태 변경 거절.
8. 검색조건 입력 중 결과 불변 → `검색` 또는 Enter 1회 뒤 전체 조건 적용 → 0건 조건 유지. 일정·현황·역할별 비노출.
9. 저장 실패·빠른 이중 제출·충돌에서 기존 상태와 입력 유지.
10. 390·1280·1440px 및 Chromium·Firefox.
11. 공개 HTTPS URL 직접 접속과 새로고침 복구.

## 9. 개발명세서에 넘길 내용

0.1 버전은 아래 항목을 전부 "이 문서 승인 뒤" 미정으로 남겼다. 이번 개정에서 4장의 클래스 분해가 화면·컴포넌트 목록과 각 `Command`·조회 함수의 필드 형식 상당 부분을 이미 채웠으므로, [개발 명세서](개발명세서.md#demo-contract)에 다음과 같이 구체화했다.

- 프론트엔드 기술과 정확한 버전 → 05번 문서 1절
- 실제 폴더·파일 구조와 데이터 타입 선언 → 05번 문서 2, 3절
- 각 화면·경로·컴포넌트 목록 → 05번 문서 2절 (= 4.7절 화면 클래스 9개)
- 각 `Command`와 조회 함수의 정확한 필드 형식 → 05번 문서 3절
- 테스트 파일과 `SR-DEMO`별 테스트 이름 → 05번 문서 4절
- 합성 기준 데이터 목록과 검토 방법 → 05번 문서 5절
- 빌드·검사·배포 명령과 호스팅 공급자 → 05번 문서 6절
- 구현 에이전트의 수직 슬라이스 순서와 완료 조건 → 05번 문서 7절

## 10. 사용자 검토 항목

1. 내부 ID를 유지하되 화면에는 `101` 형식 요청 번호만 노출한다(승인 완료).
2. 명시적 검색 실행은 메인 신청 목록에만 적용하고 BNOC 현황 필터는 유지하는가.
3. 일반 배정 작업의 네 상태를 자유롭게 정정하되 취소·재배정 완료·선조치 후보고 작업은 잠그는가.
4. 완료를 떠날 때 현재 완료정보, 반환을 떠날 때 현재 반환 사유를 제거하고 과거값은 이력에 보존하는가.
5. 5절 행동별 입력·출력·실패와 8절 테스트가 업무 의도에 맞는가.
6. 이 변경안을 승인하고 [개발 명세서](개발명세서.md#demo-contract)의 구현 순서로 넘어가도 되는가.
