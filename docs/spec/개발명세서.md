## 사용성 개선의 동작·저장·전송 계약

### 후속 사용성 계약 · 2026-10-20

2026-10-20 당시 화면·조회 DTO 결정이다. 일정 카드의 연락처·정보 표시 범위는 아래 2026-10-21 DEC-034가 대체한다. 요청 내용 예문·배정 후 목록 복귀·배정 조작별 카드·공유 목록의 전화번호 예외·작업 상태 표시명 결정은 계속 유효하다. placeholder는 저장하지 않으며 사용자가 입력·분류를 바꾸어도 작성한 값을 변경하지 않는다. 공유 목록은 기존 구조화 필드와 요청자 군내전화번호를 제공하고 상세 권한과 나머지 제외 필드를 유지한다. 작업반별 작업 상태의 내부 `WORKING`/`작업 중` 값은 그대로 저장·전달·집계하고 사용자 상태 배지·선택값·필터만 `작업 준비`로 매핑한다. 요청 종합 상태 `작업 중` 표기는 유지한다.

### 일정·선조치 후보고 저장·전송 계약 · 2026-10-21

요청의 희망 일정은 선택 `SchedulePreference[]`로 표현한다. 항목은 `rank: 1|2`, `date: YYYY-MM-DD`, `period: AM|PM`이며 시각은 받지 않는다. 둘 다 비워 둘 수 있고 2지망만 입력하는 것은 거절한다. 실제 작업 일정과 독립이며 BNOC 배정 시각에 복사하지 않는다. 기존 정확 희망 시각은 Asia/Seoul에서 기존 날짜와 오전/오후를 계산해 1지망으로 옮기고 2지망은 비운다. 원래 정확 시각은 이관 이력/보존 원본에 남겨 정보 손실을 막는다.

실제 작업 일정은 `WorkScheduleInterval[]`이며 각 구간은 `[startsAt, endsAt)` UTC ISO 8601 시각이다. 신규 입력은 Asia/Seoul 달력의 정시 경계만 허용하고 1시간 슬롯 하나 이상을 고른다. 연속 선택은 하나의 구간으로 합칠 수 있고 비연속 구간 여러 개도 허용한다. 하루는 00:00~24:00 전체를 제공한다. `previousSchedule`도 여러 구간으로 보존하며 반환 때 현재 구간 전체를 이전 계획으로 옮긴다. 기존 `schedule`/`previous_schedule`의 정확 시각은 분·초를 반올림하지 않고 시작값으로 유지하고 끝을 시작+1시간으로 변환한다. 반환 전 일정 재사용은 모든 원래 구간을 재사용한다.

선조치 후보고의 실제 시작 시각은 기존 후보고 이력 기록을 원본으로 유지하고 달력 조회용으로 정확한 값에 접근한다. 실제 시작 시각이 속한 정시 1시간 셀에 완료 기록으로 나타내되 예정 구간 1시간짜리 작업으로 변환하지 않는다. 전체 공유 작업의 할당·완료 합계에는 후보고 완료 작업을 한 번 포함하고 `after-action` 출처는 유지한다. 후보고 전용 하위 건수/필터는 포함된 작업의 부분집합이며 합계에 다시 더하지 않는다. 남은 작업은 미완료 일반·긴급 BNOC 배정 작업만 포함한다.

`GET /api/schedule`은 허용된 조회 권한에서 작업 번호·반·시간 구간 또는 후보고 실제 시작 시각·작업 상태·위치·작업 메모·`request.requestNumber`만 투영한다. `request.detail`, 요청 상세 요약, 전화번호는 제외한다. `location`은 이 자기 반/BNOC 일정 응답에만 추가하고 `GET /api/work-overview`에는 추가하지 않는다. 프런트 일정은 선택 기간과 겹치는 같은 작업을 한 카드로만 표시하고 가장 이른 겹침 구간 시작 시각으로 배치·정렬한다. 카드에는 그 기간과 겹치는 작업의 모든 구간을 함께 보이며, 계획 구간이 없는 완료 작업은 완료 시각이 속한 시간 칸에 배치하되 완료 날짜·시각 문자열을 카드에 반복하지 않는다. 완료 일반 작업 카드에 완료 시각을 덧붙이지 않고 예정/완료 카드는 서로 다른 색으로 구분하며 작업 상태 문구를 유지한다. 후보고는 실제 시작 시각을 기준으로 한 번만 표시하고 정확한 실제 시작 시각을 보존한다. 기간 시작 전에 시작해 범위에 이어진 구간은 기간 안에서 처음 보이는 겹침 시각에 배치하고 원래 시작을 카드 텍스트에 보존한다. 일정 카드 전체를 작업 상세 링크로 만들며 키보드 초점/Enter를 지원하고 이동 시 서버 상세 권한을 다시 검사한다. 전화번호는 이전 DEC-033에 따라 공유 작업 현황에서만 계속 보인다.

DB의 단일 `requested_schedule`, `schedule`, `previous_schedule` 값은 두 희망 지망과 여러 작업 시간 구간을 표현할 수 없으므로 정규화한 선호 행(요청+순위)과 일정 구간 행(작업+현재/이전 구분+시작/끝)으로 바꾸는 마이그레이션이 필요하다. 기존 값을 손실 없이 변환하고 변환 전후 행 수·시간값을 대조한다. 빈 DB 초기화와 실제 기존 자료를 포함한 DB 모두에서 마이그레이션·재시작 보존을 검증한다. 제품 구현 승인 전에는 코드·DB를 변경하지 않는다.

### 유효 작업·배정 해소·조회의 공통 정의

작업 상태는 배정·작업 중·완료·반환 네 개를 유지한다. 별도로 `resolution.kind`를 `open`, `reassigned`, `withdrawn`으로 구분하고 해소 사유·서버 시각·행동자·대체 작업 번호 목록을 보존한다. 이전 `resolvedBy`가 비었는지만으로 해소를 판단하지 않는다. 기존 해소 이력은 재배정으로 이관하고 이력/작업을 삭제하지 않는다.

취소되지 않은 요청에서 `resolution.kind=open`인 작업이 현재 유효 작업이다. 미해결 반환은 유효하며 남은 작업에 포함한다. 해소된 작업만 담당/완료 분모·현재 부서 조건·작업 집계에서 제외한다. 후보고 완료는 전체 할당·완료 합계와 부서별 작업 수에 한 번 포함하되 출처별 부분 집합으로 구분한다. 여기서 BNOC 배정 요청은 일반·긴급 모두를 뜻하며 우선순위 `general`과 동의어가 아니다.

`RequestStatusCalculator.summarizeEffectiveWorks`가 같은 조회 스냅샷의 현재 작업·담당 부서·완료 부서·미해결 반환·전체 상태를 계산한다. 신청 목록·BNOC 현황/일정·공유 집계는 이 정의를 함께 사용한다. 반수는 부서를 중복 제거하고 같은 부서의 유효 작업이 여러 개면 모두 완료여야 완료 반으로 센다. 기존 중복 자료를 조용히 삭제/병합하지 않는다.

| 상태 변경 사례 | 전체·집계·권한의 결과 |
| --- | --- |
| 한 반 완료·다른 반 미해결 반환 | 완료 아님. 반환은 남은 작업이며 BNOC 반환 대기에 포함 |
| 위 반환 배정 해제 | 유효 작업1·완료1·남은0·반환 대기0·전체 완료. 계정 연결 요청자에게 기존 완료 알림 |
| 마지막 유효 반환 배정 해제 | 전체 대기·미배정 요청1·할당/완료/남은 작업0·반환 대기0·현재 예정0. 본인 수정 허용, 취소 아님 |
| 해제 이력만 남은 요청에 부서 추가 | 기존 분류/이력 유지, 새 작업은 과거 최대 순번 다음 번호·새 서버 배정 시각·일정 미정 |
| 추가와 마지막 작업 완료의 경합 | 요청 잠금 후 최신 상태 재검사. 완료 선행이면 추가 거절, 추가 선행이면 새 작업까지 완료해야 전체 완료 |

`addTeams`는 과거 BNOC 배정 이력과 저장된 general/urgent가 있는 미완료·비취소·완료 후보고 아닌 요청의 현재 미담당 부서를 추가한다. 신규 미배정·분류 null 요청은 거절하여 최초 분류를 우회하지 못하게 한다. 유효 작업0개이지만 과거 배정 이력이 있는 대기도 포함한다. payload는 중복 없는 `teamIds`만, 주 대상은 요청 버전이다. 기존 분류를 변경하지 않는다. 최초 배정은 계속 `assignTeams`이며 명시적 분류가 필요하다. 부서 추가·재배정·해제는 요청 잠금 후 상태와 대상 버전을 다시 검사하고 업무/이력/알림/영수증을 함께 저장한다. 최초/추가/재배정/배정 해제처럼 배정 구조가 바뀌면 전체 상태가 같아도 요청 버전을 증가시킨다. 다른 반 작업 저장에는 유효한 주 대상 작업 버전만 요구하고 요청 버전까지 강제하지 않는다.

`withdrawReturnedWork`는 BNOC가 미해결 반환의 배정만 해제한다. 주 대상은 작업 버전, payload는 빈 객체이며 서버가 “해당 부서 작업 불필요”라는 고정 사유를 기록한다. 새 필수 사유 입력은 없다. 원래 작업·반환 사유·계획·인원 참조·이력·과거 조회 권한은 보존한다. 진행 중/완료 작업의 소급 삭제나 완료 요청 재개·취소 요청 변경·후보고 조정은 허용하지 않는다. 반환 정정/재배정/해제 중 하나만 성공한다. 재배정과 추가는 이미 현재 담당인 반으로 중복 생성하지 않는다.

반환 상태로 전환하는 저장에서만 기존 `scheduleIntervals` 전체를 `previousScheduleIntervals`와 이력에 보존하고 현재 구간을 비운다. 이미 반환된 작업의 사유·메모만 저장할 때 previousSchedule을 비우지 않는다. 반환 정정 시 작업반이 이전 구간 전부 재사용 또는 미정을 선택한다. 현재 예정/미정 실행 목록은 유효 작업 중 배정·작업 중만 대상으로 한다. 완료 기록의 계획 구간과 실제 `completedAt`은 데이터로 구분해 보존하되, 완료 일반 작업 카드에는 계획 구간과 완료 날짜·시각을 중복 표시하지 않는다. 계획 구간이 없는 완료 카드도 시간 칸으로 위치만 나타내고 시간 문자열은 생략한다. 반환 전 계획·대체/해제 이력은 예정 건수에 포함하지 않는다. 기존 작업 시각의 분·초를 그대로 시작값으로 두고 1시간 길이로 해석한다. 신규 구간의 시작 시각은 정시만 허용한다.

### 목록·검색·개인별 현황 관리

요청 요약의 `status`는 전체 상태다. 추가 조회값은 `myTeamWorkStatus`, `participation`(current/past/none), `currentDepartmentCount`, `completedDepartmentCount`, `departmentProgress`(부서·작업 상태 요약)다. 후보고 출처를 보존해 표시하되 전체 공유 할당·완료 합계에는 한 번 포함한다. 내부 메모·인원·연락처를 새 요약에 추가하지 않는다. 작업반은 자기 반 상태를 우선, 과거만 참여했으면 현재 담당 아님을 표시한다. 내 신청은 동일 본인 요청자 열을 생략한다.

검색 `status`는 전체 상태, 작업반 전용 `myTeamStatus`는 자기 현재 유효 작업 상태다. `participation=current|past|all`로 자기 반의 현재/과거 참여를 구분하며 관련 신청의 기본은 all이다. BNOC가 부서 조건을 쓸 때 기본은 현재 담당 기준이다. 과거 참여 조회는 별도 선택한다. 공유 현황은 항상 현재 유효 작업 기준이고 과거 이력 조건을 섞지 않는다. 지원하지 않는 역할의 자기 반 조건은 거절한다. 버튼/Enter·초기화 한 번과 BNOC 빠른 필터의 기존 시점은 유지한다.

현황 관리자는 각 부서 지정 개인의 인증 식별자·소속 부서·`departmentManager` 권한으로 표현한다. `role=team`이나 BNOC 소속만으로 이 권한을 자동 부여하지 않는다. 관리 권한만으로 작업 수행/배정 권한을 얻지 않고 별도 겸임은 허용한다. 초기 BNOC 범용 담당자와 모든 작업반 일괄 관리자 설정은 정정 대상이며 신규 구성의 기본값은 담당 권한 없음이다. 과거 계정/행동 이력을 삭제하거나 다른 사람에게 재연결하지 않는다. 실제 SSO 규격은 후속이며 화면은 소속·허용 담당 범위만 표시한다. 비담당자의 자기 부서 쓰기와 담당자의 타 부서 쓰기를 서버가 거절한다.

### 서식 공지

기존 `body`는 일반 텍스트다. 선택 `bodyDocument`는 `{version:1,blocks:[...]}` 구조이며 각 블록은 paragraph/listItem, listItem의 목록은 bullet/ordered, 내용은 text 문자열과 bold/underline, size=16/20/24, color=기본/#1d4ed8/#b91c1c/#166534만 허용한 runs다. 임의 HTML/CSS·스크립트·링크/원격 자원·알 수 없는 속성을 받지 않는다. 붙여넣기는 이 구조로 정규화한다. 이는 저장용 기술 선택이며 군 외부 규격이 아니다.

`bodyDocument`가 있으면 서버가 본문 문자열을 계산하고 함께 저장한다. 별도 `body`도 보냈다면 계산값과 일치해야 한다. 본문은 공백만 있는 문서를 거절하며 기존 10,000자 제한, 구조화 문서는 UTF-8 64KiB 제한을 별도로 적용한다. JSON 깊이는 고정 구조이고 blocks/runs 각각 1,000개 이하다. 일반 텍스트 공지는 `bodyDocument=null`로 기존 줄바꿈을 보존한다. 서식 공지 수정 시 문서가 누락되면 서식 소실을 막기 위해 거절하고, 일반 텍스트 전환은 명시적 null과 body를 보낸 경우만 처리한다. 첨부·공동 수정·공지 버전·전후 이력/제거 파일 보존은 동일하다. UI 편집기와 읽기 화면은 같은 허용 구조를 렌더링한다.

### 공통 상단·알림 항목별 확인

로그인 중 공통 상단은 GPS/CPCON의 작은 단계 그래픽·문자·기준시각과 조회/수집 이상을 항상 표시한다. 상단과 상세는 한 조회 상태를 공유하며 종류별 수집 실패는 독립이다. 응답의 `expiresAt`, `serverNow`와 수신 이후 경과시간으로 오래됨을 판단한다. API 실패 시 마지막 값은 남기되 갱신 확인 불가를 표시하고 정상 표시를 유지하지 않는다. 로그아웃/사용자 변경은 캐시를 비우며 숨긴 화면 복귀 시 재조회한다. 일반 수집/화면 갱신은 30초, 실제 외부 정보원·단계 의미는 기존 계약을 유지한다.

BNOC 반환 처리 대기는 `GET /api/work-overview?bucket=returned&size=1`의 현재 필터 없는 returned 건수로 조회한다. 알림 확인 여부와 독립이며 기존 수신 알림을 지워 해소하지 않는다. 새 알림은 `GET /api/notifications/unseen`이 반환하는 본인 수신·현재 조회 허용 사건의 is_read=false 건수다. 알림 목록에는 상태 갱신용 notificationId를 포함하되 화면 문구·경로에는 표시하지 않는다.

`POST /api/commands`의 `markNotificationsSeen`은 payload.notificationIds(문자열 배열 1~100개, 서버 중복 제거)에 실제 화면에 표시한 항목만 담는다. operationId는 필수이고 expectedRevision은 불필요하다. 서버는 모든 ID의 본인 수신·현재 조회 권한을 먼저 검사하며 다른/접근 불가 ID가 섞이면 전체 거절한다. 기존 is_read를 각 항목별 false→true로만 갱신하고 재시도·동시 확인은 같은 결과를 유지한다. 커서나 최대 번호로 이전 전체를 확인하지 않는다.

최신20개를 읽어도 과거 미표시 항목은 미확인이다. 화면 확인 중 새로 도착하거나 낮은 번호로 늦게 커밋된 알림도 ID 목록에 없으면 미확인으로 남는다. 확인 저장과 영수증은 함께 커밋한다. HistoryAndNotificationQueryService와 TransactionStore가 처리하며 NotificationRules의 사건 수신자 계산은 유지한다. 공지 읽음 확인·미확인자 집계·업무 자동 처리는 추가하지 않는다.

아래 기존 계약에서 위 변경 대상 외의 업무·인증·기술 설정·보존 조건은 유지한다. 0.8 구현은 완료했으며 합격 기준과 실제 실행 결과는 구분해 §9 및 연결된 검증 기록에 남긴다.

**2026-10-14 PC 전용 완성도 개선 승인:** 모바일 UI·전용 meta viewport·표 카드/data-label·작은 화면 스타일/검수를 제거한다. 현재 제품과 설계 웹의 검수 너비는 1280·1440이다. 기존 업무 서버·DB·API 필수값·권한·이력/영수증은 유지하며 화면의 필드 오류 매핑/첫 오류 초점·저장/미저장 피드백·조회 성공 조건/시각·요청/작업 단위·목록/선택 입력 배치를 개선한다. 이전 390 실행 결과는 역사 증거이며 현재 지원으로 간주하지 않는다.

## 백엔드 계약

**설계 0.7 · 2026-10-13 구현 재개 승인.** 설계 미결을 구현 승인 뒤 질문한 순서 오류를 바로잡기 위해 사용자 지시로 기획·설계에 복귀했다. 기존 구체 제안인 현재 작업 집계 산식·공유 목록 허용 항목·배정 시각 서버 기록·공지 전체 로그인 조회와 기존 업무 결정은 보존한다. 답변을 문서·아키텍처 웹·API 계약에 연결했고 사용자가 이 설계대로 구현하도록 승인했다. 이 계약대로 구현했으며 실제 실행 결과·접속 주소·미실행 범위는 [개발 진행](../records/개발진행.md)에 연결한다. 문서 작성만으로 완료를 판정하지 않는다.

**당시 확정한 업무 결정:** 배정 후 일반/긴급은 BNOC가 정정할 수 있고 반환 재배정은 기존 분류를 유지한다. 완료 후보고는 BNOC 승인 없이 미분류로 등록하고 BNOC가 사후 분류한다. 요청 내용이 작업지시이며 작업반이 자기 반 명부에서 담당 인원을 선택한다. 각 부서 담당자가 자기 부서 명부와 병력·야간 현황을 관리한다. 반장 지정은 추가하지 않는다. 병력은 선택 날짜, 야간은 시작일 기준이며 자기 부서 과거 입력/수정도 허용한다. 모든 유효 작업이 현재 배정이면 본인 비취소 요청 수정 가능. GPS/CPCON은 모든 로그인 조회, 공지 전체 로그인 조회 유지·모든 BNOC 계정 수정이다. 게시 종료·숨김·미완료 별도 접수/BNOC 전달은 만들지 않는다. 이 결정은 아래 계약에 반영됐고 2026-10-17 사용성 개선은 이후 별도 승인으로 구현·검증했다.

**고도화 유예:** 연결부 교체 시험·인터넷 없는 환경 설치·백업/복원·업데이트·운영 인수는 후속 백엔드 고도화에서 다룬다. 외부 연결/업무 처리와 환경별 설정 분리, 실제 저장·재시작 보존은 이번 기본 구현에 포함한다.

**2026-10-14 공개 접속 정정:** 사용자 “장난하니? 로컬?”을 공개 HTTPS 접속 요구로 반영한다. 우선 별도 대회 시연 서버를 HTTPS 터널로 연결하며 상시 호스팅으로 표시하지 않는다. 브라우저 인증은 `BNOC_PUBLIC_URL` Origin의 정확한 `GET/POST /identity`만 업무 서버가 loopback 모의 제공자로 전달한다. 서버의 `BNOC_PROVIDER_URL`은 비공개 loopback 검증·수집 주소로 유지한다. `/identity/verify`, `/identity/issue`, `/control`, `/feeds/*`는 공개하지 않는다. 전달할 URL을 요청의 Host나 사용자 입력으로 만들지 않으며 공개 HTTPS에서는 세션 쿠키 Secure·HttpOnly·SameSite=Lax와 기존 Origin/CSRF 검사를 유지한다. 공개 시연 DB·계정·첨부·모의 제공자는 8081 제품·8083 검증과 분리한다. 실제 인명·운영 자료·기존 DB·파일은 공개 서버로 옮기지 않는다. 별도 호스팅 계정 연결 전에는 상시 운영 미완료다.

공개 `/identity`의 POST는 서비스 Origin과 일치하는 `application/x-www-form-urlencoded` 폼만 받으며 본문은 64KiB 이하다. 전달 대상은 고정 `/identity`이고 요청 Cookie·X-Mock-Key는 전달하지 않는다. 모의 제공자의 응답은 Content-Type·Content-Security-Policy·Cache-Control·X-Content-Type-Options만 보존한다. 제공자 연결 실패는 503으로 안내한다. 기존 세션 생성과 확인표 검증은 `/api/auth/start`·`/api/auth/complete`를 그대로 사용한다.

## 1. 현재 구현과 이식 경계

웹 데모 기준선은 역할별 `App.tsx`와 `store/sessionStateStore.mjs`의 메모리 저장, `workflow/`의 요청·작업·후보고 명령, 상태 계산·권한·알림 규칙과 `query/` 조회였다. 현재 App은 `ApiClient`를 호출하고 서버가 업무 규칙과 실제 저장을 처리한다. 기존 메모리 모듈은 회귀 검사로 보존하며 현재 화면의 실행 경로가 아니다. 다른 옛 상태 체계인 `frontend/src/domain/workflow.mjs`도 이식 대상이 아니다.

| 기존 데모 책임 | 서버 구현 책임 | 유지할 의미 |
| --- | --- | --- |
| `SessionManager`·`AccessPolicy` | SSO 검증과 서버 세션·권한 확인 | 화면이 보낸 역할·행동자를 신뢰하지 않음 |
| `RequestCommands` | 요청 생성·수정·취소·문서 대기·배정·재배정 서비스 | 기존 주체·필수값·상태 전이, 최신 사용자 배정 입력 |
| `WorkItemCommands` | 자기 작업반의 작업·일정·상태 정정 서비스 | 일정 미정·명시적 저장·4상태·반환/완료 규칙 |
| `AfterActionReportCommand` | 요청·완료 작업 동시 생성 | 완료 후보고만, 별도 승인 없음 |
| `RequestStatusCalculator`·`NotificationRules` | 서버 업무 규칙으로 이전 | 전체 상태 계산·이벤트별 수신 조건 유지 |
| `SessionStateStore` | 명령 처리·DB 저장·중복 영수증·변경 버전 관리 | 한 명령이 부분 저장되지 않음 |
| `query/` | 역할별 정비 상세 응답과 공유 현황 응답 분리 | 정비 상세의 본인/자기 반/BNOC 범위 유지, 공유 조회는 새 결정과 허용 필드 적용 |
| 화면 `run/dispatch` | 비동기 API 호출과 조회 갱신 | 입력 유지·검색 시점·성공 후 갱신 |

작업 현황은 사용자 결정에 따라 기존 요청·작업을 바탕으로 집계한다. 집계 산식은 [인터랙션 §9](유스케이스.md#9-부대-운영-화면)의 설계 0.6에서 승인된 현재 상태 집계안이다. 작업 건수에서 장비 가용 상태를 생성하지 않는다. 병력·야간 근무·GPS·CPCON·지시는 각각의 입력 계약에 따라 다룬다.

## 2. 시스템 구성 제안

기존 React 화면, 하나의 서버 애플리케이션, 트랜잭션을 지원하는 관계형 저장소, 권한 검사 후 접근하는 첨부 저장소를 출발안으로 한다. 업무 서비스는 단일 서버로 유지한다. 대회용 외부 대체를 위해 별도 모의 서버 하나에 인증·GPS/CPCON 제공 모듈을 둔다. 추가 업무 서버·이벤트 플랫폼·자동 편성 엔진은 도입하지 않는다.

대회 기술안은 Java 17·Spring Boot MVC 4.1.1·Kotlin 2.3.20·Gradle 9.3.0·MySQL 8.4 LTS와 비공개 로컬 파일 저장이다. 단일 업무 JAR에서 화면과 API를 제공하고 모의 서버를 별도로 실행한다. [기술 선택 근거](#technology)와 [기술 설계값](#technical-settings)을 함께 검토한다. 새 선택안이며 폐기된 서버 복구가 아니다. 실제 공군 실행환경 호환과 공개 백엔드 배포는 별도 증거가 필요하다.

SSO는 외부 인증 경계다. 대회에는 실제 연결 없이 모의 제공자를 사용하며 아래에 시연 연결 계약을 정한다. 실제 공군 규격·로그아웃은 후속 실연동 때 별도로 구현·검증한다. 대회 세션 정책은 실제 규격 확보를 기다리지 않고 설계할 수 있다. SSO 식별자와 서비스 내 역할·작업반 권한을 분리하고, 매 요청에서 최신 서비스 권한을 적용하는 안이다. 최초 권한 관리자는 서버 시작 설정의 외부 식별자로 지정한다. 권한 관리자 복구·운영 인수는 후속 고도화이며 공개 운영 준비 완료로 표현하지 않는다.

계획 작업 저장에서 `teamId`는 요청 payload가 아니라 인증된 ActorContext에서 정한다. 계획 항목을 `bnoc_works`에 `request_number IS NULL`로 저장하지 않는다. 공유 조회가 미연결 작업 행 때문에 실패한 실제 사례는 [회귀 기록](../records/작업기록.md#shared-work-overview-orphan-rows-20261021)이다. 기존 비계획 `assigned` 집계·목록은 그대로 두고 계획 `planned`와 전체 작업 `all` 버킷을 별도로 계산한다. `all`에는 비계획 유효 할당·선조치 후보고 완료·계획 작업을 포함하고 미배정 요청은 제외한다. 논리 계획 작업은 상태 기준으로 한 번만 센다. 진행 중은 진행 중 1건, 완료는 완료 1건이다. 계획을 기존 BNOC 배정 작업으로 기록하거나 부르지 않는다. 날짜 기준일 이후의 여러 일일 목록에 같은 항목이 보여도 별도 작업이나 집계 행을 만들지 않는다. 완료 작업은 이후 날짜의 진행 목록에서 제외한다. 날짜별 목록 개수와 전체 현재 상태 건수는 구분한다. 외부 계획 체계는 작업반이 수동 확인하는 출처다.

**일반·긴급 저장 제안:** 요청의 `priority`에 `general` 또는 `urgent`를 저장하고 신청 단계에는 비어 있을 수 있게 한다. BNOC의 배정 명령은 명시적인 분류값을 받아 작업 생성·분류·이력·알림을 같은 트랜잭션으로 저장한다. BNOC 최초 배정 폼은 일반이 기본 선택된 미저장 초안이다. 저장 시 명시값을 보내며 서버는 분류 누락을 일반으로 보정하지 않는다. 서버가 BNOC 권한을 검사하며 요청 수정·작업 저장 명령으로 이 값을 우회 수정할 수 없다. BNOC는 배정 후에도 changePriority로 general/urgent를 정정한다. 반환 재배정은 기존 분류를 유지한다. 완료 후보고는 priority=null로 완료 저장 후 BNOC가 사후 분류하며 별도 승인·작업 상태 변경은 없다.

최신 답변으로 접수 시간은 배정 시각이고 반장 지정은 제거됐다. 최초 배정/재배정 사건의 서버 시각을 배정 기록과 이력에 저장하는 안이다. 요청 등록시각·희망 일정·작업 일정과 구별하며 클라이언트 임의 시각은 받지 않는 안이다. 과거 배정 시각 정정 기능은 이번 범위에서 추가하지 않는다.

기존 명세의 `origin='assignment'`와 실제 타입의 `'assigned'`, 대리 등록의 `actualRequesterText`와 실제 `requesterDisplayText`는 표기가 다르다. 현재 동작과 상위 요구를 대조해 후자를 기준으로 명세·전송 타입을 통일하는 제안이다. 업무 상태를 바꾸지 않는 기술 정리이며 사용자에게 새 현업 질문을 만들지 않는다.

## 4. 명령·조회 경계

명령별 주체·주 대상 버전, 조회 경로, 오류 응답, 동시 저장 사례의 상세 제안은 [정비 API와 저장 계약](개발명세서.md#api)에 정리했다. 최신 업무 결정과 대회 인증·첨부 전송을 아래 허용 입력·조회·설정 계약으로 구체화한다. 실제 공군 인증/정보원 규격은 별도 후속 조건이다.

기존 화면 명령의 `type`, `operationId`, `requestNumber`, `workNumber`, `expectedRevision`, `payload` 의미를 유지하는 전송안을 우선 검토한다. 서버는 행동자·역할·작업반을 인증된 세션에서 얻는다. 필드 허용 목록을 두어 이 값을 덮어쓰려는 입력은 거절하는 안이다.

| 기능 | 서버 입력 | 결과·거절 조건 |
| --- | --- | --- |
| 요청 생성 | 직접/대리 구분에 맞는 기존 입력·첨부 참조·제출 식별값 | 새 공개 번호. 필수값·권한·첨부 소유권 검사 |

성공 응답은 공개 번호·갱신에 필요한 결과만 반환하고 DB 전체 상태를 보내지 않는다. 기존 오류 `VALIDATION`, `FORBIDDEN`, `INVALID_STATE`, `NOT_FOUND`, `CONFLICT`, `DUPLICATE_ACTION`, `SAVE_FAILED`의 의미를 유지한다. HTTP 상태·URL·허용 필드·본문 제한·파일 전송은 아래 명세를 따른다. 대회 모의 인증의 만료·거절은 아래 시연 계약에 정의하며, 실제 인증의 오류 매핑은 후속 SSO 규격에 맞춘다.

정비 상세 조회에서는 요청자에게 작업반 내부 메모·반환 내부정보·다른 사람 개인정보를 보내지 않는다. 작업반에는 다른 반 내부 메모·처리자 상세를 보내지 않는다. BNOC에도 내부 UUID·명령 지문 등 화면에 불필요한 구현 정보는 보내지 않는다. 공개 번호를 추측해서 접근해도 같은 권한 검사를 적용한다. 공유 작업 목록과 병력·야간의 인원별 상호 조회는 아래의 별도 허용 범위를 적용한다.

**공유 현황 권한 · 2026-10-20 DEC-033 보완:** 전체 작업 집계·목록 응답은 요청 상세 응답과 분리한다. 작업 번호·부서·유형·표시 상태·일반/긴급·작업 일정·요청자 군내전화번호를 허용한다. 요청자 군내전화번호는 모든 로그인 사용자에게 표시하는 명시적 예외다. 요청 본문·위치·정비대상자 연락처·첨부·인원 정보·작업 메모는 공유 목록에 넣지 않는다. 상세 접근은 기존 권한으로 다시 검사한다. 집계·목록의 조건과 총 항목 수는 같아야 한다. 이 조회 권한 확대로 요청 수정·취소·작업 저장 권한이 바뀌지 않는다.

병력·야간 근무는 모든 부서의 인원별 현황을 조회하되 승인된 인원 식별 표시만 제공하는 안이다. 각 부서 담당자가 자기 명부·현황을 관리하고 권한 관리자가 부서 쓰기 권한을 부여한다. 병력은 선택 날짜, 야간은 시작일이며 과거 입력/수정도 허용한다. SSO가 전체 명부를 제공한다고 가정하지 않는다. 다른 부서의 값을 보낼 수 있어도 쓰기는 거절한다. 야간 근무가 없는 부서에 제출을 강제하지 않고, 미입력 사람의 상태를 가용으로 채우지 않는다.

## 5. 저장·중복·동시 수정

아래는 기존 비기능 요구를 실제 저장으로 옮기는 **기술 제안**이다.

1. 서버가 인증·권한·입력과 제출 식별값을 확인한다. 같은 행동자·같은 제출의 이미 성공한 결과는 재전달하고, 같은 식별값의 다른 내용은 거절한다.
2. 명령의 주 대상인 요청 또는 작업의 예상 버전을 비교한다. 오래된 변경은 `CONFLICT`로 거절한다. 서버 내부에서는 같은 요청의 변경을 직렬화하고 연결 작업들의 최신 상태로 전체 상태를 계산한다. 다른 반 작업이 바뀌었다는 이유만으로 버전이 그대로인 자기 작업의 저장을 충돌 처리하지 않는다. 클라이언트가 요청·모든 작업 버전을 동시에 제출하도록 요구하지 않는다.
3. 업무 변경·전체 상태 재계산·변경 이력·내부 알림·처리 영수증을 한 트랜잭션으로 저장한다. 하나라도 실패하면 전체 롤백한다.
4. 커밋된 결과를 응답한다. 응답만 유실돼도 같은 제출로 결과를 찾을 수 있어야 한다. 공개 요청 번호·작업 번호에는 고유 제약을 둔다.

기술안은 MySQL InnoDB에서 요청 행→주 대상 작업 순으로 잠그고 잠금 후 버전·현재 권한을 재검사한다. 공개 번호·행동자+제출 키·부서/날짜 기록에 고유 제약을 적용한다. 실제 SQL/통합 실행은 구현 승인 후 검증한다. 현재 한 탭의 `revision` 검사나 메모리 복사 처리를 서버 동시성 검증으로 인정하지 않는다.

## 6. 첨부 저장

파일은 임시 업로드 후 서버가 유효성과 소유자를 확인하고, 업무 저장 성공 시 해당 정비 요청 또는 공지게시물에 연결하는 방식이 제안이다. DB와 파일 저장소가 별개라면 파일 존재 확인·연결 상태·실패 복구를 명세해야 한다. DB 롤백만으로 외부 파일이 삭제됐다고 간주하지 않는다.

기술값은 아래 기술 설계값의 형식/용량/개수·임시 24시간·시간별 정리를 따른다. 파일은 저장 식별자로 비공개 경로에 저장한다. 전용 악성 파일 검사기 도입 여부는 실제 운영 연계 조건이며 기본 파일 형식/크기 검사와 혼동하지 않는다. 첨부 제거는 현재 연결만 해제하고 과거 파일/이력은 보존한다. 완료·취소 요청과 이력의 무기한 보존은 이미 정해져 있으며, 임시 파일 정리를 업무 자료 삭제로 확대하지 않는다. 다운로드는 저장된 실제 연결 대상을 읽어 정비 요청이면 기존 상세 권한, 공지이면 게시물 조회 권한을 검사한다. 클라이언트가 보낸 대상 종류로 이 검사를 우회할 수 없으며 공개 저장 URL은 노출하지 않는다.

기존 단위·E2E는 데모 회귀 기준으로 보존한다. 새로고침 시험은 현재 ‘초기화’를 확인하므로 백엔드의 ‘보존’을 검증하는 별도 조건으로 전환해야 한다. 기대값 변경은 백엔드 범위 승인 근거와 연결하며, 단순히 시험을 통과시키려고 바꾸지 않는다.

집계 산식은 설계 0.6 승인안으로 유지하며 이번 답변과 기술값은 개정 설계에 연결한다. 구현 재개 승인 후에는 복수 작업반, 반환·재배정, 취소, 완료 정정, 선조치 후보고를 각각 검사한다. 공유 목록으로 기존 상세정보가 노출되는 오류와 타 부서 수정 허용 오류를 대표 금지 사례로 삼는다.

새 서버에는 실제 DB를 쓰는 권한·중복·동시 수정·원자성·첨부 시험을 추가한다. 서로 다른 작업반의 동시 완료, 오래된 화면 저장, 성공 응답 유실 뒤 재시도, 알림 저장 실패의 롤백을 확인한다. 원본 자료·실제 개인정보는 시험 데이터로 사용하지 않는다. 기술 시험은 역할 식별자·비인물 문자열을 쓰고 사용자 화면에 가짜 인물로 표시하지 않는다.

## 8. AI 검증 절차와 증빙

사용자 원문·문서 근거와 정상/금지 사례를 구현 전에 [작업 기록](../records/작업기록.md)에 남긴다. 읽기 전용 명세 분석, 모듈별 한 작성자, 독립 reviewer·verifier를 적용한다. 검토자는 업무 원문과 설계를 직접 대조하며 구현자 설명만으로 통과시키지 않는다.

일정 주체 관련 구현에는 `node experiments/ai-workflow/run-sensitivity.mjs`를 재사용한다. 이식으로 주입 위치가 달라지면 기존 금지 기준을 보존해 검사도 이식한다. 새로운 핵심 권한 검사는 정상 복사본 통과와 대표 오류 복사본의 의도한 실패를 확인한다. 구문 오류·환경 실패는 탐지 성공이 아니다. [업무 검증 기록](../records/업무검증기록.md)의 관련 실패를 재검사하고 실제 결과만 남긴다.

대회 증빙은 기능별 사용자 요구, AI에 준 실제 입력, 채택 소스·커밋, 정상/금지 검사, 구현 화면, 사람 수정 의견을 연결한다. 동작하는 화면의 스크린샷은 구현·실행 후에만 붙인다. 설문 비율·AI 기여율·생산성 개선율·예상 점수는 근거 없이 만들지 않는다.

## 9. 현재 구현·검증 상태

업무 답변·집계 산식·배정 시각·후보고·대회 모의 연결·기술 선택·API 계약을 설계 0.7에 반영해 제품 구현·검증을 완료했다. 2026-10-17 설계 0.8 사용성 개선도 구현하고 단위·HTTP·PC 브라우저·격리 DB·오류 탐지 검사를 마쳤다. 결과 수치는 [개발 진행](../records/개발진행.md)과 [작업 기록](../records/작업기록.md#usability-design-20261017)에 기록했다. 실제 공군 SSO/GPS/CPCON 연결·상시 호스팅과 현업 과제 검수는 미확인이고 이식 고도화는 유예한다.

**2026-10-13 공개 자료 확인 · 0.7 기술 선택.** 공식 자료 조사는 실행 호환 검증과 별개다. 사용자가 구현을 승인한 조합의 실제 빌드·실행 결과는 [개발 진행](../records/개발진행.md)에 연결한다. 이 절은 기술 선택의 근거이며 업무 규칙을 바꾸지 않는다.

## 검토 결론

공고가 권장한 Spring·Kotlin·Java·MySQL 계열을 우선 검토하되, 오래된 버전 번호까지 자동으로 확정하지 않는 것이 제안이다. 새 서버에 별도 외부 WAS 제약이 없다면 **공식 지원 범위 안의 Spring Boot MVC·Kotlin, Java 17 기반, MySQL LTS, 단일 서버**를 우선 후보로 둔다. 대회 선택안은 Java 17·Spring Boot MVC 4.1.1·Kotlin 2.3.20·Gradle 9.3.0·MySQL 8.4 LTS·업무 JAR로 명시한다. 이 조합의 빌드/실행 검증은 구현 승인 후 대상이며 공군 호환 증거가 아니다. 실제 SSO 구성요소 호환은 후속 실연동 전 별도 확인한다.

공고의 버전은 [대회정보 §7](../reference/대회정보.md)에 권장으로 기록돼 있다. 실제 시연·배포 환경이 그 버전이나 특정 WAS를 요구한다는 증거는 아직 없다. 기존 백엔드 코드를 폐기했으므로 마이그레이션 비용을 이유로 옛 구현을 복구할 필요도 없다.

## 실행 형태의 제안

첫 구현 후보는 화면 정적 파일과 API를 같은 서비스 주소에서 제공하는 단일 서버다. 브라우저의 기존 화면·검색·명시적 저장은 유지하고 서버 내부를 인증, 정비 명령, 조회, 저장, 첨부 책임으로 나눈다. 서버를 여러 개로 쪼갤 근거는 현재 없다.

WAR가 실제 요구되면 실행 가능한 WAR를 검토하고, 외부 WAS에 넣어야 한다면 그 WAS의 Servlet·Java·SSO 연동 조건을 먼저 대조한다. 패키징 이름이 같다는 이유만으로 호환된다고 판단하지 않는다. 한 주소의 시연도 실제 부대 SSO 연동·운영 승인을 대신하지 않는다.

## 1. 전송 방식

기존 화면 명령의 의미를 보존하기 위해 변경은 `POST /api/commands`, 조회는 아래의 읽기 전용 경로로 분리하는 **제안**이다. 화면은 더 이상 서버 내부 상태를 직접 바꾸지 않는다. 단일 명령 경로를 사용해도 명령마다 허용 주체·입력·대상 검사를 따로 수행한다.

| 명령 공통 필드 | 의미 |
| --- | --- |
| `type` | 이 문서의 허용 명령 중 하나. 임의 메서드·SQL 실행 불가 |
| `operationId` | 사용자가 한 번 제출한 동작의 식별값. 응답 유실 때 동일 값으로 재시도 |
| `requestNumber` | 기존 요청 변경 시 공개 요청 번호. 내부 UUID 아님 |
| `workNumber` | 작업 변경 시 공개 작업 번호. 지정 요청에 속하는지도 검사 |
| `expectedRevision` | 아래 표의 **주 대상 하나**를 읽었을 때의 버전 |
| `payload` | 명령별 허용 필드만. 행동자·역할·소속 권한은 서버 세션에서 결정 |

생성 명령에는 기존 대상·예상 버전이 없고 업무 변경 명령에는 주 대상 버전이 필요하다. 알림 항목별 확인 명령만 버전 대신 실제 표시된 본인 알림 ID 집합의 확인 플래그만 단조 갱신한다. 알려지지 않은 명령·필드, 내부 `targetId`, 권한을 덮어쓰는 입력은 거절하는 안이다. 직접 신청의 요청자 정보와 후보고의 소속 반은 서버에서 정한다. 현재 폼이 전송하는 불필요한 계정/소속 필드는 API 어댑터에서 제거한다.

등록 시각과 완료 처리자의 기록은 서버가 만든다. 실제 시작/완료시각을 입력하는 후보고는 일반 완료의 자동 시각과 별도 의미다. 날짜는 YYYY-MM-DD, 시각은 UTC ISO 8601로 전송·저장하고 Asia/Seoul로 표시하며, 희망 일정·작업 일정·접수 시간·실제 작업 시각을 하나의 필드로 합치지 않는다.

## 2. 명령별 주체·대상·입력

‘유지’는 기존 명세에서 이어받은 핵심 규칙이다. 각 행은 허용 주체·주 대상·필드의 구현 계약이며 실제 군 연동 스키마를 뜻하지 않는다.

| 명령 | 주체·주 대상 버전 | 허용 입력·조건 |
| --- | --- | --- |
| `createRequest` | 요청자 또는 BNOC, 버전 없음 | 기존 공통 요청 입력. 요청자는 본인 계정 자동 연결, BNOC는 실제 요청자 텍스트. 필수 유형·내용·위치·군내전화번호 등 기존 계약 유지. `schedulePreferences`는 선택 1·2지망이며 날짜+오전/오후만 받음 |
| `changePriority` | BNOC, **요청 버전** | `priority: general 또는 urgent` 명시. 배정 후 정정·완료 후보고 사후 분류. 분류 전후 이력, 작업 상태/일정 유지. 비취소 요청만, 작업반/요청자 우회 거절 |
| `updateRequest` | 본인 요청자 또는 BNOC, **요청 버전** | `detail`, `location`, `contact`, `schedulePreferences`(선택 1·2지망; 각 날짜+오전/오후), `documentRef`, 첨부 목록. 취소 요청 거절. 요청자 수정 조건은 아래의 경계 참고 |
| `cancelRequest` | 계정 연결된 본인 요청자, **요청 버전** | 비취소 상태에서 취소. BNOC 대리 취소 권한 추가 없음 |
| `moveToDocumentWaiting` | BNOC, **요청 버전** | 대기 상태이며 연결 작업 없음. 별도 문서 대기 해제 명령 신설 없음 |
| `assignTeams` | BNOC, **요청 버전** | 최초 배정 전 대기/문서 대기, 과거 배정 이력 없음, 중복 없는 작업반 하나 이상. `priority: general 또는 urgent` 필수 제안. 작업 일정 입력 없음. 접수 시간은 배정 시각으로 서버 기록 제안. 반장 지정 필드 없음 |
| `updateWork` | 자기 작업반, **작업 버전** | `nextStatus`, 선택 `scheduleIntervals`(하루 전체·정시부터 시작하는 1시간 단위 여러 구간), `memo`, `returnReason`, `completionMemo`, `assignedPersonRefs`(자기 반 명부 선택 목록). 반환 사유 필수. 취소 요청·대체/배정 해제된 반환·후보고 작업 정정 금지 |
| `returnWork` | 자기 작업반, **작업 버전** | 기존 반환 별칭. 서버 내부에서 `updateWork`의 반환으로 처리. 다른 권한·상태 전이 없음 |
| `updateWorkDetails` | 자기 작업반, **작업 버전** | 배정/작업 중인 작업의 `scheduleIntervals`, `memo`만. 취소 요청 거절 |
| `reassignAssignedWork` | BNOC, **원 작업 버전** | `teamIds` 하나 이상. 미해결 배정만, 같은 반/현재 담당 반·취소·후보고·작업 중/완료 거절. 원 작업 보존·reassigned 처리·새 작업 생성·양 부서 알림을 원자 저장. 분류 유지·새 일정 미정 |
| `reassignReturnedWork` | BNOC, **기존 반환 작업 버전** | 미해결 반환에 기존 반 및 현재 유효 담당 반과 중복되지 않는 작업반 하나 이상. 취소 요청 거절. 기존 분류 유지·성공 시 서버 배정 시각. 새 담당 인원은 새 작업반 선택, 반장 지정 없음 |
| `addTeams` | BNOC, **요청 버전** | 0.8 구현. 미완료·비취소·후보고 아닌 요청, teamIds. 과거 BNOC 배정 이력+저장 general/urgent 필수. 현재 담당 중복 거절·분류 유지·최대 번호 다음 생성. 과거 해제 뒤 유효0 대기도 허용 |
| `withdrawReturnedWork` | BNOC, **미해결 반환 작업 버전** | 0.8 구현. payload={}·고정 해제 사유. 재배정과 별도 해소, 원래 기록 보존·전체 상태/집계/알림 갱신 |
| `markNotificationsSeen` | 본인 수신자, 버전 없음 | 0.8 구현. notificationIds·operationId, 실제 표시된 본인 수신 항목만 is_read=true. 업무 해결·공지 확인과 별개 |
| `createAfterActionReport` | 자기 작업반, 버전 없음 | 완료한 작업의 공통 입력·실제 요청자·실제 시작/완료시각·선조치 사유, 선택 완료 메모. 자기 반은 세션에서 결정. 별도 승인 없음. priority=null 미분류 완료 등록 후 BNOC 사후 분류 |

**분류 입력 제안:** 일반/긴급은 최초 배정과 함께 저장한다. 신청의 필수 입력으로 옮기지 않고, `updateRequest`·`updateWork`의 허용 필드에 섞지 않는다. BNOC 권한·명시적 분류값 확인이 끝나기 전 작업을 생성하지 않는다. 화면 기본 선택은 미저장 초안이며 분류 없는 명령을 서버가 자동 일반으로 확정하지 않는다. 사용자 답변으로 배정 후 BNOC 분류 편집은 별도 changePriority 명령으로 명시한다.

`assignTeams`의 버전 검사는 현재 코드에도 있다. 예전 아키텍처의 개별 행에서 버전 표기가 빠졌지만 공통 계약과 화면·명령에는 요청 버전이 전달된다. 이를 없는 기능으로 보고 새 업무로 추가하지 않는다.

**요청 수정 사용자 결정:** 본인 비취소 요청은 작업 없는 접수 단계 또는 모든 유효 작업이 현재 배정일 때 수정 가능하다. 과거 시작 이력만으로 금지하지 않는다. 작업 중·완료·미해결 반환이 하나라도 있으면 거절한다. 재배정/배정 해제로 해결된 반환은 유효 작업에서 제외한다. 유효 작업0개·후보고 아닌 대기는 본인 수정 가능하며 후보고 완료는 수정 허용 상태가 아니다.

**후보고 완료 확인의 경계:** 현재 화면의 완료 확인은 브라우저에서 검사하고 명령은 입력된 실제 완료시각 등을 검사한다. 서버 이전안은 완료된 작업만 기록한다는 기존 의미를 서버 입력에도 명시하는 방향이다. 최종 전송 스키마에서 확인값과 실제 완료시각을 구분한다. 미완료를 위한 새 접수·BNOC 전달·자동 역할 전환은 만들지 않는다. 끝낸 뒤 기존 완료 후보고로 기록한다.

## 3. 조회 경로와 응답 범위

아래 경로·응답 이름은 승인된 구현 계약이다. 날짜별 달력·권한 관리·파일·운영의 추가 경로는 아래 운영/API 연결안으로 제시한다. 대회 입력/권한은 최신 결정과 아래 기술 계약을 적용한다. API·저장 결과는 실행 증거로 확인하며 실제 군 규격은 후속 조건이다.

| 조회 경로 | 범위·응답 |
| --- | --- |
| `GET /api/session` | 현재 인증 사용자의 서비스 역할·작업반·허용 동작. 다른 계정 목록·SSO 토큰·내부 식별번호 묶음 반환 없음 |
| `GET /api/requests` | 적용한 검색 조건의 권한별 요약. 0.8은 전체/우리 반 상태·현재/과거 참여·담당/완료 반수·부서 상태 추가. 요청자 이름 조건은 BNOC만 사용 |
| `GET /api/requests/{requestNumber}` | 권한별 공통 정보·작업·첨부·버전. 0.8은 resolution/previousSchedule와 서버 계산 canAddTeams·작업별 canWithdrawReturnedWork 추가. canAssign은 최초 배정만 의미 |
| `GET /api/requests/{requestNumber}/history` | 해당 요청의 역할별 공개 이력. 원본 before/after 객체와 타인 내부정보를 그대로 반환하지 않음 |
| `GET /api/schedule` | 현재 작업반의 복수 일정 구간·미정 작업과 완료 선조치 후보고 기록. BNOC는 기존 전체 정비 조회 범위, 작업반은 자기 반 범위. API는 작업별 한 항목과 복수 시간 구간을 반환한다. 프런트는 조회 기간 안 각 작업을 카드 하나로 표시하고 가장 이른 겹침 구간 시작 시각으로 배치·정렬한다. 작업번호·부서·일정 구간 또는 정확한 후보고 시작 시각·상태·위치·작업 메모·상세 화면 이동용 요청 번호만 허용한다. 요청 상세·전화번호·그 외 요청 요약은 제외한다. 요청자 전체 달력 조회 확대 없음 |
| `GET /api/overview` | 기존 BNOC 전용 요청 집계와 요청 목록. 상세 필드를 가진 기존 응답을 통째로 공개하지 않음 |
| `GET /api/work-overview` | 일반 요청자·작업반·BNOC 모두 전체 집계·작업 목록 조회. 구조화된 공유 필드와 요청자 군내전화번호만 반환하고 상세는 기존 권한 유지 |
| `GET /api/notifications` | 현재 수신자의 허용 알림·공개 요청/작업 번호. 0.8은 화면에 표시하지 않는 notificationId와 항목별 확인 플래그 제공 |
| `GET /api/notifications/unseen` | 0.8 구현. 본인 수신·현재 조회 허용 사건 중 is_read=false 건수. 반환 대기와 별개 |
| `GET /api/planned-works?workDate=YYYY-MM-DD` | 선택한 날짜 기준 목록을 반환. `workDate >= firstWorkDate`이고 `in_progress`인 작업이 포함되어 다음 날짜에도 같은 식별자로 계속 표시된다. 완료 작업은 관리 목록에 따로 반환하며 이후 날짜의 진행 목록에는 넣지 않는다. 상태는 현재 상태이며 과거 시점 상태를 추정하지 않는다. 다른 작업반 항목은 반환하지 않음 |

공유 작업 현황은 같은 필터의 `counts`와 `items`·총 항목 수를 함께 반환한다. 비계획 작업 행에는 작업 번호·부서·지원/작업 유형·상태·일반/긴급·일정·요청자 군내전화번호와 상세 접근 여부를 제공한다. 요청자 군내전화번호는 모든 로그인 사용자에게 공유 목록에서만 보이는 명시 예외다. 요청 본문·위치·정비대상자 연락처·첨부·인원 정보·작업 메모·이력 원문은 포함하지 않는다. 계획 행은 `source: planned`와 안정적인 계획 식별자·부서·제목·진행/완료 상태·기준일·완료일만 제공하고 요청번호·요청 상세 링크·우선순위·연락처를 만들지 않는다. 계획 제목은 모든 로그인 사용자의 공유 목록과 작업반 계획 화면에서 표시한다. 상세 요청 접근은 기존 본인/자기 반/BNOC 권한 검사를 유지한다.

공유 버킷은 기존 `assigned/completed/remaining/returned/after-action/unassigned`를 유지하고 `planned`와 `all`을 추가한다. 최신 사용자 결정(FR-038)에 따라 비취소·유효 선조치 후보고 완료는 `assigned`와 `completed` 및 부서별 해당 수에 한 번 포함한다. `afterActionCompleted`와 `after-action` 버킷은 출처 확인을 위한 부분집합이며 다시 가산하지 않는다. 계획은 별도 `planned` 버킷으로 보이며, `all = assigned + planned`, `allCompleted = completed + plannedCompleted`, `allRemaining = remaining + plannedInProgress`다. 각 부서에도 같은 산식을 적용한다. 기존 비계획 반환·미배정 의미는 유지한다. 요청 전용 `category/systemType/workType/priority/requestNumber` 필터가 지정되면 일치하는 계획 데이터 기준이 없으므로 계획 행은 전체 집계에서도 제외하며 그 사실을 화면에서 알린다. 부서 필터는 계획 소유 작업반에 적용한다. 상태 `완료`는 해당 작업과 완료 계획을 포함하고 `진행 중`은 계획 상태만 가리킨다. 선택 버킷의 카드 수·목록·총 항목 수는 같은 필터 기준으로 맞춘다. 별도 일일 실적이나 외부 체계 자동 대조는 추가하지 않는다. 구현·검증 결과는 [작업 기록](../records/작업기록.md#schedule-after-action-implementation-20261021) 및 [계획 정비 기록](../records/작업기록.md#planned-maintenance-implementation-20261021)에 연결한다.

요청 요약은 `requestNumber`, `requesterDisplayText`, `category`, `status`, 작업반 목록, `updatedAt`를 출발점으로 한다. 상세 응답은 현재 화면이 쓰는 항목의 허용 목록으로 만들고 DB 엔티티 전체를 직렬화하지 않는다. 작업반·첨부의 기능상 참조값은 요청/작업 내부 UUID와 구별한다.

등록자·완료자는 화면에 필요한 표시값으로 변환한다. 현재 조회 객체의 `registeredBy`, `recipientActorId` 등 계정 참조를 이름만 바꿔 그대로 내보내지 않는다. 역할별 연락처·정비대상자·내부 메모·반환·이력 노출 범위는 기존 아키텍처 §6을 따른다. 가짜 이름·계급은 표시 예제로 넣지 않는다.

검색의 네트워크 호출 시점도 기존 규칙을 따른다. 신청 목록의 타이핑·조건 선택만으로 조회하지 않고 검색/Enter/초기화 때 실행한다. 입력 중 목록을 다른 조건 결과로 바꾸지 않는다. BNOC 현황 빠른 필터는 기존 즉시 적용이다.

## 4. 응답·오류·재시도

변경 성공은 `ok=true`, 공개 요청 번호, 재전달 여부 등 필요한 결과만 반환하는 안이다. 화면은 성공 뒤 권한 범위의 상세·목록을 다시 조회한다. 재전달 결과의 업무 데이터가 현재 최신 상태라는 보장은 없으므로 현재 화면값으로 그대로 덮어쓰지 않는다.

실패는 `ok=false`, `errorCode`, 허용된 `fieldErrors`, 충돌 시 `refreshRequired`를 기본으로 한다. 오류의 HTTP 매핑은 아래 **제안**이며 실제 SSO 응답·파일 전송 오류는 해당 규격 확정 후 완성하고, 모의 인증 오류는 아래 대회 계약을 따른다. 상태 코드 의미는 [HTTP 표준 RFC 9110 §15](https://www.rfc-editor.org/rfc/rfc9110.html#section-15)에 따른다.

| HTTP | 업무 오류·표시 | 조건 |
| --- | --- | --- |
| 200 | 성공 또는 동일 제출 결과 재전달 | 업무 커밋을 확인한 경우만 |
| 400 | `VALIDATION` | 잘못된 명령·필수값·형식·허용 필드 오류 |
| 403 | `FORBIDDEN` | 해당 기능 자체를 사용할 역할이 아님 |
| 404 | `NOT_FOUND` | 대상이 없거나 해당 대상에 접근할 수 없음. 권한 밖 대상의 존재·버전을 알리지 않음 |
| 409 | `CONFLICT`, `INVALID_STATE`, `DUPLICATE_ACTION`, `OPERATION_NOT_AVAILABLE` | 오래된 수정, 허용되지 않은 현재 상태, 같은 계정 제출 번호에 다른 내용, 다른 계정 제출 번호 재사용 또는 현재 작업반과 과거 결과의 소유 작업반 불일치 |
| 500 또는 503 | `SAVE_FAILED` | 내부 실패 또는 일시적 처리 불가를 구분. 내부 SQL·원시 파일 경로·SSO 정보 출력 없음 |

`SAVE_FAILED`나 연결 끊김만으로 ‘DB에 아무것도 남지 않았다’고 단정하지 않는다. 서버가 롤백을 확인한 실패와 응답 유실·커밋 결과 불명을 구별하고, 후자는 같은 제출 식별값으로 재확인한다. 처리 중인 같은 제출은 완료 결과를 기다리거나 재확인 안내로 응답하되 두 번째 실행을 만들지 않는다. 처리 중 202/PROCESSING과 Retry-After 2초를 반환한다. 같은 제출 키로 재확인하며 서버가 확정한 롤백 실패와 결과 불명을 구별한다.

권한 확인은 상세 버전·상태 오류를 반환하기 전에 수행한다. 같은 제출의 결과를 재전달할 때도 현재 인증·권한과 현재 작업반-기록된 작업 소유 작업반 일치를 다시 확인한다. 과거 영수증이 있다는 이유로 회수된 권한을 우회하지 못한다. 계획 작업 제출 번호의 계정 간 재사용은 작업 데이터와 연결하지 않은 전역 비가역 해시로 막고, 같은 계정의 과거 사용은 행동자별 해시로 막는다. 쿠키 세션은 HttpOnly·SameSite=Lax이며 공개 HTTPS에서 Secure를 사용한다. 로컬 loopback HTTP 시연만 별도 설정한다. 변경 요청은 서버 세션의 CSRF 토큰과 Origin 허용 목록을 검사한다. SSO 복귀는 사전 인증 브라우저 상태·로그인 요청에 묶고 단회 소비한다.

## 5. 저장 관계와 불변식

DB 제품과 무관한 논리 관계 제안이다. 실제 SQL·인덱스·잠금 구문을 작성한 상태가 아니다.

| 관계·제약 | 보장할 결과 |
| --- | --- |
| 요청 공개 번호 고유 | 동시 생성에도 같은 요청 번호가 두 건 생기지 않음. `101`부터의 표시 형식 유지 |
| 작업은 요청 하나에 속함, 요청 안 작업 번호 고유 | `101-1`이 다른 요청의 작업으로 해석되지 않음 |
| 작업의 작업반 참조 | 허용된 작업반만 배정. 주·부 작업반 개념 추가 없음 |
| 반환 작업과 대체 작업의 관계 | 한 재배정에서 생성한 작업과 원래 반환이 함께 기록. 대체된 원래 작업은 수정 불가 |
| 요청자 계정 연결은 직접 등록에서만 | 대리/후보고 텍스트에서 계정을 추정하지 않음 |
| 명령 주 대상 변경 버전 | 오래된 같은 대상 수정 거절. 다른 작업반 작업은 불필요하게 충돌시키지 않음 |
| 행동자와 제출 식별값의 고유 조합 | 같은 사용자의 같은 제출을 한 번만 처리. 동일 키 다른 입력은 거절 |
| 업무·이력·알림·성공 영수증의 함께 저장 | 부분 성공·재시도 중복 이력·중복 알림 방지 |

번호 생성은 현재 메모리의 `최대 번호+1` 계산을 동시에 실행하는 방식으로 복사하지 않는다. 원자적 번호 할당과 고유 제약을 함께 설계한다. 번호 중복 방지는 필요하지만 번호에 절대로 공백이 없어야 한다는 새 업무 요구를 만들지 않는다.

## 6. 같은 요청의 동시 변경 처리

서버 내부에서 같은 요청에 속한 명령을 짧게 직렬화하는 안이다. 클라이언트에 모든 작업의 버전을 제출시키거나 전체 부서를 편집 중 잠그는 화면은 만들지 않는다. 동일 잠금 순서를 정하고, 잠금을 얻은 뒤 주 대상 버전·권한·현재 요청/작업 상태를 다시 확인한다. 잠금 밖에서 계산한 오래된 전체 상태를 그대로 저장하지 않는다.

| 경합 | 정상 결과 | 금지 결과 |
| --- | --- | --- |
| 서로 다른 두 작업반이 동시에 완료 | 각 작업 버전이 유효하면 모두 저장. 마지막 변경 뒤 전체 유효 작업이 완료이면 요청 완료 | 한 작업 소실, 전체 완료인데 요청은 배정, 완료 알림 중복 |
| 같은 작업에 다른 두 변경 | 한 변경 성공, 나머지 충돌 후 최신 조회 | 뒤의 저장이 먼저 저장된 변경을 조용히 덮어씀 |
| 취소가 작업 저장보다 먼저 확정 | 취소 유지, 후속 작업 저장 거절 | 취소 요청을 작업 저장이 되살림 |
| 완료가 취소보다 먼저 확정 | 완료 이력 보존. 요청 버전이 바뀌었다면 오래된 취소는 충돌, 최신 조회 후 취소 가능 | 이미 완료된 이력을 지워 취소를 맞춤 |
| 반환 정정과 재배정 동시 실행 | 원래 반환 작업 버전으로 한 변경만 성공 | 원래 작업 재개와 새 배정이 동시에 유효해짐 |
| 같은 제출 두 번 동시 도착 | 하나만 업무 처리, 나머지는 같은 결과 재전달 | 두 요청·중복 작업·중복 알림 생성 |
| 알림/이력 저장 실패 | 업무 변경까지 롤백 | 작업은 완료인데 이력이나 알림 일부만 누락 |

변경 없는 수정 저장은 기존처럼 업무 버전·이력·상태 알림을 늘리지 않는다. 해당 제출을 재시도해도 반복 처리되지 않도록 영수증은 남기는 안이다. 첨부 외부 저장의 일관성은 [개발 명세 §6](개발명세서.md#6-첨부-저장)에서 별도로 처리하며 DB 트랜잭션만으로 해결됐다고 주장하지 않는다.

## 7. 검증과 남은 범위

실제 DB와 독립된 두 세션으로 위 경합의 실행을 검사한다. HTTP 직접 호출로 역할 위조, 타 작업 접근, 권한 회수 뒤 재전달, 내부 식별값 유출을 확인한다. 새 권한·동시 저장 검사는 대표 오류 복사본이 의도한 기준에서 실패하는지도 확인한다. 기존 일정 주체 감도 검사도 재사용한다. 실제 실행·실패·재검사 결과는 [업무 검증 기록](../records/업무검증기록.md)에 남긴다.

대회 범위의 입력 허용 목록·날짜/페이지·인증·파일·명부·권한·상황 응답은 이 명세를 구현 계약으로 사용한다. 실제 JSON/SQL 구현은 `backend/`, 호출·화면은 `frontend/`에 있으며 실행 증거는 기존 기록에 연결한다. 실제 SSO/GPS/CPCON 규격·공개 백엔드 호스팅/공군 실행환경 호환과 고도화 유예 항목은 후속 조건이다. 이미 답한 업무를 다시 미정으로 남기거나 기술값을 실무 질문으로 늘리지 않는다.

계획 쓰기는 기존 `WorkflowService`의 `POST /api/commands`에 넣지 않는다. 그 경로는 요청/작업번호와 영구 `bnoc_receipts`·`bnoc_operation_locks`를 전제하기 때문이다. 계획 API도 기존과 같은 로그인 세션·같은 Origin CSRF 검사를 거친다. 생성·수정·완료는 계획 전용 영수증을 작업 ID에 연결해 재전달을 한 번만 반영한다. 삭제 시 제목·최초 기준일·완료일·작업 ID가 들어갈 수 있는 결과 영수증은 모두 제거한다. 동시에 작업 ID·제목·날짜·명령 종류·삭제 여부와 연결되지 않는 행동자+제출 키의 비가역 해시만 남겨 이전 생성 요청의 늦은 재전달을 거절한다. 이 해시는 작업이나 삭제 이력을 조회·복원할 수 없으며 새 요청의 성공 결과를 재생하지 않는다. `DELETE`는 계획 전용 경로에서 버전·소유권을 검사하고 자체 영수증·잠금 행을 생성하지 않는다. 기존 비계획 명령 파이프라인은 변경하지 않는다.

최초 업무 기준일 입력은 서울 기준 오늘을 기본값으로 하고 과거·미래 날짜를 허용한다. 기준일은 해당 날짜부터 진행 중 항목이 일일 목록에 나타나도록 하는 값이다. 이후 날짜의 목록은 같은 작업을 자동으로 포함하며 날짜별 등록 행을 새로 만들지 않는다. 화면은 달력과 이전 날짜·오늘·다음 날짜 이동을 제공하며 date-only로 처리한다. 완료 확인은 기준일 이상·오늘 이하의 날짜를 쓴다. 완료된 작업은 이후 날짜의 진행 목록에서 빠진다. 공유 집계는 현재 상태 기준 논리 작업당 한 건이다. 외부 체계의 실제 진행을 추론하거나 자동 대조하지 않는다. 삭제 뒤의 예전 제출 키 재전달은 비연결 키 해시로 거절하고 화면은 재조회 결과로 삭제 성공을 판정한다.

**공지 게시와 첨부:** 제목·내용·문서 선택 후 BNOC가 게시한다. 업로드된 파일은 연결 전까지 임시 상태다. 서버는 BNOC·파일 소유·검증 결과·종류를 확인한 뒤 게시물과 첨부 메타데이터 연결을 같은 DB 트랜잭션에 넣는다. 본문 저장이 실패하면 임시 파일을 나중에 정리하며 성공 게시로 표시하지 않는다. 모든 BNOC 공동 수정에서 해당 공지에 이미 연결된 파일은 타 BNOC 업로드라도 유지 가능하다. 신규 추가 임시 파일에만 현재 업로더 소유를 검사하고 다른 공지/요청 첨부 참조로 우회하지 못한다. 다운로드는 저장된 실제 연결 대상의 권한을 검사한다. 게시물 조회 권한으로 정비요청 첨부를 여는 경로는 없다. 모든 BNOC 계정이 제목·본문·첨부를 수정하고 문서 제한은 아래 기술값이다. 게시 종료·숨김 기능은 없으며 공지 읽음 확인·알림 수신 확인 업무는 추가하지 않는다. 새 알림 구분을 위한 항목별 확인 플래그는 별도 기술 상태다.

**GPS 연동:** 원본 단계·원본 기준시각·수집시각·성공/실패 상태를 분리한다. 내부 단계는 1~5, 5만 ‘양호’로 표시한다. 1~4의 별도 명칭과 외부 값 매핑은 임의 생성하지 않는다. 최초 미수집, 마지막 성공 값이 있으나 갱신 실패, 유효시간 초과를 구별하는 안이다. 실패/범위 밖 값은 5로 대체하지 않는다. 대회에는 아래 모의 응답 계약과 설정 가능한 수집 주기·시간 초과·유효시간을 사용한다. 실제 주소·인증·원본 매핑은 후속 실연동 계약이며 시험 구현을 막지 않는다. 수집 작업은 기존 BNOC 백엔드에서 실행하고 대회용 모의 정보원만 별도 프로세스로 둔다.

**배정 시각:** ‘접수 시간’은 사용자 답변에 따라 배정 시각이다. 최초 요청 등록시각과 구별한다. 배정 사건/작업 연결에 서버 시각을 기록하고 상세/이력에서 ‘배정 시각(접수 시간)’으로 표시하는 안이다. 재시도는 최초 저장 시각을 유지한다. 반장 선택·수기 입력·반장 ID는 제거한다. 임의 과거 시각 정정 권한은 추가하지 않는다.

**논리 저장 보완:** 정비 요청/작업/배정 사건과 일일 병력/야간 근무/종류별 GPS·CPCON 스냅샷/수집 시도/공지게시물을 분리한다. 첨부 연결은 `request` 또는 `notice` 대상과 한 쌍으로 저장해 권한을 구별한다. 인원 참조는 확정된 명부로부터 받아야 하며 SSO 전체 명부나 가짜 인물을 생성하지 않는다. 명부·현황·담당 인원 참조·분류 변경·공지 수정은 최신 결정과 아래 허용 계약을 적용한다. DB 제약·인덱스의 실제 SQL은 이 설계에 맞춰 구현 승인 후 작성·검증한다.

**승인 범위:** 이번 산출물은 기능 명세·모듈 배정·호출·API 연결까지 검토하는 버전이다. 사용자 결정, 승인된 기존안, 기술 설계값과 실제 운영 후속 조건을 구별했다. 최종 JSON/SQL·실제 연동·제품 구현/검증·공개 배포가 완료됐다는 뜻은 아니다.

## 대회용 SSO·GPS·CPCON 모의 연동 계약

**사용자 결정:** 공군 SSO·GPS 실제 연결 불가, 연결 가능한 환경을 가정한 대회 결과물. CPCON도 포함. **기술 제안:** 모의 서버 한 개에 인증·상황 모듈을 두고, BNOC의 세션·권한·수집·DB 저장·API 응답은 동일한 실제 처리 경로로 구현한다. 아래 경로와 필드는 대회용 모의 제공자와 BNOC 서버의 구현 계약이다. 실제 공군의 API 규격을 뜻하지 않는다.

### 실행 모드와 제출 범위

- 서버 시작 설정의 `integrationMode=competition`에서만 모의 인증·GPS·CPCON 제공자를 허용한다. 업무 화면/요청 payload로 제공자를 선택하지 않는다. 실제 경계와 모의 경로는 대체 경로이며 함께 조회하지 않는다.
- 후속 `operational` 모드에서는 모의 인증·정보원을 거절한다. 실제 연결 구현·필수 설정이 없으면 준비 실패로 중단하며 모의 응답으로 대체하지 않는다. 설정 변경만으로 공군 연동이 완성되지 않는다.
- 시연 운영자는 로컬 제어로 시험 시나리오를 선택한다. 모의 제어를 BNOC 업무 API나 운영 화면으로 노출하지 않는다. 모의 서버가 BNOC 업무 DB·화면 상태를 직접 변경하지 않는다.
- 대회 실행 묶음에는 BNOC 서버·DB·첨부 저장소·모의 서버의 시작 방법과 시험 시나리오를 포함하고 기존 README에 실행 안내를 쓴다. 외부 공군망 없이 실행·재시작·저장 보존을 확인하는 것이 구현 후 합격 기준이다. 실제 배포환경의 HTTPS와 로컬 연결 구성을 명시하며 실제 연결 주소나 비밀값을 임의 생성하지 않는다.
- 사용자 화면에는 모의/대회용 표시나 실제 연동 여부 설명을 넣지 않는다. 로그인은 사용자 인증, 상황 출처는 GPS 정보원·CPCON 정보원으로 표시하며 기준시각·수집 상태는 유지한다. 내부 sourceMode·서버 설정·기술 문서·검증 기록에는 실제 모의 구현 여부를 보존한다. 역할명·비인물 시험 식별자만 사용하며 가짜 이름·합성 계급·실제 개인정보·실제 운영 수치를 넣지 않는다. 모의 연동 정상 동작과 실제 공군 호환 여부를 보고서에서 구분한다.

### 인증 시작·복귀·권한 연결

| 경계 | 입력·동작 | 결과·거절 |
| --- | --- | --- |
| BNOC `GET /api/auth/start` | SessionManager가 시작 브라우저의 서버 사전 인증 상태에 로그인 요청 식별값·만료·허용 복귀 경로를 묶어 보관하고, 설정된 제공자의 로그인 위치를 안내 | 아직 업무 세션·권한 없음. 임의 외부 복귀 주소 거절 |
| 모의 제공자 `issue(identity, loginAttempt)` | 대회 로그인에서 사전 등록된 시험 신원을 역할명으로 선택. 해당 로그인 요청에 연결된 짧은 수명의 단회 확인표 발급 | 시험 신원 목록 밖 입력 거절. 회원가입 없음. 확인표는 서비스 권한 자체가 아님 |
| BNOC `POST /api/auth/complete` | 확인표·로그인 요청을 받고 모의 제공자에 검증/소비 요청. 제공자·시작 브라우저의 사전 인증 상태·요청 일치·유효시간·재사용 검사 후 사전 인증 요청도 단회 소비 | 성공 시 시험 식별자 반환. 위조/만료/이미 사용/요청 또는 시작 브라우저 불일치/제공자 장애면 세션 생성 안 함 |
| SessionManager의 세션 생성 | 서버 저장소의 시험 식별자→서비스 역할·부서·작업반 매핑 조회 | 기존 세션 규칙으로 세션 생성. 브라우저가 보낸 역할·부서는 권한에 사용하지 않음 |
| 기존 `GET /api/session`와 업무 API | 서버 세션과 현재 서비스 권한 확인 | 권한 회수·만료 시 거절. 인증 성공이 업무 전체 권한을 뜻하지 않음 |

인증 시작/복귀는 업무 세션 생성 전 진입점이다. 이 예외를 일반 업무 API의 미인증 접근으로 확대하지 않는다. 모의 제공자의 검증 응답은 설정된 서버 경계에서만 받아들이며 확인표·비밀값을 업무 화면·일반 로그에 남기지 않는다. 시연 역할을 바꾸려면 로그아웃 후 다시 인증한다. 대회 세션·확인표 유효시간과 역할별 서버 매핑은 아래 기술값을 따르며 실제 공군 SSO 규격과 혼동하지 않는다.

### 상황 응답·수집·저장 계약

모의 서버의 `GET /feeds/gps`와 `GET /feeds/cpcon`을 서버 수집 작업이 호출하는 안이다. 두 응답은 공통 봉투를 쓰되 단계 사전과 적용 범위를 독립 정의한다.

| 필드 | 의미·검사 |
| --- | --- |
| `kind` | `gps` 또는 `cpcon`. 요청 종류와 다른 응답 거절 |
| `sourceMode` | 모의 제공자는 `simulation`. 서버 실행 모드와 함께 확인하고 저장·화면까지 보존 |
| `scopeKey` | 정보의 적용 범위. GPS는 부대 공통. CPCON은 정보원 scopeKey 그대로 독립 관리, 실제 부대 범위·부대명 임의 생성 금지 |
| `stageCode`, `stageLabel` | GPS는 1~5, 5=양호. CPCON은 별도 단계 사전과 일치해야 함. 사전 미설정은 미설정 상태이며 GPS 변환 규칙 사용 금지 |
| `observedAt` | 정보원 기준시각. 수집 시각으로 바꿔 최신처럼 보이게 하지 않음 |
| 수집 결과 | 서버가 마지막 시도·마지막 성공·유효 응답·실패 종류를 각각 기록. 오류·지연·누락은 성공 스냅샷으로 저장하지 않음 |

상황 스냅샷의 키에는 `kind`와 `scopeKey`를 포함한다. GPS 성공과 CPCON 실패를 각각 저장한다. 오류가 나면 해당 종류의 마지막 성공 값은 보존하고 실패/오래됨을 표시한다. 수집 시도 자체가 없을 때만 미수집으로 표시한다. 첫 시도가 실패했다면 성공 값 없음·실패 원인·마지막 시도를 표시한다. CPCON 단계 사전이 없으면 미설정으로 응답한다. 정보 종류별 수집 주기·시간 초과·유효시간은 양수 설정으로 검증한다. GPS/CPCON의 실제 단계·수집 조건을 같은 값으로 강제하지 않는다.

조회는 기존 API 진입점과 AccessPolicy를 거친다. 사용자 답변으로 GPS·CPCON은 모든 로그인 사용자가 조회한다. 병력·야간의 모든 부서 상호 조회와는 별도 권한이며 일반 요청자까지 인원 현황 조회를 새로 추론하지 않는다. `GET /api/situation/gps`, `GET /api/situation/cpcon`은 저장된 상태·출처를 반환한다. 사용자용 단계 변경 명령은 만들지 않는다.

### 구현 후 시연·검증할 사례

- 정상 모의 로그인, 위조·만료·재사용·로그인 요청/시작 브라우저 불일치 거절, 권한 회수 후 업무 거절. 운영 모드에서 모의 확인표를 보내도 인증되지 않아야 한다.
- GPS 정상값 수집, 단계 변경, 범위 밖 값, 시도 전 미수집과 첫 시도 실패 분리, 실패 뒤 마지막 성공 값 표시, 오래됨 표시. 서버 저장 뒤 화면이 바뀌고 재시작 후 저장값이 유지돼야 한다.
- CPCON은 공개 근거 기반 코드 사전·CPCONⅠ~Ⅴ급·정보원 scopeKey로 같은 수집 흐름을 확인한다. 임시 단계 A/B·한국어 태세명은 만들지 않는다. 단계 사전 미설정·모르는 코드 거절도 확인한다. GPS 정상과 CPCON 실패를 동시에 만들고 서로의 값/상태가 덮이지 않는지 검사한다.
- 모의 제공자 정지·시간 초과·누락 응답을 성공으로 바꾸지 않는다. 실제 연결 실패로 자동 모의 전환하지 않는다. 내부 sourceMode·기술 문서·검증 기록에 모의 출처가 남아 있어야 한다. 사용자 화면은 중립적인 정보원 이름과 시각·수집 상태를 표시한다.

CPCON 모의 코드는 공개 근거에 따른 별도 1~5 사전, 정보원·저장·API 표시명은 `CPCONⅠ급`~`CPCONⅤ급`, 범위는 정보원 scopeKey로 명시한다. 화면의 단계값 `I`~`V`와 구별한다. 국내 국방부 자료가 직접 확인한 것은 Ⅳ급→Ⅲ급 표기이며 미국 교육의 전체 1~5 설명은 별도 근거다. 한국 공군의 전체 단계 의미·범위·실제 규격을 확인한 것으로 주장하지 않는다. 상세 출처는 [조사근거](../reference/조사근거.md#cpcon-public-evidence)다.

## 3. Command·조회 필드 형식

`types.ts`에 선언할 핵심 타입. 04번 문서 3.1·3.3절 필드 목록을 TypeScript로 옮긴 것이며 새 필드를 추가하지 않았다.

```ts
type Role = 'requester' | 'bnoc' | 'team';
type RequestStatus = '대기' | '문서 대기' | '배정' | '작업 중' | '완료' | '취소';
type WorkItemStatus = '배정' | '작업 중' | '완료' | '반환';
type ErrorCode = 'VALIDATION' | 'FORBIDDEN' | 'INVALID_STATE' | 'NOT_FOUND' | 'CONFLICT' | 'DUPLICATE_ACTION' | 'OPERATION_NOT_AVAILABLE' | 'SAVE_FAILED';

interface SchedulePreference { rank: 1 | 2; date: string; period: 'AM' | 'PM'; }

interface Request {
  id: string; requestNumber: string; registeredBy: string; requesterActorId?: string; requesterDisplayText: string;

  maintenanceTarget?: MaintenanceTarget; schedulePreferences: SchedulePreference[]; documentRef?: string;

}

  id: string; requestId: string; workNumber: string; teamId: string; status: WorkItemStatus;
  scheduleIntervals: WorkScheduleInterval[]; previousScheduleIntervals: WorkScheduleInterval[];

  type: string; operationId: string; requestNumber?: string; workNumber?: string;

}
interface Command<P = unknown> { type: string; operationId: string; targetId?: string; expectedRevision?: number; payload: P; }
```

화면은 내부 ID가 없는 `ViewCommand`만 `SessionStateStore.dispatch`에 보낸다. 저장소가 신뢰된 현재 세션과 `requestNumber`, 작업 명령이면 요청별 `workNumber`로 내부 대상을 하나로 해석하고 내부 `Command.targetId`를 만든다. 기존 대상 변경에는 화면 조회값의 `expectedRevision`이 필수다. `createRequest`, `createAfterActionReport`에는 대상 번호·revision이 없다. 내부 `CommandResult`는 M-03과 저장소 안에서만 사용한다. 화면에는 전체 `AppState`·`changedIds`·원본 `latestValue`를 반환하지 않고 `ViewCommandResult`만 반환한다. 생성 성공과 같은 명령 재실행에는 같은 공개 `requestNumber`를 반환한다. 충돌이면 화면이 `refreshRequired`를 보고 M-04 조회를 다시 호출해 권한 필터된 최신값을 받는다.

### 3.1 화면 상태 계약

- `RequestListAndSearch`는 `draftCriteria`와 `appliedCriteria`를 별도 로컬 상태로 둔다. 입력·선택 변경은 `draftCriteria`만 바꾸며 조회 함수를 호출하지 않는다.
- `검색` 버튼 또는 검색 입력의 Enter는 현재 `draftCriteria`의 불변 복사본 `snapshot`을 만든다. `appliedCriteria`를 그 값으로 갱신하고 같은 `snapshot`으로 `searchRequests(snapshot)`을 한 번만 호출한다. React 상태 갱신 직후 이전 `appliedCriteria`를 읽어 조회하지 않는다. `초기화`는 두 상태를 비우고 기본 목록을 한 번 조회한다.
- 이 명시적 검색 실행 규칙은 메인 신청 목록에만 적용한다. `BnocOverviewView` 현황 필터는 이번 변경 범위가 아니다.
- `WorkExecutionPanel`은 선택 상태·반환 사유·완료 메모·일정·메모를 임시값으로 유지하고 `저장` 때만 `updateWork`를 한 번 보낸다.
- `updateWork`는 일반 배정 작업만 받는다. 취소 요청, 재배정으로 대체된 반환 작업, `origin='after-action'` 작업은 `INVALID_STATE`로 거절한다.
- `nextStatus='반환'`이면 `returnReason`이 필수다. 완료를 떠나면 현재 `completion`을 제거하고, 완료로 들어가면 새 `Completion`을 생성한다. 반환을 떠나면 현재 `returnReason`을 제거한다. 과거 값은 `HistoryEntry`에 남긴다.
- 모든 사용자 화면과 화면용 조회 결과는 요청 식별에 `requestNumber`, 작업 식별에 `requestNumber + workNumber`만 사용한다. 상세 URL도 화면용 요청 번호와 필요한 작업 참조값만 사용한다. 내부 `Request.id`·`WorkItem.id`는 상태 참조와 내부 명령 처리 안에서만 사용하고 URL, DOM 텍스트·속성, 접근성 이름, 알림·이력 문구, 복사 텍스트에 넣지 않는다.
- `RequestSummary.revision`과 `WorkItemView.revision`은 충돌 검사용 화면 버전이다. 화면은 내부 ID 대신 `requestNumber`·`workNumber`와 이 revision을 제출한다. 저장소가 내부 대상을 하나로 해석한 뒤 현재 세션의 역할·소속 작업반 권한을 검사하며, 값이 일치하지 않으면 변경하지 않는다.
- 조회 메서드는 역할·행동자·작업반 인자를 받지 않는다. `SessionManager`의 현재 `RoleContext`만 사용하며, 화면 입력으로 역할·행동자·소속 작업반을 덮어쓸 수 없다.

## 5. 합성 기준 데이터 목록과 검토 방법

`FixtureCatalog.load()`가 반환할 최소 구성 (`SR-DEMO-001·002·005·038` 근거):

- 계정: 요청자 1개 이상, BNOC 1개 이상, **서로 다른 작업반 소속 작업반 계정 2개 이상**. 권한 관리자 계정은 없음
- 작업반 고정 5개: 무선반·유선반·전장반(전산장비)·정체반·암호반
- 요청 사례: `대기`·`문서 대기`·`배정`·`작업 중`·`완료`·`취소` 각 1건 이상, 그중 하나는 작업반 2곳 이상에 배정된 복수 배정 사례, 하나는 `반환` 후 재배정된 사례
- 모든 요청의 화면용 번호: `101`부터 증가하는 중복 없는 정수형 문자열. 모든 작업의 화면용 참조값: 요청 안에서 중복 없는 `101-1` 형식. 둘 다 내부 식별값과 다른 값 사용
- 일정: 일정 있는 작업과 일정 미정 작업 각 1건 이상
- 선조치 후보고로 생성된 완료 사례 1건
- 알림: 5.3절 이벤트 종류별 1건 이상
- 이력: 위 상태 변경들에 대응하는 항목
- 첨부: 메타데이터 예시 1건 이상

검토 방법: 사람 이름·소속·위치·군번·연락처는 전부 자연스러운 합성값이며 `OOO`·`XXX`·`<이름>` 같은 가림·자리표시자가 없는지 사람이 눈으로 확인한다(`SR-DEMO-002`). 실제 부대·인물 자료가 섞이지 않았는지 배포 전 마지막으로 재확인한다.

## 6. 빌드·검사·배포 명령과 호스팅 공급자

```bash
npm run dev      # vite --host 127.0.0.1 (frontend/package.json, 기존)
npm run build    # tsc --noEmit && vite build (frontend/package.json, 기존 — 서버 빌드 스텝은 이 아키텍처에 없음)
npm test         # node --test로 위 *.test.mjs 전부 + Playwright e2e 별도 실행
```

호스팅: **OpenAI Sites**. `.openai/hosting.json`이 이미 이 저장소에 구성돼 있다(`project_id`, `d1: "DB"`). 이 아키텍처는 D1을 쓰지 않으므로 `d1` 바인딩은 불필요하다 — 기존 프로젝트를 그대로 재사용할지, 백엔드가 있던 이전 배포와 분리해 새 Sites 프로젝트를 만들지는 배포 시점에 정한다(둘 다 이 문서의 아키텍처 결정에는 영향 없음). ARCH-011 "정적 호스팅은 HTTPS와 SPA 경로 대체를 지원해야 한다"는 OpenAI Sites가 이미 충족한다.

## 8. 사용자 승인 결과

1. 화면용 요청 번호를 `101`, 같은 요청의 복수 작업 참조값을 `101-1` 형식으로 확정한다(DEC-030).

5. 4절 필수 회귀 사례가 충분한가.
