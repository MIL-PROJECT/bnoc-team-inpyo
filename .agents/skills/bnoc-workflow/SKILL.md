# BNOC 업무 근거와 검증

이 저장소의 업무 해석 오류를 줄이는 절차다. 경로는 저장소 루트 기준이다. 제품 범위·권한·현재 문서 우선순위는 `AGENTS.md`를 따른다. 루트 `개발명세서.md`는 현재 통합 명세다. `.local/` 폐기본과 Git의 옛 계약을 현재 지침으로 쓰지 않는다.

## 설계의 연결 순서

요구사항·유스케이스를 먼저 정의하고, 이를 구현 관점의 시스템 요구사항(기능 명세)으로 구체화한다. 시스템 요구사항을 각 모듈에 배정하며 행동·입력·출력·호출 관계를 설계한다. 아키텍처 웹은 이 배정과 연결을 검토하는 도구다. 일반적인 서버 구성 설명이나 기능 목록으로 대신하지 않는다. 그 뒤 개발 명세를 작성하고 사용자 승인 후 구현한다.

기존 웹을 수정할 때는 사용자 첨부·실제 화면·출처부터 대조한다. 이름이 비슷하거나 과거 AI가 복구했다고 보고했다는 이유만으로 원본으로 단정하지 않는다. 원본 복구본은 Git `fed2b10`에 보존했다. 현재 `아키텍처설계.html`은 원래 탐색 방식을 유지한 백엔드·운영 기능 검토안이다. 복구 단계의 본문 불변 검사를 이후 사용자 승인 설계 개정에 강제하지 않는다. 기능 명세·모듈 배정의 일치와 미정 사항·구현 승인 상태를 확인한다.

## 시작: 정답의 근거 확보

- `AGENTS.md`, 관련 `요구사항.md`·`유스케이스.md`·`아키텍처설계.html`과 `시스템요구사항.md`·`아키텍처설계.md`·`개발명세서.md`를 읽는다. 관련 ID만 연결하며 절차 변경에 제품 ID를 만들지 않는다.
- `docs/업무검증기록.md`에서 같은 주체·동작·모듈의 실패와 재검사 명령을 찾는다. 해결됐다는 기록만 믿지 말고 이번 코드에서도 관련 검사를 실행한다.
- 구현 전 `docs/작업기록.md`의 해당 작업에 아래 한 줄 형식으로 필요한 합격 사례를 남긴다. 단순 문구 수정에는 새 사례를 만들지 않는다.

`출처·상태 | 누가·언제 | 행동·입력 | 기대 결과 | 금지 결과 | 확인 방법`

상태는 사용자 결정 / 기존 명세 / AI 제안 / 미확정으로 구분한다. 출처는 문서 절·커밋 또는 사용자 메시지의 위치와 필요한 짧은 인용이다. 요약을 직접 인용으로 표시하지 않는다. 개인정보·부대 운영 자료를 전사하지 않는다. 원문이 제공되지 않았으면 없는 승인·인용을 만들지 않는다.

최신 사용자 결정과 기존 문서가 다르면 결정과 영향을 명시해 문서를 맞춘다. 분명히 승인된 변경을 다시 묻지 않는다. 원문·기존 자료로도 정해지지 않은 업무 의미만 구체적으로 질문하고, 답에 의존하지 않는 일은 계속한다. 기술 구현 방법은 범위 안에서 판단한다.

질문은 군 내부의 실제 담당 주체·절차·도메인 의미에 한정한다. 공개 사실은 공식 자료부터 조사하며, 일반적인 CRUD·화면 동작·기술값은 에이전트가 판단해 근거와 영향으로 기록한다. 요청하지 않은 기능을 먼저 상정하고 사용자에게 필요 여부를 묻지 않는다. 임시 단계명·가짜 이름·합성 계급을 만들지 않는다. 기획·설계에서 실제 업무 미결을 해소하고 기능 동작·입출력·모듈·API에 연결한 뒤 구현 검토로 넘긴다. 실제 공군 규격처럼 지금 확인할 수 없는 후속 실연동 조건은 대회 모의 구현의 업무 미결과 구별한다.

문서와 사용자 결정을 먼저 맞추고 설계 웹·코드를 변경한다. 기존 문서의 해당 절을 갱신하며, 새로운 종류의 문서는 목적·기존 문서로 해결할 수 없는 이유·경로를 설명해 사용자 승인을 받은 뒤 만든다. 기존 문서 이동·통합 지시는 재승인 없이 수행한다. Markdown 묶음으로 기존 설계 웹을 대신하지 않는다.

## 구현·검토: 기대값 바꿔 통과시키지 않기

- 정상 사례와 금지 사례를 먼저 고정한다. 기록 위치·시작 커밋·관련 파일 diff를 검토자에게 전달한다. 기대값을 바꿔야 한다면 새 사용자 결정이나 기존 근거의 정정 사유를 남기고 별도 검토를 받는다. 같은 파일시스템의 역할 분리·해시는 접근 차단이 아니라 변경 확인 수단이다.
- 기존 `spec_mapper`·구현자·`reviewer`·`verifier`를 사용한다. 검토자는 업무 근거 일치와 코드 품질을 구분한다. 검증자는 원문과 기대 결과를 직접 확인한다. 구현자 설명이나 AI 자기평가만으로 통과 처리하지 않는다.
- 실제 코드·명령 결과로 판정한다. 화면 변경은 해당 역할·입력·저장 결과를 관찰한다. 현재 제품에 없는 서버·SSO·영속 기능을 검증됐다고 표현하지 않는다.

## 검사 자체의 능력 점검

업무 주체·권한·필수 입력처럼 중요한 기준의 검사를 새로 만들거나 바꿀 때 적용한다. 관련 기준이 없거나 순수 문구·서식 수정이면 생략 이유만 기록한다.

1. 정상 코드와 오류 코드의 임시 복사본을 별도로 만든다. 수정 전 원본의 변경 상태·해시를 보존한다. 현재 사용자 작업을 덮어쓰거나 초기화하지 않는다.
2. 정한 업무 규칙을 어기는 대표 오류 하나를 오류 복사본에만 넣는다. 정상 사례는 통과해야 하고 오류 사례는 정한 assertion·실제 상태 차이로 실패해야 한다. 문법·모듈·환경 오류나 시간 초과는 탐지 성공으로 세지 않는다.
3. 두 결과·주입 diff·검사 버전을 보존하고 원본 불변과 자신이 만든 임시 폴더 삭제를 확인한다. 오류가 통과하면 검사의 빈틈으로 기록하고 근거에 맞춰 보강한다. 수정 중인 정상 코드가 아직 실패하면 감도 실험을 통과로 기록하지 않는다.

일정 배정·작업 일정 권한과 관련된 작업에서는 저장소 루트에서 기존 명령을 재사용한다.

```bash
node experiments/ai-workflow/run-sensitivity.mjs
```

정상 원본의 기존·계약 검사가 통과하고, 일정 자동 입력 오류는 `BNOC_ASSIGNMENT_MUST_NOT_SET_SCHEDULE`에서 실패해야 한다. 오류 복사본의 기존 시험 결과는 관찰값이다. 기존 시험이 새로 오류를 잡아 실패해도 그 자체를 실험 실패로 처리하지 않는다. 의도한 탐지인지 로그를 따로 확인한다. 주입 위치가 바뀌면 근거를 유지해 실행기를 갱신하고 재검증한다. 이 실험 하나로 다른 업무의 검사가 검증되지는 않는다.

실행기 변경 시 `node --test experiments/ai-workflow/run-sensitivity.test.mjs`도 실행한다. 추가 자세한 조건은 `experiments/ai-workflow/README.md`를 필요할 때만 읽는다.

## 실패 재사용과 종료

- 재현한 문제는 `docs/업무검증기록.md`에 발생 버전·실제 결함/인공 오류 구분·근거·예상/실제·실행 명령·검사·증거·다음 실행 조건·마지막 결과를 연결한다. 이미 있는 사례면 갱신하며 과거 실패와 결과를 지우지 않는다.
- 실제 사용자 결정·입력 프롬프트·채택 코드·검사·커밋을 작업/개발/AI 기록에 연결한다. 누락된 과거 프롬프트나 측정치를 재구성해 실측처럼 쓰지 않는다.
- 같은 문제가 재발했는지, 사람이 실제 수정 의견을 준 횟수, 확인된 경과 시간·사용량을 기록한다. 자동 리뷰 수정과 사람 수정을 구분하고 얻지 못한 값은 미측정으로 둔다. 비교 실험을 하지 않았다면 개선율·최적성은 미검증이다.
- 마지막 결과는 통과 / 실패 / 미실행과 잔여를 구별한다. 필수 검사 실패·의도하지 않은 기대값 변경이 남으면 완료로 기록하지 않는다. 안전하게 실행할 수 없는 부분은 이유와 필요한 조건을 보고하고 나머지 작업은 마친다.
